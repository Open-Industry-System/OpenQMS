# Synthetic task issuance

The trusted host runs `issue.py` inside the API containers of the two exclusive D4 cases. The two cases use separate databases, tenants, installations, grants and tasks. The host generates the report UUID for the current lease and passes the same value to both cases, so the browser can trigger both acceptance actions on the same report.

Inject a host-reviewed copy of the script into the container interpreter, or mount it read-only inside the container. Call it only after confirming the container ID, candidate build, lease label, internal network and database instance. The container process runs as UID/GID 2002; the script reads one JSON document from stdin. Both phases use exactly the same input.

- `binding` contains the current `pr`, `head`, `merge`, `plan`, `lease`, `report_id`, `issued_at` and `expires_at`.
- `db_host` is the fixed Unix socket path `/run/openqms-d4-db` for normal delivery and, for the revocation case, the internal DNS name of the dedicated database used by the candidate API's `DATABASE_URL`. The database is named `qms_d4_acceptance`; its `pg_control_system()` system identifier must equal `db_system_identifier`. Database initialisation must grant the API user permission to read that identifier and complete the normal application initialisation. First create the `openqms_d4_witness` role without write permissions; the trusted database initialiser grants it read access to `pg_control_system()`. The issuance script grants it read access to the acceptance metadata columns of the newly created tenant.
- `api_port` is the numeric loopback API port inside the container. Set `TENANT_MODE=dev`, `AGENT_TASK_RUNTIME_ENABLED=true`, `AGENT_D4_TEXT_LOCAL_TRIAL_ENABLED=true` and `AGENT_D4_TEXT_LOCAL_TRIAL_POLICY_FILE=/run/openqms-d4-issue/policy.json`.
- Mount `/run/openqms-d4-issue` in the exclusive container. The directory is owned by the API UID with mode `0700`, files use mode `0600`. Each case uses a fresh directory.

Run `issue.py prepare` first. It creates the synthetic tenant, an administrator, a least-privilege Viewer, an FMEA, an 8D report and a restricted installation. The script writes `policy.json`, `receiver.json` and `private-state.json`. Restart the application in the same API container so that start-up loads the new restricted policy. The installation secret exists only in `receiver.json`; the host uses it for verification and to feed the fixed receiver's stdin. Synthetic login credentials are written only to `private-state.json`. The host reads these files by fixed name, without following links, after checking owner and mode, and uses each field only as defined. Neither the candidate report text nor these files may be written to logs, PRs, public previews or GitHub artifacts.

Then run `issue.py task`. Through real loopback application routes it creates the source declaration, a derived source grant, enables the installation and creates a ready task as the synthetic Viewer. Phase results contain only the synthetic tenant, schema, generation, report, installation and actor IDs; the second phase additionally contains the grant and task IDs. The host verifies the IDs from both phase results, uses the dedicated read-only witness role to confirm that the task is still unclaimed, and only then opens the browser actions. The trusted portal reuses the current test slot's Engineer or Manager account and grants per-scenario permissions according to the acceptance plan. The shared test password continues to be delivered through a private channel.

Each phase is a one-shot operation; a single-use marker in the private directory rejects concurrent duplicate issuance. If a phase fails midway, the lifecycle controller reclaims the whole exclusive case; a new lease issues again later. Regular candidate services and databases still run in exclusive containers and internal networks.

The synthetic administrator serves only its exclusive tenant and the trusted revocation control; cleanup after the phase must remove the container, database and private mount directory. The two-phase issuance was verified locally with an exclusive PostgreSQL and a real loopback OpenQMS API; the task reached ready. Issuance on the real Oracle host is **NOT_RUN**.
