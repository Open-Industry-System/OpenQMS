# D4 browser portal

This portal is deployed on a trusted HTTPS domain. For one issuance it shows the synthetic report identifier and two fixed actions; the browser sends an empty POST to `/scenario/d4-deliver` or `/scenario/d4-revoke`. It is reachable from the "D4 acceptance" link in the shared test site header. Log in with the current test slot's Engineer or Manager account; the portal only offers the actions that the acceptance plan assigns to that role. The portal rejects cross-origin actions, expired issuances and receipts with mismatching identities. If the executor or a real receipt is missing, it shows "Blocked".

Each service instance is bound to PR, head, merge, plan, test slot, synthetic report and validity window through a protected configuration file. The file is owned by the service user with mode `0600`. It contains the shared accounts in `accounts` (each with `role`, a 16-byte hexadecimal `salt` and a `password_digest` derived with scrypt parameters `n=16384,r=8,p=1`), the `scenario_roles` from the acceptance plan, `origin`, `executor_socket` and `report_label`. `binding` holds `pr`, `head`, `merge`, `plan`, `lease`, `report_id` and integer Unix seconds `issued_at` and `expires_at`. A round lasts at most one hour. The standalone HTTPS portal prompts for the shared test account. The trusted host derives the verifier from the current test slot's root-only issuance record; candidate application login tokens and role claims play no part in portal identity checks.

Starting the portal:

```bash
python3 deploy/d4-acceptance/browser.py \
  --config "$D4_ACCEPTANCE_CONFIG" --port 8444 \
  --cert "$D4_ACCEPTANCE_TLS_CERT" --key "$D4_ACCEPTANCE_TLS_KEY"
```

The service binds to loopback; a trusted gateway provides the entry point. The executor serves through a dedicated root-owned Unix socket whose parent directory must not be writable by ordinary group members. After the connection's write side is closed, the portal reads one JSON document. The request contains `binding`, the fixed `scenario` and this `operation`. The executor must independently re-check the current version, issuance and report, run the reviewed fixed receiver scenario and read the actual records from the platform. The response echoes only the three request fields plus `task_id`, `run_id`, `delivery_before`, `delivery_after` and `denial`. Normal delivery requires the count to increase by one; revocation requires `denial=source_revoked` and an unchanged count. Text, passwords and installation secrets never appear in the response.

Browser portal, task issuance, receipt gate and dedicated resource cleanup all have local coverage. Enabling on Oracle still follows the existing approval. See [Oracle shared test integration](../../docs/shared-test-queue.md).

## Trusted execution wiring

After approval, install this set of files as a trusted service in a root-owned directory the application cannot write to. Run `python3 executor.py --profile "$D4_EXECUTOR_PROFILE"`. The profile must be located at `/var/lib/openqms-shared-test/d4/<lease>/profile.json`; file and parent directory are root-owned with `0600` and `0700`. The control directory `/run/openqms-d4-acceptance` is root-owned, readable by the browser service group, mode `0750`. The Unix socket accepts only the non-root browser service UID/GID from the profile.

The execution profile contains the same `binding`, `portal_uid`, `portal_gid` and two `cases`. Each scenario uses a separately prepared API container, task and lease database. It must be prepared from the reviewed runtime bundle; candidate code runs as an isolated application image. Each case declares:

| Field | Trusted source |
| --- | --- |
| `root`, `manifest_sha256`, `nonce` | Native runtime bundle of the normal delivery case, using the fixed `/run/openqms-d4-<nonce>` root |
| `api_container_id` | The candidate API container of each case |
| `db_container_id`, `db_image_id`, `db_system_identifier` | Container and PostgreSQL identity of the exclusive internal database |
| `tenant_id`, `schema`, `generation` | Synthetic tenant |
| `task_id`, `installation_id`, `grant_id` | Task and actual grant created in this round |
| `revoke_image_id` | Actual ID of the separately reviewed OCI image of the revocation case, `sha256:<64 hex>` |

The database witness role `openqms_d4_witness` only accesses `qms_d4_acceptance` and runs read-only queries through the container-internal PostgreSQL socket. During preparation it is granted read access to the target tenant's metadata tables and to `pg_control_system()`. Cluster, container, image, internal network and tenant generation must match the issuance record.

The revocation case runs a separately reviewed Linux receiver. The host starts this one-shot container from a fixed OCI image ID with a non-root UID, read-only root filesystem, no extra Linux capabilities, no host mounts and Docker container logging disabled. The container joins the verified network namespace of this round's candidate API and requests the same API at a fixed numeric loopback address. It receives this round's synthetic identity and task data only via stdin. After the first permitted read it outputs a receipt containing only five bound identifiers and pauses. The agent independently verifies the current run, the still-valid source grant and one committed delivery, then sends the fixed revocation instruction. The receiver disables the grant and reads again with the original token, expecting an actual HTTP 401 without text in the response. The agent then reads PostgreSQL to verify the revocation audit and delivery count and, once the receiver container is confirmed deleted, writes the receipt to the gate.

The execution agent checks the test slot inside the existing Oracle host lock. The native launcher records a success receipt and completion time only after verifying that watchdog and receiver were reclaimed. The shared test workflow reads the active lease receipt through the existing restricted SSH channel. The GitHub artifact contains only version and lease binding, receipt digest and validity. The gate additionally requires authorised people to confirm each item after the receipt was created and before the issuance expires. Oracle re-reads the current receipt on sign-off; the queue keeps the current lease until the dedicated issuance directory is cleaned up.

Once the lease enters `releasing`, the issuance service should stop the dedicated HTTPS portal and agent, revoke accounts and grants, remove synthetic tasks and exclusive runtime resources, and remove this round's issuance directory after confirming actual reclamation. Actual issuance on Oracle, revocation control, both browser scenarios, automatic cleanup and the online CI hand-off are **NOT_RUN**. Issuance and revocation were verified locally with the real #45 application and an exclusive PostgreSQL: the actual grant read returned 200, after revocation in the same run it returned 401, the delivery count stayed 1 and the revocation audit gained one entry. Docker cleanup was verified on local temporary resources via external endpoint rejection and reclamation of exclusive objects. Host systemd and Oracle were not exercised.

## Issuance and cleanup after approval

1. After Oracle approval, run `bash deploy/d4-acceptance/install.sh` from the reviewed version. It installs the dedicated services and trusted scripts. The trusted HTTPS gateway points to host loopback 8444 and uses `/etc/openqms/d4-acceptance/tls-cert.pem` and `tls-key.pem` for the dedicated domain. The private key is managed by root; systemd hands it to the browser process via service credentials.
2. Within the active shared test lease, prepare two identical isolated cases from the same reviewed candidate backend image, with two separate APIs, databases and private directories. Create a root-only lease directory, then prepare the Docker objects with the names and labels below. Once container and database identifiers are known, and before preparing the native root, register `/var/lib/openqms-shared-test/d4/<lease>/prepared.json` (0600). The file has two fields, `binding` and `cases`; `binding` uses the current version and one new synthetic report UUID. Each case sets `api_container_id`, `db_container_id`, `db_image_id`, `db_system_identifier`, `db_host` and `api_port`. Normal delivery additionally sets `root`, `manifest_sha256`, `nonce`; revocation additionally sets `revoke_image_id`. See [synthetic task issuance](ISSUANCE.md).
3. Docker objects carry the label `openqms.d4-acceptance.lease=<lease>`; API and database additionally carry the role label `openqms.d4-acceptance.role=api` or `postgres`. Containers are named `openqms-d4-<lease>-{deliver,revoke}-{api,postgres}`; volume names end with `-postgres-data`. Each API mounts the lease's `d4-deliver` or `d4-revoke` private directory at `/run/openqms-d4-issue`, a 0700 directory owned by UID/GID 2002. The secrets of both cases stay in their own exclusive files; receipts reference identifiers only.
   - Both PostgreSQL instances and the revocation API sit on the internal bridge `openqms-d4-<lease>`; the revocation API uses the internal DNS name of its exclusive database.
   - The normal delivery API uses `--network none`. The native receiver requires its network namespace to listen on exactly one numeric loopback API port. A custom Docker bridge adds DNS listeners and nftables rules that conflict with this check.
   - Create `/var/lib/openqms-shared-test/d4/<lease>/d4-deliver-db-socket`, owned by the non-root UID of that synthetic PostgreSQL, directory mode 0755. The normal delivery database mounts it writable at `/var/run/postgresql`, keeps the default 5432 socket port and disables TCP listening. The normal delivery API mounts the same directory read-only at `/run/openqms-d4-db`. In that case's `prepared.json`, set `db_host` to `/run/openqms-d4-db`; the API's synthetic DSN is `postgresql+asyncpg://<synthetic-user>:<password>@/qms_d4_acceptance?host=/run/openqms-d4-db`. Before issuance verify that both containers mount the same lease directory and that the PostgreSQL socket is owned by the directory owner.
4. As root, run `python3 /usr/local/lib/openqms/d4-acceptance/provision.py --lease <lease>`. It verifies the actual candidate image ID, initialises the real tenant and task, independently verifies the pending state in PostgreSQL and writes the protected profile. Then run `python3 /usr/local/lib/openqms/d4-acceptance/portal_issue.py --profile /var/lib/openqms-shared-test/d4/<lease>/profile.json --origin https://<private-host> --deliver-role field_qe --revoke-role field_qe`. These are the role settings of #45; other PRs fill in both roles according to the acceptance plan matching the current lease's plan digest. Shared test accounts continue to be issued privately from the existing root-only record. Start `openqms-d4-acceptance-portal@<lease>.service`, which starts this round's execution service.
5. Queue retirement triggers the installed `cleanup.py`. It verifies the lease being cleaned up, stops this round's services, verifies that the used native receiver was reclaimed and deletes this round's exclusive Docker objects, credentials and lease directory. If reclamation cannot be verified, the queue keeps the lease and the next poll retries.

Build the revocation receiver from the reviewed source root and pin the approved Python base image digest explicitly. The Dockerfile verifies the digest of the reused read-only receiver worker file.

```bash
docker build --build-arg BASE_DIGEST=sha256:<approved-base-digest> \
  -f deploy/d4-acceptance/revoke-receiver.Dockerfile -t openqms-d4-revoke:reviewed .
docker image inspect --format '{{.Id}}' openqms-d4-revoke:reviewed
```

Write the printed image ID into the root-only preparation record of this round's revocation case. The existing #45 normal delivery still uses the native controller. Local verification has two parts: a real Linux container and Docker attach verified both receipt phases against an isolated HTTP fixture, and the same entry script, connected to the real #45 application and an exclusive PostgreSQL, verified two real requests and the read-only audit. Joint testing of the real Linux container with the real Oracle application, browser acceptance, and automatic switch to #46 after #45 cleanup are **NOT_RUN**.
