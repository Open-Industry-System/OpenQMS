# 子故事 US-E2E-01.6：D8 关闭前文档更新审核（影响分析 + 自动化审核门禁）

**状态**: 定稿 v1（2026-07-08）
**所属 epic**: US-E2E-01（README.md v8）
**关联 skill**: `verify-capa-8d-doc-update-gate`
**前置**: 01.2、01.3（8D 根因+预防 node-action 数据就绪，方可知哪些文档受影响）

## 故事

**作为** 8D 团队负责人 / 现场质量工程师，**我想** 在 8D 报告完成、D8 关闭审批前，
系统自动**分析 8D 报告**识别需更新的相关受控文档（控制计划、FMEA、作业指导书/SOP 等），
并**自动化审核**这些文档的更新情况（是否已更新、更新是否到位），
D8 关闭审批前必须通过此审核门禁，
**以便** 8D 发现的改进真正落到受控文档、文档与实际不脱节、关闭审批有据可依。

## 背景 / 前置条件

- 系统已部署，8D 已推进至 D7（根因 + D7 node-action 已落库，01.2/01.3 就绪）。
- 对应产品已有控制计划、FMEA、作业指导书（SOP）等受控文档。
- AI 步骤必须配置 `.env.e2e` 的 LLM 凭证（文档影响分析用 LLM）。

## 能力 A：文档影响分析

8D 报告完成后（D7 填写后），系统自动分析 8D 报告，识别需更新的相关受控文档：

- **受影响文档类型**（识别清单）：控制计划（Control Plan）、FMEA（PFMEA/DFMEA）、作业指导书（SOP/Work Instruction）、检验作业指导书、其他受控文档（如适用）。
- **影响分析依据**：8D 的根因、D5 永久措施、D7 预防 node-action、严重度。
- **输出**：受影响文档清单 + 每项更新建议（哪些章节/节点需更新、更新方向）。
- **AI 辅助**：AI 基于 8D 报告内容分析受影响文档范围 + 更新建议（辅助，工程师确认）。

## 能力 B：文档更新自动化审核（D8 关闭门禁）

D8 关闭审批前，系统自动化审核相关文档的更新情况：

- **审核内容**（每项受影响文档）：
  - 是否已更新（版本号 bump、更新时间在 8D 发起之后）；
  - 更新是否到位（关键更新点是否覆盖——控制计划是否新增/修改对应控制特性、FMEA 节点是否更新、SOP 是否修订）；
  - 审核状态（通过 / 待更新 / 更新不完整）。
- **门禁规则**：
  - D8 关闭审批前，文档更新审核必须通过（所有受影响文档状态 = 通过）；
  - 未通过时，8D 团队负责人不可批准 D8 关闭（门禁阻断）；
  - 可显式"延期处理"并备注理由 + 责任人 + 期限（延期需记录，不绕过门禁）。
- **审核报告**：生成文档更新审核报告，含每项受影响文档的审核状态 + 证据（版本号、更新点）。

## 主流程

1. field_qe 完成 D7（含 node-action），8D 报告数据就绪。
2. 系统自动触发文档影响分析：识别受影响文档清单 + 更新建议。
3. 工程师按建议更新相关文档（在 FMEA/控制计划/SOP 各模块操作）。
4. 8D 团队负责人发起 D8 关闭审批前，系统自动触发文档更新审核。
5. 审核通过 → 可批准 D8 关闭；未通过 → 门禁阻断，显示未通过文档清单 + 原因。
6. 延期处理需记录（理由/责任人/期限），不绕过门禁。
7. 审核报告 + 门禁决策写审计日志。

## 业务规则 / 验收标准

- **文档影响分析**：8D 报告完成后自动触发，识别受影响文档清单（至少覆盖控制计划/FMEA/SOP）；每项带更新建议（AI 辅助 + 工程师确认）；清单落库可追溯。
- **文档更新审核门禁**：
  - D8 关闭审批前自动审核，每项受影响文档有审核状态；
  - 未全部通过时 8D 团队负责人不可批准 D8 关闭（门禁阻断，E2E 验证阻断生效）；
  - 延期处理需记录理由+责任人+期限，不绕过门禁；
  - 审核依据 = 文档版本号 bump + 更新时间 + 关键更新点覆盖。
- **审核报告**：生成文档更新审核报告，含每项文档状态 + 证据。
- **审计**：影响分析结果、审核状态、门禁决策（通过/延期）、延期记录均写审计日志。
- **数据落库**：受影响文档清单、审核状态、审核报告、门禁决策记录正确持久化。
- **执行验证**：E2E 断言影响分析 → 审核 → 门禁阻断/通过 → 审批的完整链路。
- **与 01.3 的衔接**：01.3 的 D7→D8 审批前引用本子故事的门禁状态；门禁未通过时审批不可进行。
