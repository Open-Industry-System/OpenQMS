## 1. 背景与现状

D3（临时/遏制措施）当前仅 `capa_eightd.d3_interim` 文本字段 + `capa_draft_service` 的 AI 文本草稿。故事要求的"数据导入 → 受影响范围分析报告 → AI 遏制建议"链路完全缺失，D3→D4 无闸口。

**可复用基础设施**：
- `ERPInventoryBalance`（material_code/location_code/lot_no/quantity/inventory_status/snapshot_at）— 库存
- `ERPShipment`（shipment_number/customer_code/material_code/lot_no/quantity/shipment_date）+ `ShipmentRecord`（customer_id/batch_no/quantity/destination）— 发货/物流
- `IqcInspection`（supplier_id/lot_no/defect_description/inspection_result/inspection_date/defect_qty）— 查 iqc_inspections 非 iqc_materials
- `SPCAlarm` + `InspectionCharacteristic`（`SPCAnomalySource` 30 天判异口径）— SPC
- `Customer`（customer_code/name/segment）— 客户关键性
- `recommendation_orchestrator` 的 `StageRun` + `RecommendationResult(blocked=True)` 模式
- `capa_draft_service` 的 DB-backed timeout + `_generate_and_validate` 重试 + `MAX_PROMPT_CHARS=8000` 截断 + safety_trailer
- `provider_adapter.complete_json`
- 迁移测试基础设施 `backend/tests/migrations/`（`mig_db_url` + `_cfg`）
- `CapaRootCauseVerification.evidence_attachments`（JSONB `[]`，无受控附件表先例）

**字段缺口**：物流到货状态（arrival_status）在 ERPShipment/ShipmentRecord 均无字段。v4 口径：**从 `ERPShipment.erp_raw_data["arrival_status"]` 读取**，仅接受 `in_transit`/`signed`/`unknown` 枚举值；缺失或非法时回退 `unknown`（finding 4，不制造假事实，也不靠日期/地址推导）；E2E seed mock 在 erp_raw_data 显式注入；**风险下限**：unknown 且有受影响客户时 `deterministic_risk_floor='high'`，后端 `risk_level = max(llm_risk, floor)`（非靠 prompt 指示）。

## 2. 架构总览

D3 遏制链路是独立于 12 阶段 DAG 的 3 阶段流，按不可变 generation 组织（**v4：generation 覆盖到 advice**）：

```
import_run (代根, is_current)
 ├─ import: [inventory, shipment, iqc, spc] 4 子源，库内查询 → JSONB 快照（run 内 UQ type）
 ├─ analyze: 报告 5 项 — 事实确定性计算(批追溯/数量/客户/时间窗) + LLM 风险分级（受后端 floor 约束）+ 解释
 ├─ advice_generation (代, is_current) → llm_advice: LLM 消费报告事实 → 建议绑 generation_id
 └─ execution: 工程师执行记录（manual 或 adopted advice，绑 report generation）
       ↑ adoption: 单一当前决策 UQ(advice_id) + 文本修订审计（保 report_id 归属）
                           → D3→D4 闸口（当前 generation，读最新有效 execution）
```

- **不可变 generation 覆盖 run→report→advice_generation→advice**（finding 1）：每层 is_current + partial UQ；adoption/execution 绑当前 generation。
- **两阶段事务 + 重检 is_current**（finding 5）：事务 A 提交 run/快照 → 事务 B 获锁后重检 run.is_current，过期返回 `superseded` 不调 LLM。
- **后端 risk floor**（finding 4）：`risk_level = max(llm_risk, deterministic_floor)`，unknown+受影响客户→floor=high。
- **record_key 定义 + provenance 按 advice_type 映射**（finding 3/6）：每类稳定 record_key；alternative 允许 report-level `{report_id, aggregate_key}` schema。
- **复合 FK 保证 factory 一致**（finding 6）：父表 (id, factory_id) UQ + 子表 (parent_id, factory_id) 复合 FK。
- **审计实体保留 policy**（finding 2）：adoption 保不可空 report_id（CAPA 归属）；execution report_id RESTRICT（不可变 report 不删）；CAPA 删除时 adoption/adoption 审计行保留（advice_id SET NULL 但 report_id 保留可归回 run→capa 链）。

每阶段产 `StageRun{name, status, hit_count, summary, error?}`。无 LLM 凭证时 analyze/llm_advice BLOCKED。

新增服务 `backend/app/services/capa_d3_containment_service.py`。复用 `StageRun`/`RecommendationResult` 数据结构，不复用 12 阶段 DAG。

## 3. 数据模型（7 张新表，一个 Alembic 迁移）

所有表 `factory_id` NOT NULL。**冗余可派生列去除**：snapshot/report/advice/execution 不存 capa_id（可从 run→capa 派生），只存 run_id；adoption 不存 capa_id，保不可空 `report_id`（CAPA 归属，finding 2）。

**复合 FK 保证 factory 一致**（finding 6）：父表（run/report/advice_generation/advice）建 `UNIQUE(id, factory_id)`；子表用 `FOREIGN KEY(parent_id, factory_id) REFERENCES parent(id, factory_id)` 复合 FK，DB 级保证子表 factory_id 与父一致，杜绝跨工厂。adoption 的 report_id 同样用复合 FK（保归属 + factory 一致）。factory_id 同时保留为普通列（RBAC 过滤，防 N+1）。

**审计实体保留 policy**（finding 2）：
- `capa_d3_advice_adoption.advice_id` = ON DELETE SET NULL（建议删留痕），但 `report_id` 不可空（CAPA 归属链 report→run→capa 可追溯）。
- `capa_d3_execution.report_id` = ON DELETE RESTRICT（不可变 report 原则上不删；删 report 须先删 execution）。`advice_id` = SET NULL（manual 无 advice）。
- CAPA 删除（CASCADE 到 run→report）：report CASCADE 删时，execution 因 RESTRICT 阻断（须显式删 execution）；adoption 的 report_id 复合 FK 用 RESTRICT 或先迁移——**采纳 RESTRICT，删 capa 前须清理 execution/adoption**，避免静默丢审计。

### 3.1 `capa_d3_import_run` — 导入代根

| 列 | 类型 | 约束 |
|---|---|---|
| `run_id` | UUID PK | default uuid4 |
| `capa_id` | UUID FK→capa_eightd.report_id | ON DELETE CASCADE, NOT NULL |
| `factory_id` | UUID FK→factories.id | ON DELETE RESTRICT, NOT NULL |
| `is_current` | Boolean | NOT NULL, default true |
| `status` | String(12) | CHECK IN ('importing','completed','failed'), NOT NULL, default 'importing' |
| `imported_types` | JSONB | `["inventory","shipment","iqc","spc"]` |
| `started_at` | DateTime(tz) | server_default now() |
| `completed_at` | DateTime(tz) | nullable |
| `imported_by` | UUID FK→users.user_id | NOT NULL |
| `created_at` | DateTime(tz) | server_default now() |

**partial unique index**（finding 2）：`UNIQUE(capa_id) WHERE is_current = true`。新建 run 时旧 run is_current 置 false（同一事务，锁 capa 行 FOR UPDATE）。所有生成/重试入口锁 capa 行。**复合 FK 基础**：`UNIQUE(run_id, factory_id)`（子表 snapshot/report 复合 FK 用）。

### 3.2 `capa_d3_containment_snapshot` — 导入快照

| 列 | 类型 | 约束 |
|---|---|---|
| `snapshot_id` | UUID PK | default uuid4 |
| `run_id` | UUID FK→capa_d3_import_run.run_id | ON DELETE CASCADE, NOT NULL |
| `factory_id` | UUID FK→factories.id | ON DELETE RESTRICT, NOT NULL |
| `snapshot_type` | String(20) | CHECK IN ('inventory','shipment','iqc','spc'), NOT NULL |
| `payload` | JSONB | NOT NULL — 原始记录副本 |
| `source_query` | JSONB | 生成快照的查询参数 |
| `record_count` | Integer | NOT NULL, default 0 |
| `imported_by` | UUID FK→users.user_id | NOT NULL |
| `imported_at` | DateTime(tz) | server_default now() |
| `created_at` | DateTime(tz) | server_default now() |

**UQ(run_id, snapshot_type)** — run 内每类唯一。**复合 FK**：`FOREIGN KEY(run_id, factory_id) REFERENCES import_run(run_id, factory_id)`。索引：`(run_id)`、`factory_id`。

`payload` 按 type 结构（**v4：每条记录统一带 `record_key` + `source_id`**，finding 3；arrival_status 从 erp_raw_data 读，finding 4）：

每条记录统一头部：`{record_key: str（类型内稳定唯一）, source_id: str（原表 PK 或复合业务键）, ...字段}`

- `inventory`：`[{record_key, source_id: balance_id, material_code, location_code, lot_no, quantity, unit, inventory_status, snapshot_at}]`
- `shipment`：`[{record_key, source_id: erp_shipment_id（含 line_number，不可只用 shipment_number）, shipment_number, customer_code, customer_name, material_code, lot_no, quantity, shipment_date, arrival_status}]`（arrival_status 从 `ERPShipment.erp_raw_data["arrival_status"]` 读，枚举 `in_transit`/`signed`/`unknown`，缺失/非法→`unknown`，**不靠日期/地址推导**）
- `iqc`：`[{record_key, source_id: inspection_id, inspection_no, supplier_id, supplier_name, part_no, lot_no, defect_qty, defect_description, inspection_result, inspection_date}]`（来源 iqc_inspections JOIN suppliers）
- `spc`：`[{record_key, source_id: alarm_id, ic_id, characteristic, triggered_at, rule_violated}]`

**batches[].batch_key 生成规则**（finding 3，target_batch_refs 依赖）：批追溯的 batch_key = `{snapshot_type}:{source_id}` 或按 (物料+批次号) 归一化（如 `inventory:{balance_id}`、`shipment:{erp_shipment_id}`），后端在 `_compute_batches` 时确定并稳定。target_batch_refs 引用此 key，后端校验存在于 report.batches。

### 3.3 `capa_d3_impact_report` — 受影响范围报告

| 列 | 类型 | 约束 |
|---|---|---|
| `report_id` | UUID PK | default uuid4 |
| `run_id` | UUID FK→capa_d3_import_run.run_id | ON DELETE CASCADE, NOT NULL |
| `factory_id` | UUID FK→factories.id | ON DELETE RESTRICT, NOT NULL |
| `is_current` | Boolean | NOT NULL, default true |
| `batches` | JSONB | 确定性批追溯 |
| `impact_qty` | JSONB | 确定性 `{in_transit, inventory, shipped}` |
| `customer_impact` | JSONB | 确定性 `[{customer_name, qty, arrival_status}]`（真名） |
| `time_window` | JSONB | 确定性 `{start, end}` |
| `risk_level` | String(8) | CHECK IN ('high','medium','low'), nullable |
| `risk_explanation` | Text | nullable — LLM 风险解释（客户名已还原真名） |
| `status` | String(10) | CHECK IN ('done','failed'), NOT NULL, default 'failed' |
| `stage_runs` | JSONB | analyze 阶段执行记录 |
| `prompt_stats` | JSONB | `{fact_chars, truncated: bool, original_total}` 容量观测 |
| `error` | Text | nullable |
| `llm_available` | Boolean | NOT NULL, default false |
| `model` | String(40) | nullable |
| `generated_by` | UUID FK→users.user_id | NOT NULL |
| `generated_at` | DateTime(tz) | server_default now() |
| `created_at` | DateTime(tz) | server_default now() |

**partial unique index**：`UNIQUE(run_id) WHERE is_current = true`（**含义澄清 finding 5**：每 run 至多一条 current report；跨 run 的旧 report 仍可能 is_current=true，故所有查询必须先锁 current run，再在该 run 下取 is_current report，不可直接按 report.is_current 全局查）。`status='done'` 才被闸口认可。batches/impact_qty/customer_impact/time_window 确定性计算。**risk_level 受后端 floor 约束**（finding 4）：`risk_level = max(llm_risk, deterministic_floor)`，其中 `deterministic_risk_floor` = 若 customer_impact 存在 arrival_status='unknown' 的受影响客户则 `'high'`，否则由 capa.severity 映射（critical/fatal→high，serious→medium，general→low）；floor 存 `risk_floor` 列便于审计。后端校验：`impact_qty` = batches 明细求和。新增列：`risk_floor` String(8) nullable。**复合 FK**：`FOREIGN KEY(run_id, factory_id) REFERENCES import_run(run_id, factory_id)`。

### 3.4 `capa_d3_ai_advice` — AI 遏制建议

| 列 | 类型 | 约束 |
|---|---|---|
| `advice_id` | UUID PK | default uuid4 |
| `generation_id` | UUID FK→capa_d3_advice_generation.generation_id | ON DELETE CASCADE, NOT NULL（v4，绑 advice generation，finding 1） |
| `report_id` | UUID FK→capa_d3_impact_report.report_id | ON DELETE CASCADE, NOT NULL（冗余，便于直查；与 generation.report_id 一致） |
| `factory_id` | UUID FK→factories.id | ON DELETE RESTRICT, NOT NULL |
| `advice_type` | String(24) | CHECK IN ('recall','isolate','notify_customer','strict_inspection','alternative'), NOT NULL |
| `advice_text` | Text | NOT NULL（落库前客户名已还原真名） |
| `source_provenance` | JSONB | NOT NULL — 见下方 schema（finding 3） |
| `target_batch_refs` | JSONB | nullable — batch_key（须存在于 report.batches，后端校验；非批次建议 null） |
| `stage_runs` | JSONB | llm_advice 阶段执行记录 |
| `llm_available` | Boolean | NOT NULL, default false |
| `model` | String(40) | nullable |
| `generated_by` | UUID FK→users.user_id | NOT NULL |
| `generated_at` | DateTime(tz) | server_default now() |
| `created_at` | DateTime(tz) | server_default now() |

索引：`(generation_id)`、`(report_id)`、`factory_id`。**绑 generation_id**（finding 1）：重生成建议 = 新 advice_generation，旧 generation is_current=false，旧 advice 不再采纳/执行（闸口与 GET 只认当前 generation）。**复合 FK**：`FOREIGN KEY(generation_id, factory_id) REFERENCES advice_generation(generation_id, factory_id)`。

**source_provenance schema**（finding 3，放宽以兼容 alternative）：
```json
[{"snapshot_id": "uuid|null", "record_key": "str|null", "source_type": "inventory|shipment|iqc|spc|report", "stage": "llm_advice"}]
```
- 批次类建议（recall/notify_customer/isolate/strict_inspection）：`snapshot_id` + `record_key` 非空，指向具体快照记录。
- `alternative`（无批次）：允许 `source_type='report'`，`snapshot_id=null`，`record_key=null`，但须带 `aggregate_key`（在 record_key 字段存 report-level 聚合键如 `report:{report_id}:summary`）保证非空字符串。
- **规则**：每条建议 provenance 数组非空且每元素 `record_key` 非空字符串（report-level 用 aggregate_key）；后端按 §4.3 映射，映射后为空 → 拒绝该建议。

**UQ(advice_id)** — 单一当前决策。改决策或改文本 UPDATE 该行（非新增）+ 写 `D3_ADVICE_DECISION_CHANGED` 审计（记 old/new decision + old/new adopted_text）。CHECK：`(decision='adopted' AND adopted_text IS NOT NULL) OR (decision='rejected' AND adopted_text IS NULL)`。**advice_id SET NULL 防级联删丢失留痕，但 report_id 不可空**（finding 2）：建议被删后 adoption 仍可通过 report_id→run→capa 归回 CAPA。次要1：同 decision 但 adopted_text 变化 → UPDATE + 审计 old/new 文本（不静默忽略）。**复合 FK**：advice_id 与 report_id 均 (id, factory_id) 复合 FK。**仅当前 generation 的 advice 可被采纳**（应用层校验 advice.generation_id == report 当前 generation）。

### 3.7 `capa_d3_execution` — 执行记录（v4：绑 generation + report_id RESTRICT + PATCH 全审计）

| 列 | 类型 | 约束 |
|---|---|---|
| `execution_id` | UUID PK | default uuid4 |
| `report_id` | UUID FK→capa_d3_impact_report.report_id | **ON DELETE RESTRICT, NOT NULL**（v4 改 RESTRICT，不可变 report 不删，finding 2；删 capa 前须显式清理 execution） |
| `generation_id` | UUID FK→capa_d3_advice_generation.generation_id | ON DELETE CASCADE, nullable（绑当前 advice generation，finding 1；manual 时可 null） |
| `factory_id` | UUID FK→factories.id | ON DELETE RESTRICT, NOT NULL |
| `advice_id` | UUID FK→capa_d3_ai_advice.advice_id | **ON DELETE SET NULL**, nullable（manual 时 null） |
| `source` | String(8) | CHECK IN ('manual','adopted'), NOT NULL |
| `measure_text` | Text | NOT NULL |
| `result_status` | String(16) | CHECK IN ('completed','in_progress','pending','failed'), NOT NULL, default 'in_progress' |
| `evidence_refs` | JSONB | default `[]` — schema + scheme 白名单（finding 次要2，见下） |

## 4. 服务层（`capa_d3_containment_service.py`）

### 4.1 导入 + run（两阶段事务，finding 1）

```python
async def import_containment_data(db, capa_id, user, request) -> dict
```
**事务 A**（锁 capa → run/快照 → 提交）：
- 锁 capa 行 FOR UPDATE（防双击产生两代 run）。
- 新建 `capa_d3_import_run`（is_current=true，旧 run is_current=false，partial UQ 保证唯一）。
- 按 `request.snapshot_types`（默认全 4 类）调子源查询 → 每类落 snapshot（run 内 UQ）。
- run `status='completed'`。
- 写 `D3_DATA_IMPORTED` 审计。
- **提交事务 A**。

**事务 B**（自动报告生成，独立事务）：
- 调 `generate_impact_report(db, run_id, user)`。
- **重检 run.is_current**（finding 5）：获锁后若 run 已被另一 import 置非 current → 返回 `report_status='superseded'`，不调 LLM，前端刷新当前 run。
- 成功 → `report_status='done'`；失败 → `report_status='failed'`；无凭证 → `report_status='blocked'`；被取代 → `report_status='superseded'`。
- 事务 B 失败/异常**不回滚事务 A**（run/快照已提交）。

**返回**（始终 200）：
```json
{"run_id": ..., "snapshots": [{snapshot_type, record_count}], "report_status": "done"|"failed"|"blocked"|"superseded", "report": {...}|null, "report_error": "..."|null}
```

子源查询（私有，product_line_code + factory_id 隔离）：
- `_query_inventory` → ERPInventoryBalance（payload 每条带 `record_key` + `source_id: balance_id`）
- `_query_shipment` → ERPShipment LEFT JOIN ShipmentRecord LEFT JOIN customers（**arrival_status 从 `ERPShipment.erp_raw_data["arrival_status"]` 读**，枚举 `in_transit`/`signed`/`unknown`，缺失/非法→`unknown`，不靠日期/地址推导，finding 4；payload 每条带 `record_key` + `source_id: erp_shipment_id`）
- `_query_iqc` → IqcInspection JOIN suppliers（按 supplier_id/part_no + 近 N 天；payload 每条带 `record_key` + `source_id: inspection_id`）
- `_query_spc` → SPCAlarm JOIN InspectionCharacteristic（复用 SPCAnomalySource 30 天口径；payload 每条带 `record_key` + `source_id: alarm_id`）

### 4.2 报告生成（事实确定性 + LLM 风险 + 精简 prompt + risk floor）

```python
async def generate_impact_report(db, run_id, user) -> dict
```
- 锁 capa 行 FOR UPDATE（防并发报告重试双 current）。
- **重检 run.is_current**（finding 5）：若 run.is_current=false → 返回 `superseded`，不调 LLM。
- 读当前 run 的 4 类快照。
- **确定性计算 4 项事实**：
  - `_compute_batches(snapshots)` — 按物料/批次 join 聚合；每 batch 带 `batch_key`（=`{snapshot_type}:{source_id}`，finding 3）
  - `_compute_impact_qty(batches)` — 按状态聚合 + **校验 = 明细求和**
  - `_compute_customer_impact(shipment_snapshot)` — join customers，真名
  - `_compute_time_window(spc_snapshot)` — alarm 最早~最晚
  - `_compute_risk_floor(customer_impact, capa.severity)` — 若存在 arrival_status='unknown' 的受影响客户 → `'high'`；否则 severity 映射（finding 4）
- **精简 prompt**（finding 5）：prompt 只含：确定性报告事实 + 每类来源统计摘要（record_count + 高风险项 top N）+ 截断标记 + 原始总数。**不含全量快照**。遵守 MAX_PROMPT_CHARS=8000 截断（截断标 `truncated=true` + `original_total`）。
- 客户名脱敏：prompt 里 `customer_01` 代号。
- 调 `provider_adapter.complete_json` + safety_trailer（injection 防护）。
- LLM 返回 `{risk_level, risk_explanation}` → schema 校验 → 失败重试 1 次 → 仍失败 `status='failed'`。
- **后端 risk floor**（finding 4）：`final_risk = max(llm_risk, risk_floor)`（high>medium>low），存 `risk_level` + `risk_floor` 列。
- 落库前还原客户名（代号→真名）。
- 落 `capa_d3_impact_report`（新 generation，旧 report is_current=false，partial UQ 保证唯一）。
- `prompt_stats={fact_chars, truncated, original_total}` 容量观测。
- 写 `D3_REPORT_GENERATED` 审计（成功/失败都写）。
- 无 LLM 凭证 → BLOCKED（返回 blocked 状态给 import 端点；独立 /d3/report 端点才 422）。

### 4.3 建议生成（advice_generation + provenance 按 advice_type 映射）

```python
async def generate_advice(db, capa_id, report_id, user, request) -> dict
```
- 锁 capa 行 FOR UPDATE。
- 读当前 report。
- **新建 advice_generation**（finding 1）：旧 generation is_current=false，新 generation is_current=true（partial UQ 保证）。
- LLM prompt 含确定性报告事实（已脱敏）+ safety_trailer。
- LLM 返回建议列表（advice_type + advice_text + target_batch_refs + provenance_sources_hint）。
- **后端标注 provenance**（finding 3/6，按 advice_type 映射，用 record_key）：
  - `recall`/`notify_customer` → 反查 shipment snapshot 命中批次的 `{snapshot_id, record_key, source_type:'shipment', stage:'llm_advice'}`
  - `isolate` → 反查 inventory snapshot `{snapshot_id, record_key, source_type:'inventory', ...}`
  - `strict_inspection` → 反查 iqc snapshot `{snapshot_id, record_key, source_type:'iqc', ...}`
  - `alternative` → report-level `{snapshot_id:null, record_key:'report:{report_id}:summary', source_type:'report', ...}`
  - **规则**：每条建议 provenance 数组非空且每元素 `record_key` 非空字符串；映射后为空 → 拒绝该建议（不落库）+ 记 stage_runs error
- 后端校验：`target_batch_refs`（非 null 时）须存在于 report.batches 的 batch_key；`advice_text` 客户名还原真名。
- 落 `capa_d3_ai_advice` 多行（绑当前 generation_id）。
- 失败仍落 generation 行 `status='failed'`（无 advice 行），写审计 `D3_AI_ADVICE_GENERATED`。
- 无凭证 → BLOCKED → 422。

### 4.4 采纳/拒绝（单一当前决策 + 文本修订 + generation 校验）

```python
async def adopt_advice(db, capa_id, advice_id, decision, adopted_text, user) -> dict
```

- 查 adoption where advice_id：
  - 不存在 → INSERT（带 report_id + generation_id 归属）。

- 写 `D3_ADVICE_ADOPTED`/`D3_ADVICE_REJECTED` 审计（新增/首次决策时）。

## 14. 关键约束

- `factory_id` NOT NULL 全表（**7 表**）+ 复合 FK 保证父子一致（finding 6）
- `enqueue_embedding` 不适用（D3 非 RAG 实体）
- 交付顺序：01.1 完成后才进 01.7

- 状态机：D3_INTERIM→D4_ROOT_CAUSE 线性边已在
- D3 阶段守卫：写端点 `capa.status == D3_INTERIM`
- 不可变 generation 覆盖 run→report→advice_generation→advice + partial UQ is_current（finding 1）
- 审计实体保留 policy：adoption advice_id SET NULL 但 report_id 不可空保归属；execution report_id RESTRICT（不可变 report 不删）（finding 2）
- IQC 查 iqc_inspections
- 发布策略：A+B 原子发布（Slice A/B 仅实现顺序）
- 两阶段事务：A 提交 run/快照，B 生成报告，B 失败不回滚 A；B 获锁后重检 run.is_current，过期 superseded（finding 5）
- record_key 定义：每类快照带 record_key + source_id；batches[].batch_key = `{snapshot_type}:{source_id}`（finding 3）
- risk floor：`risk_level = max(llm_risk, deterministic_floor)`，unknown+受影响客户→high（finding 4）
- arrival_status 从 erp_raw_data 读，枚举校验，缺失→unknown（finding 4）
- provenance 按 advice_type 映射；alternative 用 report-level record_key 非空（finding 6）
- execution PATCH 全字段审计 + evidence_refs scheme 白名单（次1/次2）
