## 1. 背景与现状

D3（临时/遏制措施）当前仅 `capa_eightd.d3_interim` 文本字段 + `capa_draft_service` 的 AI 文本草稿（含 `containment_actions` 结构）。故事要求的"数据导入 → 受影响范围分析报告 → AI 遏制建议"链路完全缺失，D3→D4 无闸口（`advance_capa` 注释明确"D3→D4 无闸口"）。

**可复用基础设施**（gap analysis 已确认）：
- `ERPInventoryBalance`（material_code/location_code/lot_no/quantity/inventory_status/snapshot_at）
- `ERPShipment`（shipment_number/customer_code/material_code/lot_no/quantity/shipment_date）
- `ShipmentRecord`（customer_id/batch_no/quantity/destination）
- `SPCAlarm` + `InspectionCharacteristic`（`SPCAnomalySource` 已查 30 天判异）
- `iqc_materials` + `IQCSource`
- `CapaAIAdoption`（参考，不复用——见 §3.4）
- `recommendation_orchestrator` 的 `StageRun` + `RecommendationResult(blocked=True)` 模式（01.2 已落地）
- `capa_draft_service` 的 DB-backed timeout + `_generate_and_validate` 重试口径
- `provider_adapter.complete_json`（01.2/01.3 已迁移的 LLM 层）
- 迁移测试基础设施 `backend/tests/migrations/`（01.2/A3 已建 `mig_db_url` fixture + `_cfg` helper）

## 2. 架构总览

D3 遏制链路是独立于 12 阶段 DAG 的 3 阶段流，挂在 `capa_eightd` 下：

```
import(4 源: 库内查询 → JSONB 快照)  →  analyze(LLM: 快照 → 报告 5 项)  →  llm_advice(LLM: 报告 → 建议+provenance)
                                          ↑ stage_runs 持久化                ↑ adoption(adopted/rejected)
                                                                                       → D3→D4 闸口
```

- **import**：4 子源（inventory/shipment/iqc/spc），各自 `should_skip` → 查询库内表 → 拼 JSONB 快照落 `capa_d3_containment_snapshot`。确定性、不依赖 LLM。
- **analyze**：LLM 消费 4 快照 → 结构化报告 5 项（批追溯/影响数量/客户影响/风险分级/时间窗口）。落 `capa_d3_impact_report`（单份覆盖）。
- **llm_advice**：LLM 消费报告 → 建议列表（每条带 advice_type + source_provenance）。落 `capa_d3_ai_advice` 多行。
- **adoption**：工程师采纳/拒绝，落 `capa_d3_advice_adoption`（adopted/rejected 都留痕）。
- **D3→D4 闸口**：`advance_capa` 新增 per-edge 分支。

每阶段产 `StageRun{name, status, hit_count, summary, error?}`，`status∈{pending,running,done,skipped,error}`。无 LLM 凭证时 analyze/llm_advice 阶段 BLOCKED（沿用 01.2 orchestrator 顶部 `pc is None → RecommendationResult(blocked=True)` 模式，endpoint 返回 422 + `detail.blocked`）。

新增服务文件 `backend/app/services/capa_d3_containment_service.py`（一个文件，内部按阶段分函数）。复用 `StageRun`/`RecommendationResult` 数据结构，**不复用 12 阶段 DAG 本身**（D3 是"先止损"非"找根因"，语义独立）。

## 3. 数据模型（4 张新表，一个 Alembic 迁移）

### 3.1 `capa_d3_containment_snapshot` — 导入快照（Slice A）

| 列 | 类型 | 约束 |
|---|---|---|
| `snapshot_id` | UUID PK | default uuid4 |
| `capa_id` | UUID FK→capa_eightd.report_id | ON DELETE CASCADE, NOT NULL |
| `factory_id` | UUID FK→factories.id | ON DELETE RESTRICT, NOT NULL |
| `snapshot_type` | String(20) | CHECK IN ('inventory','shipment','iqc','spc'), NOT NULL |
| `payload` | JSONB | NOT NULL — 原始记录副本 |
| `source_query` | JSONB | 生成快照的查询参数（产品线/时间窗/物料等） |
| `record_count` | Integer | NOT NULL, default 0 |
| `imported_by` | UUID FK→users.user_id | NOT NULL |
| `imported_at` | DateTime(tz) | server_default now() |
| `created_at` | DateTime(tz) | server_default now() |

索引：`(capa_id, snapshot_type)`、`factory_id`（RBAC 过滤）。

`payload` 按 type 各自结构：
- `inventory`：`[{material_code, location_code, lot_no, quantity, unit, inventory_status, snapshot_at}]`
- `shipment`：`[{shipment_number, customer_code, material_code, lot_no, quantity, shipment_date, arrival_status}]`
- `iqc`：`[{material_code, supplier_id, batch_no, defect_desc, inspect_date, result}]`
- `spc`：`[{alarm_id, ic_id, characteristic, triggered_at, rule_violated}]`

### 3.2 `capa_d3_impact_report` — 受影响范围报告（Slice B，LLM 生成）

| 列 | 类型 | 约束 |
|---|---|---|
| `report_id` | UUID PK | default uuid4 |
| `capa_id` | UUID FK→capa_eightd.report_id | ON DELETE CASCADE, NOT NULL, **UNIQUE** |
| `factory_id` | UUID FK→factories.id | ON DELETE RESTRICT, NOT NULL |
| `batches` | JSONB | 批追溯清单 |
| `impact_qty` | JSONB | `{in_transit, inventory, shipped}` |
| `customer_impact` | JSONB | `[{customer_name, qty, arrival_status}]` |
| `risk_level` | String(8) | CHECK IN ('high','medium','low'), nullable（failed 时 null） |
| `time_window` | JSONB | `{start, end}` ISO date |
| `status` | String(10) | CHECK IN ('done','failed'), NOT NULL, default 'failed' |
| `stage_runs` | JSONB | analyze 阶段执行记录 |
| `error` | Text | nullable（failed 时存错误） |
| `llm_available` | Boolean | NOT NULL, default false |
| `model` | String(40) | nullable |
| `generated_by` | UUID FK→users.user_id | NOT NULL |
| `generated_at` | DateTime(tz) | server_default now() |
| `created_at` | DateTime(tz) | server_default now() |

UQ(capa_id) — 单份覆盖（每次生成覆盖旧行）。`status='done'` 才被闸口认可；`status='failed'` 时 `risk_level` 等为 null，UI 显示重试。

### 3.3 `capa_d3_ai_advice` — AI 遏制建议（Slice B）

| 列 | 类型 | 约束 |
|---|---|---|
| `advice_id` | UUID PK | default uuid4 |
| `capa_id` | UUID FK→capa_eightd.report_id | ON DELETE CASCADE, NOT NULL |
| `factory_id` | UUID FK→factories.id | ON DELETE RESTRICT, NOT NULL |
| `report_id` | UUID FK→capa_d3_impact_report.report_id | ON DELETE CASCADE, NOT NULL |
| `advice_type` | String(24) | CHECK IN ('recall','isolate','notify_customer','strict_inspection','alternative'), NOT NULL |
| `advice_text` | Text | NOT NULL |
| `source_provenance` | JSONB | NOT NULL — `[{source, stage, detail?}]` |
| `target_batch_refs` | JSONB | nullable — 建议针对的批次引用 |
| `stage_runs` | JSONB | llm_advice 阶段执行记录 |
| `llm_available` | Boolean | NOT NULL, default false |
| `model` | String(40) | nullable |
| `generated_by` | UUID FK→users.user_id | NOT NULL |
| `generated_at` | DateTime(tz) | server_default now() |
| `created_at` | DateTime(tz) | server_default now() |

索引：`(capa_id)`、`factory_id`。建议是集合，不 UQ（一次生成多条）。建议生成失败不落行（集合无单例 artifact，重试即重调），仅写审计。

### 3.4 `capa_d3_advice_adoption` — 采纳/拒绝留痕

| 列 | 类型 | 约束 |
|---|---|---|
| `adoption_id` | UUID PK | default uuid4 |
| `capa_id` | UUID FK→capa_eightd.report_id | ON DELETE CASCADE, NOT NULL |
| `factory_id` | UUID FK→factories.id | ON DELETE RESTRICT, NOT NULL |
| `advice_id` | UUID FK→capa_d3_ai_advice.advice_id | ON DELETE CASCADE, NOT NULL |
| `decision` | String(8) | CHECK IN ('adopted','rejected'), NOT NULL |
| `adopted_text` | Text | nullable（rejected 时 null） |
| `advice_type` | String(24) | 冗余存（建议删了也能读） |
| `source_provenance` | JSONB | 冗余存 |
| `decided_by` | UUID FK→users.user_id | NOT NULL |
| `decided_at` | DateTime(tz) | server_default now() |
| `created_at` | DateTime(tz) | server_default now() |

UQ(advice_id, decision) — 同条建议同决策不重复。审计日志（`D3_ADVICE_ADOPTED`/`D3_ADVICE_REJECTED`）独立留痕，CASCADE 删建议时审计不丢。

## 4. 服务层（`capa_d3_containment_service.py`）

### 4.1 Slice A — 导入

```python
async def import_containment_data(db, capa_id, user, request) -> dict
```
- 按 `request.snapshot_types` 列表（默认全 4 类）触发子源查询。
- 每个子源查询 → 落 `capa_d3_containment_snapshot` 一行（payload 含全部记录，record_count 可为 0）。
- 空数据时 `record_count=0` 仍落行（明确"该源无数据"），不阻断导入。
- 写 `D3_DATA_IMPORTED` 审计（`changed_fields={snapshot_types, record_counts}`）。
- 返回快照摘要 `{snapshots: [{snapshot_type, record_count}]}`。

子源查询函数（私有，均按 `product_line_code` + `factory_id` 隔离）：
- `_query_inventory(db, capa, params)` → ERPInventoryBalance（可选 material_code/lot_no 过滤）
- `_query_shipment(db, capa, params)` → ERPShipment LEFT JOIN ShipmentRecord（时间窗）
- `_query_iqc(db, capa, params)` → iqc_materials（supplier_id/物料 + 近 N 天不良）
- `_query_spc(db, capa, params)` → SPCAlarm JOIN InspectionCharacteristic（复用 SPCAnomalySource 30 天判异口径）

### 4.2 Slice B — 报告生成

```python
async def generate_impact_report(db, capa_id, user, request) -> dict
```
- 读该 capa 全部快照 → 拼 LLM prompt → 调 `provider_adapter.complete_json`（DB-backed timeout，复用 `capa_draft_service` 口径）。
- JSON schema 校验 5 项 → 校验失败重试 1 次（复用 `_generate_and_validate` 口径）→ 仍失败 `FAILED`。
- 落 `capa_d3_impact_report`（覆盖旧行）：成功 `status='done'`，失败 `status='failed'` + `error` + `risk_level=null`。
- 写 `D3_REPORT_GENERATED` 审计（成功/失败都写，`changed_fields={status, model, llm_available}`）。
- 无 LLM 凭证 → `RecommendationResult(blocked=True)` → API 返回 422 `detail.blocked`。

### 4.3 Slice B — 建议生成

```python
async def generate_advice(db, capa_id, user, request) -> dict
```
- 读报告 → LLM → 建议列表（每条带 advice_type + provenance_sources）。
- 后端把 `provenance_sources` 展开成 `source_provenance=[{source, stage:'llm_advice'}]` 落 `capa_d3_ai_advice` 多行。
- 建议生成失败不落行，仅写审计 `D3_AI_ADVICE_GENERATED`（`changed_fields={status:'failed', error}`）。
- 无 LLM 凭证 → BLOCKED → 422。

### 4.4 Slice B — 采纳/拒绝

```python
async def adopt_advice(db, capa_id, advice_id, decision, adopted_text, user) -> dict
```
- 落 `capa_d3_advice_adoption`。UQ(advice_id, decision) 冲突 → 409。
- 冗余存 `advice_type` + `source_provenance`（从 `capa_d3_ai_advice` 读）。
- 写 `D3_ADVICE_ADOPTED` / `D3_ADVICE_REJECTED` 审计。

## 5. D3→D4 闸口（`advance_capa` 新增分支）

`capa_service.advance_capa` 的 per-edge 分发新增：

```python
elif current == EightDState.D3_INTERIM and target == EightDState.D4_ROOT_CAUSE:
    await _d3_to_d4_gate(db, capa)
```

`_d3_to_d4_gate`（fail-closed）：

```python
# 1. 快照≥1（任一 type）
snap_count = count(capa_d3_containment_snapshot where capa_id, factory_id)
if snap_count == 0: raise ValueError("D3→D4 需先导入遏制数据")

# 2. 报告已生成且 status='done'（仅 Slice B 加严；Slice A 闸口不查报告）
#    Slice A 落闸口时跳过此检查；Slice B 落报告 status 列后启用。
if report_done_exists(...):  # status='done'
    pass
else:
    raise ValueError("D3→D4 需先生成受影响范围报告")

# 3. (d3_interim 非空) OR (adoption adopted 记录≥1)
interim = (capa.d3_interim or "").strip()
adopted = count(capa_d3_advice_adoption where capa_id, decision='adopted')
if not interim and adopted == 0:
    raise ValueError("D3→D4 需填写遏制措施或采纳 AI 建议")
```

**切片衔接**：
- **Slice A 闸口**：只检查 1 + 3（快照≥1 AND (interim OR adoption)）。不查报告表（Slice A 报告表未建）。
- **Slice B 闸口**：加严为 1 + 2 + 3（+ 报告 done）。

两切片闸口都 fail-closed。

**重要推论**：报告是 LLM 生成（AI_REQUIRED），Slice B 闸口要求报告 done 意味着即便工程师想全手填人工措施，也必须先导入数据 + 跑通 LLM 报告才能推进。这与故事 BLOCKED 口径一致。

## 6. LLM 结构化输出契约（JSON schema，强校验）

### 6.1 报告 schema（analyze 阶段）

```json
{
  "batches": [
    {"batch_no": str, "type": "in_transit"|"inventory"|"shipped",
     "location": str|null, "qty": number, "customer": str|null}
  ],
  "impact_qty": {"in_transit": int, "inventory": int, "shipped": int},
  "customer_impact": [
    {"customer_name": str, "qty": int, "arrival_status": "in_transit"|"signed"|"unknown"}
  ],
  "risk_level": "high"|"medium"|"low",
  "time_window": {"start": "ISO date", "end": "ISO date"}
}
```

校验失败 → 重试 1 次 → 仍失败 `status='failed'`。`risk_level` 推导维度（prompt 指引 LLM）：到货状态 + capa.severity + Customer.segment（seed 为 key/strategic/normal）。

### 6.2 建议 schema（llm_advice 阶段）

```json
[
  {"advice_type": "recall"|"isolate"|"notify_customer"|"strict_inspection"|"alternative",
   "advice_text": str, "target_batch_refs": [str],
   "provenance_sources": ["inventory"|"shipment"|"iqc"|"spc"]}
]
```

后端展开 `provenance_sources` → `source_provenance=[{source, stage:'llm_advice'}]`。

### 6.3 provenance 标注规则

- 每条建议的 `source_provenance` = LLM 声称命中的数据源 × `{stage: 'llm_advice'}`。
- 报告的 `batches[].type` 反映 import 阶段命中的源。
- E2E 断言：每条建议 `source_provenance` 非空数组、元素含 `source`+`stage` 字段；不断言具体源名（LLM 可能只命中部分源）。

## 8. 审计事件（`AuditLog.action`，`table_name='capa_eightd'`）

| 事件 | 触发 | `changed_fields` |
|---|---|---|
| `D3_DATA_IMPORTED` | import 端点 | `{snapshot_types, record_counts}` |
| `D3_REPORT_GENERATED` | report 端点（成功/失败都写） | `{status: done/failed, model, llm_available}` |
| `D3_AI_ADVICE_GENERATED` | advice 端点（成功/失败都写） | `{advice_count, model, llm_available, status}` |
| `D3_ADVICE_ADOPTED` | decision=adopted | `{advice_id, advice_type, source_provenance, adopted_text}` |
| `D3_ADVICE_REJECTED` | decision=rejected | `{advice_id, advice_type, source_provenance}` |

沿用 `AuditLog` + `correlation_id`（`uuid.uuid5(NAMESPACE_URL, ...)`）口径。所有审计 `factory_id` 填 capa.factory_id。
