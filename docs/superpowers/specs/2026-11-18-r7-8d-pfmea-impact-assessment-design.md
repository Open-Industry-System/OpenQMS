## 2. 正式产物与目标绑定

- **D4 准入**。当前正式根因修订须有与其绑定的有效验证和来源证明，并能解析全部继承来源。候选确认到正文与现场验证通过是不同事实。非空正文、旧采纳记录或单个主来源 proof 均不能代替完整来源。
- **D5 准入**。至少一条员工正式采纳、当前仍有效且适用于该根因的措施。纳入全部适用的当前正式措施，采用最近一次正式更正文本，保留采纳与更正历史引用。CAPA 判定适用性，根因被更正时不得自行把旧措施重绑到新依据。待审、撤回、替代候选、手工自由文本和无可信绑定的旧记录均不能代替正式采纳。D6 的实施与验证单独呈现，采纳本身不证明措施已实施或有效。
- **阶段**。建议从 D5 正式采纳后按材料就绪准入，允许仍具有效材料的后续可读阶段，含结案或归档。重新打开报告不恢复已过期依据。无已确认并验证根因、无适用采纳措施或来源不可核实，分别提示「请先确认并验证 D4 根因」「请先采纳适用于当前根因的 D5 措施」「请补齐可核实的正式来源」。缺权限优先通用提示「当前不可评估」，不提示具体条目或数量。上述情况不调用模型。
- **服务端绑定**。固定租户及代际、报告 ID、工厂、适用产品线、根因修订和验证/证明引用、当前措施 ID 和版本集合、完整继承来源及版本、PFMEA ID 和版本。报告与目标须同租户、同工厂且产品线适用，由各模块依据正式范围校验。当前关联可预选，本次显式目标不改报告关联。首片建议只选当前已批准 PFMEA 快照，绑定版本 ID、显示版本号、快照哈希及 FMEA 验证的对象代际。源与目标须能区分原地变更、删除重绑和 A→B→A。优先复用能覆盖这些路径的单调代际，发现现有 `lock_version` 未覆盖的写路径时由 FMEA 补齐或暂不开放对应对象。历史缺可靠代际不补造绑定。

**批准基线选择**。在当前目标文档和工厂内，选择可唯一识别、哈希可验证且主版本最高的正式批准快照。沿用现有批准来源识别条件 `change_type=approve`、`major_no >= 1`、`minor_no=0`。送审也会产生快照，不能按所有版本的最高版本号或仅按次版本为零选取。无合格快照、最高批准版本不唯一或无法验证时不准入。

建议同一文档有已批准 `v3.0` 和在编或送审 `v3.1` 时，继续允许锁定并评估 `v3.0`。界面显示「批准基线 v3.0」并标明存在未批准修订，直接请求 `v3.1` 也拒绝。读取只用 `v3.0` 的快照。仅形成后续草稿或送审版本，不视为批准基线变化。目标校验区分批准基线及对象范围/身份代际与草稿编辑计数。若在编变更还影响独立绑定的 8D 来源、对象范围或访问权，仍按 §7 复核。 [状态转换](../../../backend/app/services/fmea_service.py) · [版本生成与批准来源筛选](../../../backend/app/services/version_service.py)

| 平台 · 报告侧栏读取 | 报告和结果引用，或分页 | 可读建议、基于授权计算的时效和来源入口 | 当期查询者满足 §4 | 保存原版本，另比对当前有效版本 | 不可读与不存在同响应，过期见 §7。仅读及既有访问审计 |

FMEA 按正式 PostgreSQL 图快照解析 PFMEA 的工序、功能与失效链，保留边的方向和控制措施的真实归属。一页、轮数、跳数、累计节点数和字节数均由服务端设硬上限，游标绑定 run、快照与筛选条件。实施时冻结并验证预算。插件可先搜索，再查节点邻域，最后补查现有控制。查不到或查不完的边界进入建议。首片不依赖异步图投影、向量索引、全图导出或跨文档搜索，CAPA 和 FMEA 分别从自己的正式业务服务取数。

**两种查询回执**。术语、节点类型等筛选的最后一页仅证明该筛选已翻完。业务范围覆盖由 FMEA 定义和核验。首片支持固定批准快照中的完整工序失效链，包含全部相关失效模式、原因、预防和探测控制及其关系。排除整个文档时，另须有正式适用范围及完整工序目录。FMEA 依据 CAPA 已授权的工序或适用范围线索与 PFMEA 正式标识，确定每条措施为得出否定结论所需的范围。插件的关键词结果、单个候选节点或自行缩小的范围不能替代该判定。范围无法可靠界定时，不能得出「未发现影响」。

覆盖回执由服务端在完整范围的有界分页全部合法交付后签发，绑定当前任务、run、epoch、目标快照和代际、范围及覆盖的节点和关系类型。缺页、截断、断链或无法交付完整范围时不签发完整覆盖回执，后台也不读取不可交付的正文来补证。预算不足报「证据不足」，权限不足按 §4 拒绝。

**存储选择**采用平台不可变任务结果，报告侧栏按报告读取授权后的结果引用，目标 PFMEA 作为快照与证据引用。CAPA 正式字段和 FMEA 草稿分别具有自己的业务生命周期，把建议放入其中会混淆正式材料和风险库。临时插件文本又无法支撑同事复审和历史追踪。平台结果可复用任务记录、回执、来源限制和审计，重新评估创建新结果并关联前版。活动和日志只存引用与运行状态，正文仅由受控结果路径物化。首片可见范围限报告侧栏和该结果的受控直达链接。

## 4. 权限与副作用

平台先预授权并固定员工、安装、任务、报告、目标、能力和接收方。插件只在获准范围内自己安排调用顺序。业务模块独立复核当期权限。所有工具读取前先查范围、完整来源与身份，向插件、模型、员工各自交付前再次复核。

| 动作 | 执行身份与复核 | 副作用 |
|---|---|---|
| 员工发起 | 员工须有 CAPA VIEW、FMEA VIEW、两端适用的租户/工厂/产品线权限和完整来源读取权，并符合显式 R7 准入。排队与启动均复查 | 创建绑定任务、状态与引用审计 |
| 运行取数和入模 | 短期凭据代表原发起人，交集包含当前业务权限、安装授权、任务授权、固定范围与接收方许可。重新检查租约/代际、累计来源及版本 | 最小投影、释放回执、审计。仅正式业务读 |
| 生成后提交/重试 | 在最终事务内锁定并重验任务/run/epoch、两端版本与当前授权。服务端汇总该 run 已释放回执及模块继承来源，插件不能省略依赖 | 不可变结果、版本、回执关系和状态原子提交。只发布不含正文的受控指针 |
| 同事列出、打开、跟随来源 | 用审阅者自己的当前身份。须能读报告、目标及每项完整来源，满足派生敏感级别。已保存结果可在运行结束后查看。列表、活动重连、详情、证据跳转均受限 | 只读与既有访问审计。能看目标但缺一项 8D 来源时，整份隐藏，含标题、结论、节点、摘要、专属活动和计数。直接打开通用不可用，不返回部分建议 |
| 员工判断与正式修改 | 首片员工可查看并自行判断，系统不保存认可状态。正式修改须另行经过 FMEA 针对目标对象和具体业务操作授权 | 本片无节点、关系、控制、评分/AP、版本、状态、报告关联写入。无 D7/D8 门禁、控制计划、知识库、同步、传播或通知联动 |

建议继承派生来源的最严限制，解释正文至少按受限结果处理。先鉴权，再判断时效，避免靠过期提示探测无权对象。响应禁止缓存。权限、身份或任务切换时清除旧内容，迟到响应不能重新填回。已合法释放的字节无法追回，审计区分已释放、未保存和未显示。

沿用已批准的不可变模型部署绑定、数据分类、接收方与精确出口政策。默认关闭，遵循既有 dev/Darwin 受控试点边界。LOCAL 也须允许接收全部来源。云端仅在目标环境对实际部署和全部跨模块输入均已有外发批准时可用，合成试用或协议批准不能代替本次数据许可。获准 Responses 沿用 `store=false` 与受控回放。首片推荐受控本地接收方，失败不回退到其他云端、普通进程或旧出口。 [模型出口](../../development/r5-model-egress.md) · [权限参考](../../permissions.md)

## 5. 端到端正常流程

1. 员工在 8D 侧栏点「评估对 PFMEA 的影响」。后端校验报告材料及完整来源，显示匹配范围内可读的已批准 PFMEA。员工确认一份目标和版本。授权通过后创建带版本绑定的待运行任务，平台启动登记的 FMEA Agent。
2. Agent 先读取 CAPA 正式产物，确定现象、工序线索、已验证根因及适用措施。再在目标快照查候选工序和失效模式。需要分辨相近工序时再查具体原因和控制。平台逐次检查并记录释放回执，任何一侧越界即停止该次运行。
3. Agent 提交有证据引用的结构化建议。服务端按 §6 校验每条措施均有结论、否定结论具备对应的业务范围覆盖与排除依据，并复核引用版本、完整来源及当前权限。通过后在同一事务保存结果和终态。侧栏刷新后只展示当前审阅者可读的报告版本及目标版本，员工可沿证据回看原始记录。PFMEA 业务快照与发起前一致。

## 6. 建议的形态与制造现场示例

建议卡包含报告和目标版本、生成时间、结论、逐项影响、证据、判断理由及缺失信息。逐项区分正式事实、Agent 推断与待员工确认的调整。平台校验每条证据引用都来自获准回执且类型、同版本关系和路径匹配。可追溯性不能代替员工判断技术结论。覆盖范围及限制必须可见。

**完成条件**。CAPA 在准入时绑定的每个 `(measure_id, formal_revision)` 必须在结果中恰好出现一次，并有明确结论及对应的分析引用。多项措施可以共用分析，须逐项指明对应关系、结论及其依据。平台用绑定集合核验遗漏、重复、未知措施和旧修订，不能用完整来源集合代替逐项评估。缺证据的措施可显式提交「证据不足」并说明尚缺什么。卡片结论由平台根据通过校验的逐项结论计算，插件不能另行指定。

**否定结论的提交校验**。对每条「未发现影响」，平台须经 FMEA 验证同一 run 和快照下的覆盖回执足以覆盖该措施所需的业务范围，且排除依据引用已交付回执中的正式事实并适用于所述范围。平台核验范围、关联和引用完整性，技术判断留给员工。只有关键词翻完或证据无法排除影响时，拒绝该提交为完成结果。插件可补查，或在权限完整时改交「证据不足」并说明缺口。被拒绝的提交不保存结果、不发成功活动，也不标记任务完成。

**示例为合成数据。** 8D `8D-0268`，工厂 A 制动器线，D4 修订 3 的验证记录 `V-12` 用控制器参数履历及复现试验确认，OP40 辅助支架紧固时换型恢复了旧扭矩程序，导致部分螺栓低扭矩。CAPA 正式投影给出该验证与它的关联证据引用。D5 措施 `M-07@2` 已由员工正式采纳并更正，正文要求按工单锁定程序号，不一致时禁止启动，并保存控制器事件记录。建议同时链接初次采纳和更正。该输入未证明 D6 已验证措施有效。

员工选定 `PFMEA-BRK-004 v3.0`。第一次查询找到 OP40「辅助支架紧固」和失效模式 `FM-18`「紧固扭矩不足」。第二次按已签发句柄确认原因 `FC-09`「紧固程序选择错误」，以及已有预防控制 `PC-04`「换型双人确认」和探测控制 `DC-02`「末件抽测」。正式快照的边将这条原因及控制归到同一条失效链。

- **有明确影响**。针对 `FC-09` 的预防控制提出评审建议，将工单程序号校验和不一致启动互锁纳入候选控制，并保留现有控制，待工程确认。证据是 D4 修订 3 与 `V-12`、`M-07@2`、v3.0 的 OP40→FM-18→FC-09 路径及控制引用。Agent 的判断是同一工序、失效机制与措施对象相符，互锁可能降低程序误选风险。还缺互锁验证、错误程序故障注入结果和覆盖各换型的证据。无依据直接建议降低 O/D 或 AP。正式图中的控制和评分保持现值。
- **未发现影响**。例如另一次评估选了同线的压装 PFMEA v3.0。FMEA 的范围回执证明完整工序目录与正式适用范围均已交付，正式范围明确只涉及无软件选方的独立压装，排除本条紧固措施所对应的工序。列出覆盖回执、正式排除依据和限定语「在所选 v3.0 的已核范围内」。
- **证据不足**。例如两个相似工序缺可区分的工位标识，或关系断开、达到预算未查完。展示已查范围和需补充的工位、程序或图关联信息。可以列出实际返回的待核候选，不签发已定位节点或具体节点调整。权限不足仍走拒绝交付，不能伪装成此结论。

全部措施通过完成校验后，卡片有至少一条「有明确影响」时显示该结论并标出其余未决项。否则只要一条「证据不足」，卡片即显示「证据不足」。全部措施均满足否定结论条件时，卡片才显示「未发现影响」。

## 7. 变更、重复与晚到结果

| 情况 | 正在生成 | 已有建议及后续操作 |
|---|---|---|
| 撤发起人权限、租户/工厂/产线范围、安装或接收方许可 | 下一个调用或最终释放围栏拒绝。已发送的模型请求尽力取消，回包丢弃，禁止成功结果和正文活动。只留脱敏状态与审计 | 已保存结果按每位审阅者自己的当前读取权判断。撤审阅者任一来源或对象权限后，隐藏整份；保留原始记录。恢复读取权也须复核版本与历史来源 |
| D4/D5 正式更正、补入或撤销适用措施 | 版本/完整集合不匹配即终止，不混用新旧输入 | 权限完整且历史版本可验证时，显示「已过期」和生成时材料。当前材料重新就绪后可发起新评估 |
| PFMEA 新版本批准、相关代际变化、批准基线或已绑定来源中的节点删除/重绑 | 版本冲突即停止，旧句柄无效 | 权限完整且旧快照可校验时，显示「已过期」，证据链接只指向旧快照，缺历史节点入口可显示「旧节点当前不可定位」。不得按现 ID 或标签自动重绑。整份来源无法解析或授权时不交付正文 |
| 重复发起或提交 | 同一员工在同一租户以同一请求键、同一规范输入重试，当前授权下复用原任务；同键改目标或绑定冲突。结果提交按 run 和结果操作键去重 | 重放须再授权，旧任务变动只返回获准状态及重评入口。显式重评使用新键、重取两端版本并关联前版。复用历史结果不修改原版本 |
| 暂停/取消、超时、重启或完成后的晚到包 | 下一次放行与提交核对当前 run、租约和 epoch。首片若重启则按当前权限与版本从头取数，新 run 不复用旧回执。旧进程没有状态回写或公布权 | 终态不被覆盖。结果、回执关联和发布指针同事务建立，失败或 fencing 冲突全部回滚，保留最小拒绝或迟到审计 |

旧建议只在当前权限覆盖**完整历史来源**、历史版本可认证时供历史审阅，不能借缓存绕过限制。版本已变与权限不完整并存时先按权限拒绝。故障恢复、重复提交和权限写入竞争须覆盖事务边界，等锁之后再验，避免最后校验后到提交间的撤权窗口。

## 8. 第二个插件的复用与最小平台改动

**直接复用**任务/运行/租约、安装/长期授权、租户代际、能力目录的声明原则、员工侧栏外壳、引用活动和受控读取模式、模型交付围栏、不可变部署绑定、幂等及审计机制。通过现有 SDK/运行协议的版本扩展承载新契约，继续兼容旧任务。FMEA Agent 自管推理循环，不能导入 CAPA 私有模型、查询数据库、接触 D5 写工具或使用跨模块通用搜索。

**模块承担** CAPA 正式产物、来源继承、修订与适用性、当前/历史授权判断。FMEA 目标适用范围、快照及稳定代际、图投影/关系、授权、查询边界与业务范围覆盖回执。两者注册各自能力、投影分类、版本与来源解析规则，经平台协调；平台不解释业务表结构或节点语义。FMEA Agent 的提示词、调查路径和输出结构适配由插件负责。

| 确需修改的平台契约 | 现有契约为何不足及最小改动 |
|---|---|
| 双对象任务绑定及准入 | 现有任务/侧栏入口以 CAPA 报告为锚，不能把一个目标 PFMEA 当作运行对象锁定。保留报告锚，给新任务类型增加经校验的目标快照绑定和版本化 profile。明确两对象能力、接收方许可与恢复边界。 [任务创建](../../../backend/app/services/agent_runtime/task_service.py) · [准入](../../../backend/app/services/agent_runtime/deployment_profiles.py) |
| 跨模块来源回执、结果契约与读取 | `readonly_delivery` 的结果来源识别目前约束为 CAPA masked 投影和同一报告，且接受插件提交的回执引用。R5 完整依据面向 D5 写命令，不能直接代表 PFMEA 目标与完整继承来源。为新结果类型绑定服务端累积的双模块来源和版本，引用由模块校验，结果通过逐措施完成条件及业务范围覆盖校验后方可公布，读取时调用两模块当前/历史授权。继续使用平台结果/回执关联和活动指针语义，避免建立第二套任务库。 [只读交付](../../../backend/app/services/agent_runtime/readonly_delivery.py) · [任务读取](../../../backend/app/services/agent_runtime/task_reads.py) |
| 受控运行的工具面与提交围栏 | 主线 `model_workflow` 固定 D5 工具及保存命令。新 profile 注册相应读取、结果工具及预算，复用现有出口和身份锁。两模块在释放、提交与阅读的最后边界提供可串行核验的版本/权限依据。旧 profile 不扩权，也不引入平台内固定调查顺序。 [模型工作流](../../../backend/app/services/agent_runtime/model_workflow.py) |

## 9. 实施依赖、放行与产品复审

本地实施可基于计划中冻结的 R6 集成候选并行开展。合入主线前确认实际集成版本的 R6 正式 D4 继承来源与代际、D5 当前正式版本及更正链、完整读保护，并对受集成差异影响的路径补齐验收证据。按路线图，正常用户入口放行还需 R6 台账给出当前候选 C9、同份数据 C10、Task 11 签收和实际切换/兼容结论，核对与当前主线的迁移和权限组合。R7 自身须再验收精确部署、全链授权、源/目标代际、独立进程和无业务副作用。旧试点收据不能签发 R7 准入。缺任一条件时保持 R7 默认关闭，受控隔离验证只用批准的测试接收方与数据。

以下三项产品取舍已确认，作为实施计划基线。

1. **可评估的目标版本**。只评估最近一次正式批准的 PFMEA 快照。存在后续在编或送审版本时继续允许评估该批准基线，并按 §2 明示版本。
2. **历史建议与协作范围**。完整授权的同报告读者可查看，过期版本在仍有全部历史来源读取权时保留为历史。比只给发起者更适合同事接手，比共享到 PFMEA 页更容易保持 8D 来源权限。
3. **结案或归档后能否发起**。仍可读且材料齐备时允许，便于质量复盘。入口可独立限制，同样严格复核正式版本和权限。
