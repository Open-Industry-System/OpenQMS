### 1.1 旧 API 调用方与审计边界

按仓库生产源码及测试中的精确路径、函数引用核对：

- D4/D5 推荐的生产前端调用方分别为 `D4RecPanel` / `D5RecPanel`，经 `frontend/src/api/capa.ts` 包装；两面板只在对应 D4/D5 阶段挂载。旧采纳生产调用方是这两个面板，经同一包装；服务的生产调用方为 `capa.py:adopt_recommendation_ep`。旧 Agent 工具目录仅有 demo，未发现另一生产调用方。此结论限仓库，不能证明外部客户端、书签或脚本不存在。
- 草稿生产调用方为 `CAPADetailPage` → `useAIDraft` → `api/capaDraft.ts`。`GET /draft/capabilities` 提供步骤能力，`GET /capa/capabilities` 是全局 AI 配置可用性提示；配置可用不代表具体步骤仍被允许。
- 测试直接消费旧 API：`backend/tests/capa/test_capa_api_d4_d5.py`、`test_capa_verification_api.py`、`test_capa_recommend_api_stages.py`、`test_capa_reviewed_writes.py`；另有 `backend/tests/test_capa_recommendation.py`、`test_capa_draft_api.py`、`recommendation/`、`test_agent_readonly_resume_process.py`，以及前端 `capa-story-ai-recommend.spec.ts`、`capa-story-knowledge-sink.spec.ts`、`outcome-review.spec.ts`。R6 将来需区分退役断言与新流程验收，不把全部旧用例简单删除。旧服务的直接测试也不等于生产入口必须保留。
- 混合管道会写 `RecommendationCache`（24 小时到期、write-only）和有实际 LLM 尝试时的 `llm_recommend` 审计；这不是候选采纳证据。草稿服务缓存为 60 秒，单独尽力写 `AI_DRAFT` 生成审计；不能证明某段正文被员工采用。旧面板的 `beforeAdopt` PUT 与采纳 POST 是两个独立请求，不是一个原子事务；前者可能成功、后者失败。旧采纳有去重键 `(capa, d_step, source, item_ref, adopted_text)`、唯一索引和父行锁，但 `source/item_ref` 来自请求，不等同 R5 的服务端来源证明。

## 3. D4 范围决定与必要补齐

### 3.1 选择和取舍

**已确认（本轮用户回复）**：R6 补齐受控 D4 候选及员工确认，然后整体切换 D4/D5；不授权 Agent 直接改正式根因。

比较过的方案：

| 方案 | 受影响的用户场景与代价 | 结论 |
|---|---|---|
| 补齐 D4 后整体替换 | 保留员工从 D2/D3 出发寻找根因、修改候选并形成正式 D4 的能力；增加受控候选、来源读取和员工决定契约 | **推荐，用户已选择** |
| 退役 D4 AI，只保留手工 D4，替换 D5 | 可以减小交付范围，但员工失去候选根因推荐与草稿辅助，必须人工先完成根因；不能声称功能等价替换 | 未选 |
| 暂留旧 D4、先切 D5 | 保留短期功能，但继续维护两套推荐/模型出口与权限，旧通用采纳仍需收口；不满足 R6 整体替换目标 | 未选；不能作为静默上线降级 |

### 3.2 D4 新契约

执行状态：Tasks4/5专项、C9同报告确认/验证/证明及C10兼容已完成，C11最终全量进行中。

D4 入口必须在正式根因为空时也能工作。首片来源限当前报告有权使用的 D2/D3 事实及明确批准的 FMEA 投影；缺少这些能力声明/投影时阻塞任务，不偷用旧混合管道的跨模块搜索来填缺口。不引入 R7 通用搜索或跨模块写入。候选包含假设根因、支持/反对证据、缺失信息、来源版本及任务/命令引用；没有实证的内容标为待验证假设，不编造现场证据。

候选与来源归 CAPA，持久状态沿用待审、已采纳、已撤回、已替代；创建、更正、备选、命令重试与检查点定位采用 R5 的事务与范围语义。候选保存不改变 `d4_root_cause`，不签发“验证通过”或 D5 可用的来源证明。

员工确认要求当前员工对目标报告具有 **CAPA EDIT**，且满足该报告的租户、工厂和产品线写入范围；仅有 VIEW 或全部来源读取权不能确认。操作仅在 D4、候选仍待审且材料可编辑时执行。提交绑定候选 ID、原依据版本、当前正式根因版本、操作键、最终文本及追加/替换选择；界面默认追加，替换必须明确展示当前全文差异。CAPA 在同一事务锁定报告、候选、来源与当前身份，在提交事务内、全部可能等待的锁取得后重新核对当前员工的 CAPA EDIT、报告写入范围、全部来源读取权限、版本、阶段和终态，再写正式根因、修订、候选决定、原文/最终文本关系、来源限制、操作者和审计。只有 VIEW，或打开确认页后被撤销 EDIT 的员工，提交均失败；正式根因、修订、采纳决定及成功业务审计均不得新增或改变。冲突要求刷新，不重放旧全文覆盖同事。R5 `staff_action` 的 D5 专用规则不直接当作 D4 规则复用。

**受限 D4 的读取是硬前置**：现有 `d4_root_cause` 是自由文本，不能把受限候选直接追加后仍按普通报告权限输出。新采纳必须把完整来源限制绑定正式根因修订；正文、历史修订和派生内容的每个读取/导出/审核/模型交付入口均按当前报告和完整来源权限控制，无法保留限制则拒绝输出。字段含任一受限片段时对整段保守限制，不尝试不可靠的子串脱敏。普通手工修改继承已有来源限制，不能通过改措辞或全文替换自行清除；降敏/解除限制不在 R6 范围。全链读取保护未验收时，受限 D4 采纳保持关闭，**整体切换不放行**。

正式根因确认后仍由员工现场验证并按现有合同声明来源、取得有效证明，才能用 R5 生成 D5。R5 当前支持的来源证明类型不能因 D4 候选已采纳而扩大：若根因无法形成现有有效证明，明确说明 D5 Agent 任务不可用，员工仍可手工维护 D5。候选采纳、根因验证、证明、措施采纳是四个独立事实。

**“有效证明”不替代完整来源授权**：每次向 D5 插件或模型交付前，服务端必须从当前正式根因修订解析其继承的完整来源集合，并同时核对证明与该修订的绑定、来源版本，以及执行身份×安装×任务对全部来源的当前读取/交付权限和实际接收方许可；不能仅检查证明的主来源节点。追加来自 B 的候选后，原正文来自 A，则正式修订仍受 A＋B 限制；针对 B 签发的新证明不移除 A，也不授权仅有 B 权限的运行接收全文。来源集合无法完整解析、当前 R5 证明/交付契约无法表达或覆盖 A＋B 时，必须在正文离开服务端前拒绝该次交付，提示员工走手工 D5；不自动扩大证明类型或退回旧模型出口。后续重试、恢复和每轮交付重新判断，不能沿用之前的权限快照。

**来源版本必须抵抗 ABA**：FMEA 节点指纹本身不能识别“修改后又改回原文”。R6 的来源捕获还须持久绑定 FMEA 单调更新代际，并在交付、保存、重试、恢复及每轮调用前核对；合法的图或范围修改均推进代际，既有业务层递增不重复增加，禁止倒退。旧不可变来源缺少代际时保留其真实历史，不补填当前值；当前有权员工仍可读历史，但不能凭它重新签发可交付绑定。D2/D3 使用独立字段快照版本，历史捕获时的报告通用编辑计数不代替字段版本。来源变化后，若完整继承集合仍不能由当前 R5 证明范围表达，继续手工 D5；R6 不自动删减旧来源或解除限制。 已有来源记录或依赖代际的交付绑定时，迁移降级不得拆除代际防护；旧根因的合法交付 sidecar 也属于受保护证据，不能因 Origin 集合为空而允许降级。部署回退仍不降级数据库。

**报告输入授权单独表达**：K2/K3 不塞进 R5 的 FMEA 来源结构。采用服务端显式选择的 R6 D5 profile 和默认拒绝的精确报告快照能力；插件与任务两侧均须授权当前唯一报告，并在最终交付时重验。原 R5 profile、证明含义和历史 receipt 保持；R6 输入绑定及签名 sidecar 与原完整覆盖证明共同判定，不由客户端声明升级。此技术适配已独立复审，完整运行验收仍见实施台账。

静态依据：[验证来源服务](../../../backend/app/services/capa_verification_service.py) 的来源仅为关联 FMEA 的 `fmea_id/cause_node_id`；[R5 来源服务](../../../backend/app/services/capa_d5_proposals.py) `delivered_sources` 虽合并已交付来源并检查主来源，但不能据此推断它已经覆盖 R6 新增的正式修订继承集合。完整来源覆盖与交付前围栏已通过Tasks3–5受控接收器专项，随后C9真实模型合法正向与C10双配置来源反例亦已完成；不能只在建议保存时补查。

“获准/明确批准的FMEA投影”指本次来源能力、精确grant和接收方授权，不等于FMEA文档状态已正式approved；沿用R5范围，不新增文档审批门槛，测试如实记录draft状态。

**Task 5 技术适配（实现、专项和独立双复审通过）**：员工 D4 确认的当前表单令牌使用 material v2，除报告计数/切换代际外绑定正式修订、完整来源及其当前 FMEA 代际/范围元数据，开页后任一旧来源变化或 ABA 即使报告计数未变也拒绝旧提交。历史来源事实不改写；刷新并重新核对后，只要旧 Root 当前全来源资格成立且选中候选捕获仍新鲜，可继续员工确认。该区分不放宽模型 D4→D5 的证明/新鲜度要求，也不修改已签审核、R5 receipt或sidecar的历史验证。

**验证来源限制的技术补齐（实现、专项和独立双复审通过）**：验证记录的 `source_ref` 可清空或替换，已知来源限制须独立持久、单调保留；不能只在编辑当刻查旧来源。同行nullable JSONB ACL marker与DB约束记录实际已知 FMEA/节点/范围，不含正文/epoch、不等于来源证明，不自动给正式Root加来源或签发proof。旧NULL历史不回填为完整事实；合法编辑捕获原/新已知引用，读取与更新按完整已知集合∪当前引用、当前资格/范围先判元数据再读正文并末端复核。PPT、完整审核、preview和传播正文口同步保护；旧审计正文按来源未核实投影而非借当前ref猜权限。当前审核source版本/锁纳入已知集合；旧已签历史不重构。正式回退构建也须识别该marker及全部守卫。

## 4. 用户入口、服务端授权与退役边界

报告页保留 D4/D5 手工正文、根因验证、阶段推进及集中结果审核。统一侧栏提供“分析 D4 根因”和“根据当前根因建议 D5 措施”两种明确动作，选择管理员批准的具体部署；创建时绑定当前报告，换页面或换模型选择不改在途任务目标。报告中的候选/建议区按报告归属展示，不要求处理员工是任务发起者；追加指令和运行控制继续遵守任务角色规则。

员工逐项看原文、当前依据有效性、来源详情和最终文本；来源核对至少显示有权读取的模块/对象说明、版本、证据定位、证明状态及其与本项的关系。来源链接重新鉴权，不提供永久直链。R5 的 `D5ProposalItem` 仅含 task、state、basis_current 等，未提供上述来源详情；不能把“有来源行”当成已有核对 UI。R6 必须补受控来源详情读取/展示，先判完整权限再给名称和坐标，撤权后清除旧内容，隐藏项不泄露计数或摘要。

- 旧 `adopt_recommendation` 不再作为 D4/D5 的活动生产写路径；普通手工编辑不依赖它。`update_capa`、根因验证服务、`advance_capa`、根因修订、审核/审计/outbox 服务保留。旧推荐实现可随安全回退构建保留，默认路由禁用。旧 `AgentSession`/同步聊天不得经工具调用、内部绕路重新触达已退役写路径；仓库外调用方以访问清单/日志确认，不承诺无未知客户端。

本设计不要求历史正文业务转换；将来若需要查询适配，只做可逆的只读兼容投影，保留旧 ID/审计。旧采纳历史的受控只读呈现也是 R6 补齐项：当前不能将内部表存在等同员工已有历史查询入口。旧数据中原已出现的权限/来源缺失不能靠切换自动修复，也不能据此继续向新派生/模型无条件交付。进入新任务、采纳或审批时以当前证明和完整材料合同重新判定，不将历史保留误作新授权。

新known capture的继承须在读取相应正文前完成元数据鉴权，覆盖普通detail/list、历史、审核/导出、批量候选、embedding、缓存及模型首次/在途返回；SQL批量路径先排除不可授权项再取正文，不能只在SELECT后隐藏历史行。新采纳审计只保留受控引用，不把受限adopted_text放入普通日志。无法证明来源完整性、capture损坏或接收方许可不足时安全拒绝；缺证据的旧行仍保持原真实身份，不回填或推断为空来源。该保护是Task8实施中的必要补齐，专项与双版本运行验收仍须据实记录。 仅CAPA来源也须具备§12本地手工结案资格，保存真实CAPA来源及其创建身份，不虚构FMEA或文档版本；来源删除不改原证据或新增删除权限，当前来源不存在则安全拒绝。部署切换、运维续期和关闭生成不得使业务内容未变的已批准审核回执失效，手工表单切换版本与业务签名材料分域验证。

旧 `AI_DRAFT` 错误自由文本可能包含模型输入/输出，却无可靠来源绑定。原存储保留其真实历史；应用查询在 SQL 投影中仅给“历史错误详情未核实”等固定安全说明，异常 JSON 形状不回显原片段，不补填来源或假定有读取权。新格式错误响应及审计亦使用固定安全提示，状态/步骤等元事实保留；其他业务审计仍按其完整来源权限读取。

## 6. 在途切换：以已提交事实为准

目标采用**短暂的推荐写入停止受理与排空屏障**，而非让两版同时写。切换是服务端部署状态，有可审计的版本/时间/负责人和范围；不是浏览器 feature flag。Task8已实现tenant-local追加状态账本、独立短事务关闭准入及原业务事务级shared/exclusive advisory排空屏障；C9真实CLI及C10实际双进程运行验收已完成，用户环境尚未切换。

切换前先具备 R5、新 D4、来源核对 UI、手工版本冲突保护与安全回退版本。停止受理旧生成和采纳；停止旧实例接受新写入，排空已准入请求并确认最终提交/回滚和审计，再开放新入口。所有 worker、内部调用及旧版本实例必须一起纳入，不能旧实例带流量而新实例宣称切换完成。不能在界限内确定事务结果时保持停止受理，核清后再切换；不以杀进程或超时当作回滚证据。

运维文书在准入已关闭后过期时，过期文书仍不能完成切换。恢复须由受信部署登记授权准确新文书摘要，以显式续期操作绑定同一operation_ref、持久前文书摘要和当前draining epoch；目标、租户代际、构建、Schema、exercise_id、purpose与原始initial epoch不变，仅更新有效期和续期关联，正式文书另需新的独立批准。续期以独立短事务追加draining→draining新epoch及旧/新摘要、操作者审计，不恢复legacy、不等待排空锁、不改历史。提交结果未知的同文书重放先认持久新摘要，两份竞争续期仅一份生效；持旧文书等待的finish发现epoch/摘要已变须拒绝，不能静默继承新授权。该项是停止受理状态下的技术恢复合同，不改变§9已确认决定；实施及运行验收见计划Task8。

Task8已将旧采纳去重、独立准入见证、原业务事务提交审计和真实PG事务结果纳入排空核对；机制专项及独立双复审通过，实际候选/兼容应用演练与正式放行证据尚未产生。切换完成点 T 的前提是全部旧写入结果已经确定，T 后不再有旧事务提交。服务不可用窗口中保存的员工本地输入不自动重放。

## 7. 两种回退

### 7.1 业务撤回与正式更正

**Task 6 核心合同（实现、专项与双复审通过；6B API回审已验证，界面/整链/兼容待7/9/10）**：更正所需来源权限按所选措施及其完整历史来源，不以别的不可读条目/当前Root正文替代；整份审核仍要求全部材料来源。全报告版本令牌可内部收集完整元数据并签名，不读取/返回隐藏正文或来源ID，隐藏B变化使可读A旧表单冲突。旧v1批准历史保持严格只读，含更正的材料使用独立v2契约；Task6 core与后续6B正常回审、9/10整链/回退证据分开签收，不用测试种入新通过分析代替实际门禁。

沿用 R5：暂停不撤回，选检查点不撤回，重开不复活。员工逐项勾选仍待审项并填写原因；服务端重查当前权限、命令位置和状态，分别提交并返回结果。已采纳可读项显示已采纳，撤权项仅通用“当前不可操作”，不能泄露正文。更正的旧候选保留已替代历史。

已采纳 D4/D5 不适用“撤回建议”。D4 正式改写沿用 §3.2 的版本、来源继承和终态保护；不得把已采纳候选改回待审。**已采纳受限 D5 措施的正式更正是 R6 上线必需能力，缺失即阻塞切换**。R5 `staff_action` 只有 adopt/withdraw，目前没有此入口，不能用修改 `d5_correction` 或“联系人工流程”替代交付。

员工从报告页“正式 D5 措施”的指定条目进入“更正”，查看当前文本、当前版本、采纳时文本及受控更正历史，填写新文本和原因后提交。只有当前具备该报告 **CAPA EDIT**、租户/工厂/产品线写入范围，以及完整来源读取权的员工可以更正；不要求是原采纳人，Agent 无此权限。允许阶段为 D5_CORRECTION、D6_VERIFICATION、D7_PREVENTION；D7 完成及 D8 各待审核阶段先按正常流程退回可编辑阶段再更正，不直接改审核中的材料。此阶段白名单仅约束新的措施更正入口，不改变普通手工字段已有规则，也不新增状态机退回边。结案（D8_CLOSURE）和 ARCHIVED 核心材料继续冻结。

提交绑定 measure_id、当前条目版本、当前报告材料版本、操作键、最终文本及原因。服务按报告→措施→来源→当前身份的既有锁序，在所有等待后重验当前权限、完整来源、报告阶段、终态及两个版本。两个员工基于同一版本提交，只有先成功的一份生效，另一份返回冲突；响应丢失可用原操作键重试，换参数冲突。权限已撤销的重试同样不得返回受限结果。

原始建议与采纳时最终文本不可覆盖；每次更正以独立不可变版本保存前后关系、新文本、原因、操作者、时间及审计，当前展示解析最新有效版本，所有版本继续继承原完整来源限制。更正记录、当前版本变化、报告材料版本和业务审计在同一事务提交。更正导致审核材料版本改变：旧审核页面和旧 approval expectation 不可批准，审核人必须重新读取包含当前措施文本、更正版本及来源的完整材料；不得沿用更正前批准或静默省略条目。旧轮次已审快照保留原文；安全回退构建必须同时认识采纳原文、当前更正文本及受控历史。未实现此完整读取和版本化更正合同，不得进入正式切换。
