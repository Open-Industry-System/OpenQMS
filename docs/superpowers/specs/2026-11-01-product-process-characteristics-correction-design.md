## 1. 目标与约束

Issue 指出案例混淆产品特性与过程特性，未提供页面、截图或记录编号。本设计针对当前仓库静态核对中确认的问题，不声称已复现报告者当时的具体操作或线上数据。

用户确认的边界：

1. 按产品特性、过程特性的业务定义纠偏。
2. 控制计划内容依据 `Reference` 资料，不改变标准文档结构。
3. 考虑 DFMEA、IATF 16949 以及 APQP、FMEA、MSA、SPC、PPAP 五大质量工具的衔接。
4. 本阶段只整理详细设计，不修改代码、数据库、部署环境或 GitHub 内容。

成功标准：同一产品案例中，设计要求、制造风险与实际控制对象清晰对应；控制计划保持标准栏目，特性、规范、测量、抽样、控制及反应计划的归属明确；首次导入和后续同步不再产生功能冒充特性、规格丢失、错配或漏项。

非目标：重建全仓领域模型、建设全局特性主数据平台、重写审批体系、实现全部五大工具功能、引入新 AI 审核功能、宣称系统已取得或全面满足认证。

- 本设计是针对已确认语义错误的产品改进，不是完整合规审计结论。

- 不因资料缺失暂停已明确的特性区分与案例纠偏；依赖缺失版本的规则不得上线为强制门禁。
- 实施前记录实际适用版本和 CSR；涉及表格原始合并方式、符号含义且转换文本无法辨认的部分，以可读原件核对，不擅改现有模板。

## 4. 业务语义与不变量

### 4.1 四类概念

| 概念 | 含义 | 示例 |
| --- | --- | --- |
| 功能 | 对象需要完成的作用或预期结果 | 将元器件准确贴装至指定位置 |
| 产品特性 | 产品可判断或可测量的属性，来源于图纸、设计／性能规范等 | 贴装偏移量、输出电压、表面状态 |
| 过程特性 | 为实现产品特性所控制的制造过程条件／参数，也可能是可验证的定性状态 | 贴装力、炉温曲线参数、工装定位状态 |
| 控制／评价方法 | 控制或确认对象符合要求的手段 | 力传感器监控、AOI、首件确认、防错挑战试验 |

不根据“温度”“压力”等关键词强制判定类型：运行温升可为产品性能，炉温则可为过程条件。检测过程中使用的设置参数也不能未经风险和控制要求确认就自动成为过程特性。

### 4.2 必须保持的规则

1. 产品／过程类型与 CC／SC 特殊分类相互独立；不得按类型自动赋 CC 或 SC，也不把 CC／SC 当作全球统一含义。
2. 标准要求、顾客指定或组织风险识别是特殊分类依据；演示标记须说明只是组织示例。
3. 功能名称不等于特性名称；预防／探测措施不等于特性。
4. 数值和单位须对应控制对象；力使用 N，压力使用相应压力单位，不以字符串替换推断物理含义。
5. PFMEA 可以没有具体量值，不能因此阻止合法风险分析；CP 若缺少可执行的准则，应呈现未完成项而非编造限值。
6. 一个功能允许多项特性，一项产品特性可能由多项过程条件共同保证；不能取首项或构造全量笛卡尔配对。
7. 不把所有预防控制写为测量技术，也不把所有探测控制直接转为 SPC。
8. 缺失输入与明确清空必须区分；不能用“新值为空就保留旧值”掩盖源要求删除。

| 方案 | 优点 | 不足 | 结论 |

## 6. FMEA 数据设计

### 6.1 结构化特性集合

在现有功能节点中增加可选 `characteristics` 数组，不新增图节点类型，不改既有结构边枚举。每项至少包含：

| 字段 | 语义与约束 |
| --- | --- |
| `id` | 文档内唯一、创建后稳定的特性 UUID；改名／改规格不重建；复制为新特性时生成新 ID |
| `kind` | `product` 或 `process`；由实际 FMEA 类型、层级与业务语义校验 |
| `name` | 独立的特性名称，不从功能 `name` 自动替代 |
| `specification` | 对应该特性的规范／公差，可为空；允许定性准则或受控规范引用 |
| `unit` | 可选显示单位；与规范一致；不要求将所有文本限值结构化为上下限 |
| `classification` | 可选，沿用本系统支持的特殊分类；不在本次引入任意顾客符号字典 |
| `reference` | 可选的受控图纸／规范编号及版本说明，不作为已验证的跨文档外键 |
| `related_product_characteristic_ids` | 仅 PFMEA 过程特性使用的可选关系，指向同一 PFMEA 文档内产品特性；显式多对多，不跨文档隐式连接 |

约束：ID 文档内唯一；关联目标存在且为产品特性；禁止跨工序误关联。跨工序确有共同控制的业务应留待独立设计，不用宽松外键绕过当前工序边界。

功能节点原有 `name` 保持功能含义。现有 `requirement`、`specification`、`classification` 为兼容保留，不在读时直接覆盖或清空；规范化后以特性集合为 CP 映射事实来源，UI 明确标记旧字段仅为历史信息，避免双写形成两个权威来源。

### 6.2 DFMEA 与 PFMEA 的差异

- DFMEA：系统、子系统、零部件层级的相关功能可维护产品特性；不因底层共用 `ProcessWorkElementFunction` 就允许其被解释为制造过程参数。设计控制因素也不自动变成 PFMEA 过程特性。
- PFMEA：步骤功能维护产品特性；工作要素功能维护过程特性；过程项功能继续表达上层功能，不自动下发为所有工序的产品特性。
- 既有 `HAS_FUNCTION`、`FUNCTION_MAPPED_TO` 等结构不变；函数级关联不能无条件解释成其下所有特性的逐项关联。
- DFMEA 向 PFMEA 提供设计特性及风险输入。本次标准案例使用可核对的图纸／要求编号体现传递；不新增未经设计的跨文档自动同步服务。
- 既有 DFMEA 系统／子系统／零件表格和 PFMEA 七步法栏目不改变，仅在所属功能／特性编辑区域补充结构化录入。

### 6.3 旧图读取与保存

- 缺少 `characteristics` 的旧图可正常读取、展示、导出和保存，不强制批量改写已批准数据。
- 旧规格文本可预填为“待确认要求”，不得自动把整段功能名或自由文本拆成正式特性。
- 创建／编辑界面提供显式确认：选类型、填特性名、确认规范与特殊分类；只对用户提交的草稿保存规范化结果。
- 规范化采用既有 FMEA 写入服务、权限、状态、锁版本、审计及 embedding outbox；不得由图读取层写库。
- 图／表格转换、复制、节点删除、历史比较／恢复均保留特性集合；删除被关联的特性需提示并显式处理悬空关系，不能偷偷重指向第一项。

## 7. 控制计划文档结构与行项规则

### 7.1 不变的外部结构

沿用附录 A 及现有模板的标准栏目：

- 表头：编号、日期／修订、顾客信息、组织／现场、零件、工程更改、阶段、联系人／责任团队等适用信息。
- 过程编号、过程名称／作业描述、机器／设备／工装。
- 特性编号、产品特性、过程特性、特殊特性分类。
- 产品／过程规范与公差。
- 评价／测量技术、样本量、频率、控制方法（含适用防错要求）。
- 反应计划。

不删除、增设或重排标准业务栏目，不另建“产品版”“过程版”表格。参考资料对表头最低内容的要求应逐项与现有 UI 核对；若发现现有字段确实缺失，单列差距交用户确认，不在此次语义纠偏中擅自扩表。

### 7.2 明细行填写规则

参考 `FMEA_Explanation.md` §3.8：同一工序可有多条控制明细，分别填写最大间隙、拉脱力、压装压力、行程等对象及其对应控制内容。本设计对**新生成明细**采用：

- 每条明细表达一项明确控制的特性及其要求。
- 产品特性填产品列，过程特性填过程列；另一列留空，不用“同上”推断另一个控制对象。
- 同工序的编号、过程名称、设备信息可按既有样式重复或合并显示；不改变列分组和模板合并规则。
- 同一特性确有多个不同控制活动时允许多行，不能用“唯一特性 ID”限制合法控制计划。自动生成默认每项一个初稿行，后续复制控制行有独立行身份。
- 历史双特性行原样保留，只提示归属复核；不批量拆行，不认定所有双列填写均违反标准。

这是本产品为确保对应关系清晰采用的生成约定，不宣称标准一概禁止同一行两列均有内容。

## 8. CP 内部追溯设计

保留现有 `source_fmea_node_id` 表示来源工序，新增可空内部 `source_characteristic_ref`（JSONB、受约束的服务端 Schema），不出现在标准表格的新增业务列中。

内容：映射版本、来源 FMEA ID、工序 ID、功能 ID、工作要素 ID（适用时）、特性 ID。来源 FMEA 版本在每次导入／同步记录中捕获；基于批准快照的生成记录真实 `version_id`，不以“最新版本”推测来源。

身份规则：

- CP 行 `item_id` 始终是业务行身份，保持 CAPA 文档门禁及历史引用稳定。
- 特性来源键用于寻找同源行，不等于 CP 行 UUID；不能对同源特性多控制行设全局唯一约束。
- 对一个来源键只有一个自动管理行时可确定性同步；出现多控制行则逐行预览，不任选一条覆盖。
- 手工行或外部导入行可没有来源元数据，不伪造关联。
- 来源元数据由服务验证／生成，客户端不能伪造跨租户、工厂、产品线或其他 FMEA 的来源。
- 新增元数据纳入版本快照、比较、恢复和哈希计算；旧快照缺失字段按缺失处理，不回写更改历史哈希。

## 9. 统一导入、预览和同步

### 9.1 单一派生口径

在现有业务服务区域设置一个聚焦的纯映射能力，输入 FMEA 类型、确定的 graph 快照与已选工序，输出标准 CP 初稿字段、稳定来源键与问题列表。以下调用共用：

1. 首次 PFMEA 导入；
2. `build_sync_preview`；
3. `check_sync`；
4. 本次相关的一致性校验。

不要求这些调用读取同一“最新图”：首次导入使用用户确认的批准版本，同步使用用户选择的目标批准版本，检查明确展示所比较版本。复用的是派生规则，不是混用来源版本。

### 9.2 映射矩阵

| CP 字段 | 来源／规则 |
| --- | --- |
| `step_no`、`process_name` | 所选 ProcessStep 的工序号和名称 |
| `equipment` | 关联的真实机器／工装信息；不能将 Man／Material 等所有 4M 工作要素名称当设备；无可靠设备来源则留空待补 |
| `characteristic_no` | 有受控业务编号时使用；不存在时由用户补充，不冒充图纸特性号；内部 UUID 不强行打印为业务编号 |
| `product_characteristic` | `kind=product` 的特性 `name` |
| `process_characteristic` | `kind=process` 的特性 `name` |
| `specification_tolerance` | 当前行特性的 `specification`，单位按对应对象展示且不重复拼接 |
| `special_class` | 当前特性的分类，不再从同工序另一个特性继承 |
| 评价／抽样／控制／反应 | 无逐项可靠来源时留待人工完善；已有控制节点只提供有来源标识的候选，不凭功能级连接自动套用到所有特性 |
| 来源元数据 | 服务端从实际快照及特性身份生成 |

### 9.3 遍历与覆盖

- 按正确的边类型遍历：工序→工作要素用 `HAS_WORK_ELEMENT`，结构→功能用 `HAS_FUNCTION`；不只检查目标节点类型。
- 先列出工序下全部明确产品特性和过程特性，独立生成明细；显式关系用于追溯，不用于把两者合并成一个混合要求行。
- 同一过程特性关联多个产品特性时，不因关系数重复生成默认控制行。
- 缺少显式特性关系时仍可生成其独立明细，但标记关系待确认；不回退选择第一条，不编造关联。
- 所选工序只含旧自由文本时，阻止该次生成并列出需规范化的节点；不自动复制功能名，也不悄悄跳过后报告全部成功。用户可先确认源数据或显式缩小工序选择。
- 只允许 PFMEA 作为制造控制计划生成入口；DFMEA 不直接套入该导入接口。

### 9.4 接口与并发约定

保留现有业务 URL。导入支持显式目标 `source_fmea_version_id` 与 CP `expected_lock_version`；旧调用不带版本时，只有在服务能唯一确定批准源且确认锁版本后才能继续，否则返回明确的业务冲突，不能静默改选来源。

设计两个阶段：同一派生逻辑先给出无写入预览，再由用户确认应用。预览描述源版本、目标 CP 锁版本、映射版本、稳定候选键及问题；应用重新授权、核对版本并重新派生。通过稳定候选键选项，不依赖每次生成的新随机“候选行 UUID”。

- 预览与应用之间 CP 有修改：拒绝过期应用，重新预览。
- 目标版本、工序选择或映射版本不符：拒绝，不能应用另一份结果。
- 新增行 UUID 仅在实际创建时确定；已存在同源自动行不重复追加，人工复制控制行不被合并。
- 首次应用要求 CP 处于允许编辑状态，来源批准状态及版本可用性在后端验证，而不是只信任前端过滤。
- 使用现有事务、作用域及锁策略，不新增独立任务运行时。

### 9.5 同步及字段归属

同步预览按特性来源键和实际 CP 行身份逐项展示新增、修改、删除、历史歧义或人工冲突。不能按工序 ID 覆盖整个工序，也不能把多行压成首条。

源管理字段：工序信息、特性名称、规范、分类及可靠设备来源。CP 人工管理字段：评价方法、样本量、频次、控制方法、反应计划及执行关联。源数据变动不能直接覆盖人工字段，应提示其适用性需复核。

- 每项源字段展示“当前值／上次接受源值／本次源值”，用来源版本及既有快照取得基线；无基线标记需人工确认，不假装三方自动合并。
- 用户主动修改过源管理字段时作为冲突处理，不无提示覆盖。
- 源规范从有值变为空、特殊分类被取消时，预览显式清空及影响；只有确认后生效。
- 来源特性删除：提示控制覆盖影响，不自动删除关联 SPC／量具或历史证据；有关受审材料和来源删除限制按既有保护执行。
- 工序改号、特性改名保留 ID，识别为修改，不变成删增。
- 未全部接受目标版本的变更时，不把整份 CP 标成已完全同步；来源版本标记和 sync_pending 按覆盖结果保守处理。

## 10. 编辑、校验和人工确认

### 10.1 页面变化

FMEA 功能编辑区域分别展示“功能”“特性名称”“规范／公差”“单位”“特殊分类”“依据”。支持一功能多特性及显式关联；DFMEA／PFMEA 使用符合各自层级的中文标签。

CP 标准表格不新增业务列；来源、旧数据提示和一致性问题放在既有详情、预览或校验面板。导入成功仅意味着初稿生成，不能提示“已符合标准”。

现有图表转换、共享节点删除及多后果语义保持不变；不能为增加特性编辑而重新排列失效链或丢弃 wizardScope。

### 10.2 校验分层

| 情况 | 行为 |
| --- | --- |
| 新结构 ID 重复、关联越界、类型与所属 FMEA 层级不合法、来源伪造 | 保存／应用时确定性拒绝 |
| 所选源工序无明确特性、源版本不符或预览过期 | 生成／同步时拒绝，并定位问题 |
| 旧双特性行归属不清、规格缺失、检测方法可能不适用 | 保留原记录并提示复核，不自动改写 |
| 量纲明显不一致 | 有明确结构化证据时提示；不以宽泛正则误拒定性要求或外部规范引用 |
| 缺控制、抽样或反应内容 | 复用既有完整性校验并补相关提示；不在本次未经批准地全局加严批准门禁 |
| SPC／量具链接不存在、跨作用域或已失效 | 遵循现有后端有效性及访问检查；名称相似不自动建立关联 |

关键词／语义推测不能作为唯一强制拒绝依据。本次不使用 LLM 自动判定标准符合性。

新增校验规则须使用未占用的规则标识；同工序多特性、多控制行的稳定问题键要包含实际特性／行身份，避免复核状态互相覆盖。

## 11. 标准案例设计

### 11.1 产品与要求传递

主产品保持“DC-DC 100W 电源模块”，制造环节保持 SMT；删除该产品下无业务依据的电机空载转速内容。

- DFMEA：表达电源模块的设计功能与产品性能要求，例如稳压输出；要求值、工作条件与验证方法需作为一组演示规范定义。
- PFMEA：分析 SMT 步骤的预期产品结果及过程条件，说明制造缺陷如何影响设计功能。
- CP：来自相同产品和明确工序的特性控制，不要求 DFMEA 每一个性能指标都与某一个 SMT 偏移量做一对一直接映射。
- 通过示例图纸／规范编号说明来源，不生成假冒真实顾客批准、MSA 合格报告或 PPAP 证据。

### 11.2 同工序的两条控制明细

以下均为演示参数，非通用工艺推荐，不得用于实际生产设定。

| 标准栏目 | 产品特性控制明细 | 过程特性控制明细 |
| --- | --- | --- |
| 工序 | OP10 SMT 元器件贴装 | OP10 SMT 元器件贴装 |
| 设备 | 贴片机；评价设备按实际方法说明 | 贴片机及贴装力监控装置 |
| 产品特性 | 元器件贴装偏移量 | 空 |
| 过程特性 | 空 | 贴装力 |
| 规范／公差 | ≤0.05 mm，测量基准引用演示规范 | 3.0±0.5 N |
| 评价／测量技术 | 3D-AOI 位置测量，引用对应程序／判定规范 | 贴装力传感器及经确认的监控程序 |
| 样本量／频率 | 按演示控制方案完整定义，不能与 AOI 实际覆盖矛盾 | 按演示监控方案定义，不能沿用位置抽检频次 |

首次实现示例以逐件 AOI 检查和逐贴装动作力监控作为演示假设，样本量／频次填写相应“1 件／每件”“1 次动作／每次贴装”；不自动宣称使用 Xbar-R 图。若另行展示 SPC，应提供适用抽样方案、数据和判异规则，作为独立明确的演示配置。

特殊分类默认空；需要展示 CC／SC 时，以明确的“演示组织特殊特性规则”指定及解释，不能仅为页面效果任意贴标。

其他工序仅保留能给出具体特性及控制依据的示例。“焊接质量”细化为可判断属性；“包装防护”“测试参数设置”“磨损检测”分别回归正确的控制对象或方法栏目。没有可靠内容的占位不包装成已批准完整案例。

## 12. 五大工具的一致性检查边界

| 工具／文件 | 本次检查 | 本次不承诺 |
| --- | --- | --- |

## 13. 历史数据、迁移与发布

1. 结构化特性存在于既有 JSONB 内；CP 新增可空来源元数据需要手写迁移。迁移只加兼容存储，不自动重写业务内容。
2. 后端先支持读取新旧结构、保留新增字段及快照兼容，再上线编辑和新映射；不能先开放前端导致后端丢字段。
3. 旧已批准 FMEA／CP、版本快照、签批信息保持不变。修正内容必须经现有返工／修订／审批流程；若 CP 缺少可用修订路径，作为实施阻塞记录，不绕过 approved 写保护。
4. 对历史单特性来源，只能在唯一且经人工确认后补充元数据；混合行提供替换建议，不自动拆分，不重新分配已有行 UUID。
5. 关联 CAPA 门禁、受审材料、SPC、量具、特殊特性清单的行不可强制删除；必须经过已有业务保护和确认。
6. 普通 seed 当前命中已有数据会跳过，因此修正 seed 只保证新环境。已有演示环境采用明确授权、可审计的修订；不运行清库／重置，也不以 `document_no` 匹配就覆盖真实记录。
7. E2E 数据修正要同步 canonical snapshot、差异断言、哈希和门禁夹具；不能只改显示名导致验收基线失真。
8. 回退应用不得丢失新增字段。新数据写入后禁止直接降级到会过滤字段的旧 Schema；回退前保持兼容读取并验证备份，必要时停止新映射而不是删列。

## 14. 权限、事务与审计

- 所有读写沿用 RequestScope 与现有工厂／产品线检查；预览不能泄露无权访问的源图或版本。
- 来源解析、状态检查、锁版本确认在实际应用时重新执行；不将预览成功视为持续授权。
- 同一事务完成行项、来源元数据、版本及业务审计；失败全量回滚，不留下部分生成明细。
- 新增／修订图继续沿用现有 embedding 入队约定，在 commit 前入队；不依赖 Neo4j 是否及时投影决定写入结果。
- 审计保留操作者、源文档／版本、目标 CP、接受项、旧值／新值及变更原因；不自动授予审批权限。
- 人工选择“不处理”不能成为隐式永久豁免；保留未完成标识，按既有流程复核。
