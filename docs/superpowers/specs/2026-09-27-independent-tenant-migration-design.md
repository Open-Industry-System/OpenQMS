设计前的 `TenantService.provision` 与 `app.cli.tenant_migrate` 调用 `alembic -x schema=<tenant> upgrade tenant@head`。`t001_tenant_squash` 与平台、历史业务分支在 `999_merge_all` 合流，使 `tenant@head` 不再只包含租户专用步骤。当前实现已改为锁所有者执行独立链；以下保留原问题作为设计依据。

在一次性测试库验证：

- 已迁移的公共库中，对空租户运行 `tenant@head`，在本次新迁移之前尝试再次建立 `public.tenants`，报 `DuplicateTableError`。
- 否则为空的测试库中，相同命令在历史 `20260711_d3_containment_tables` 处失败：`capa_d3_import_run` 的复合外键指向尚不存在的 `capa_eightd.factory_id`。**不是** `factories.factory_id`；后者的真实主键为 `factories.id`。
- 已迁移的公共库中，只执行 `t001_tenant_squash` 可返回成功，却只在目标租户留下版本表：`TenantBase.metadata.create_all(checkfirst=True)` 的表存在检查会看见 search_path 中的 `public` 表。改用 `checkfirst=False` 在隔离租户里可建立业务表，但不具备公共库的完整数据库语义：同名业务表的索引计数 529 对 265、约束计数 746 对 715，公共库另有 5 个非内部触发器。计数只用于说明差异，验收须比较具体定义。

因此不通过改一个外键、动态 `create_all()` 后 stamp head、复制公共库业务数据或直接回放现有合流历史来声明租户已建成。Task 1 的插件表迁移在其已确认的父版本之上通过；它不证明完整空租户可升级。

## 2. 已确认决策与非目标

1. 新租户采用**独立版本链和独立租户版本表**；公共库/单租户历史链维持原样，不重写已应用的 Alembic revision 关系。
2. 初始租户 schema 是在干净、一次性公共库迁移到受控基准后生成并审查的**版本化静态结构快照**，只含业务 schema DDL，不含业务数据、平台租户登记或凭据。运行时不从公共库动态导出，也不调用当前 ORM 的 `create_all()` 冒充完整迁移。
3. 当前已有租户均为可丢弃的**测试租户**，允许经明确清单和测试环境门禁逐个删除 schema、重建与重新初始化；不承担旧测试数据原地保留。此许可不延伸到未来真实租户或 `public`。
4. 新、旧测试租户都必须先通过结构完整性与租户隔离检查，才标为 `active`；失败留下 `failed` 与错误证据，不自动 stamp 或假装恢复成功。
5. Agent R1 Task 2 在新租户完整迁移验收与 Task 1 的新租户回归测试通过前保持暂停。已有 R1 代码不因本设计而删除或改变默认禁用状态。
6. 租户上下文**逐事务绑定**，不仅用于迁移 DDL：每次新事务在第一条业务 SQL 前重新确认租户仍可访问，并使用无 `public` 业务表回退的租户搜索路径；`commit`、`rollback`、连接重用之后均重新绑定，缺失或失败时拒绝业务查询与写入。平台登记操作走独立 public 会话。
7. 测试租户重建采用离线排空与租户代际隔离：先停止接入新请求/新后台任务，停止或等完已有执行，确认静默并持有迁移互斥锁后才能删除 schema；无法证明静默就拒绝。每次重建递增 tenant generation，旧请求、预先枚举的 worker 或旧运行凭据在新 schema 上不得继续写入。
8. 新租户失败可对**同一登记**按真实 schema/版本/seed 状态恢复；不再用重复创建租户行处理重试。seed 原子化或经可验证的幂等检查重试，平台状态滞后时以 schema 内版本和数据不变量对账。只有测试重建路径可在显式授权下丢弃部分 schema，真实租户绝不自动重置。
9. 普通业务与迁移维护使用**不同的事务门禁**。普通业务取得事务级共享锁，只在平台登记为 `active` 且 generation 与入口捕获值一致时访问。维护协调器在一条固定数据库连接上持有会话级独占锁，**只暴露受控维护上下文，不把原始 `AsyncConnection` 交给调用方**；上下文封装迁移、seed、校验，每个新事务核对当前尝试 ID、generation、维护状态、连接身份与独占锁所有权后绑定租户 schema。维护操作不再申请另一连接上的普通共享锁；“内部调用”或自报维护标志不构成例外。
10. 多租户模式下暂时**禁止进程全局 AI provider 初始化/重建**及**全局 Neo4j 图谱重建/失败任务批量重置**（服务、CLI 与 API 入口）；不能把租户密钥写入一个共享 `app.state`，也不能因遍历租户反复执行 `MATCH (n) DETACH DELETE n`。单租户路径保持原行为。租户级模型配置和图谱命名空间另立设计，不在本迁移前置任务内启用。多租户日志写入和 CP 同步 worker 则必须采用受 generation 检查的租户绑定会话，不得回退 public 业务表。

首版不迁移真实租户历史数据，不实现生产租户 schema 重置，不建立从公共库复制业务行的模板，也不修改 `tenant@head` 历史 revision 来碰运气。未来第一个真实租户产生之后，只能走独立链的向前增量迁移；需要跨版本数据变换时另立迁移规格。

## 3. 组件与接口边界

| 组件 | 职责 | 不得做的事 |
|---|---|---|
| 独立租户 Alembic 环境 | 使用单独 `script_location`、`tenant_schema_version`，只遍历租户 revision；设置经过校验的租户 schema 搜索路径 | 读取或创建 `public.tenants`、重放公共历史、把失败版本 stamp 为成功 |
| 静态基线生成器（开发时） | 从干净、已迁移的 PostgreSQL 15 一次性库导出业务对象定义，排除平台对象/数据；生成规范化快照、哈希和对象清单，供代码审查 | 在生产启动或租户请求中调用 `pg_dump`；把测试账号或秘密写入快照 |
| 基线 revision | 在目标租户内建立固定版本的业务表、索引、约束、函数与触发器；再记录独立版本 | 依赖 public 中同名业务表的存在性检查或用动态 ORM 元数据默默改写历史基线 |
| 租户事务绑定入口 | 请求 `get_db`、后台 `get_tenant_aware_session`/`run_for_each_tenant` 走共享锁＋active/generation 校验；维护 seed 走专用维护上下文；两者每个事务都严格设置 `SET LOCAL search_path` | 只在会话建立时设一次路径，或让维护事务误用普通 active 门禁 |
| 租户迁移协调器 | `TenantService.provision`、租户迁移 CLI 共用创建、升级、结构检查和阶段记录；受控维护上下文内部固定连接持有会话级独占锁，由上下文方法调用 Alembic/seed/校验 | 子进程或另一个连接绕过锁所有权，或维护时额外申请另一连接的共享锁 |
| 静默/代际门禁 | 测试重建前设置维护态、停止新任务，等待/终止旧请求和 worker，验证静默；每次事务验证 tenant generation，迁移独占锁等待现有事务结束 | 仅凭请求开始时的 active 判断，或仅凭迁移进程的互斥锁就删除 schema |
| 恢复协调器 | 同一 tenant ID 的显式重试；检查 schema 是否存在、独立版本号、结构校验、seed 不变量、平台状态，逐阶段恢复或拒绝 | 重复登记相同 slug、盲目重跑分段 seed、对真实租户自动删除部分 schema |
| 测试租户重建命令 | 先 dry-run 列出明确 tenant ID/slug/schema，显式 test-only 开关及确认；确认静默后逐个重建和 seed | 模糊匹配租户、碰 `public`、在生产模式/未列入清单或有在途工作时执行删除 |
| 结构一致性检查 | 比较公共基准与租户的业务对象定义和租户特有版本对象的允许差异 | 只比较表数，或对未知差异自动豁免 |

租户迁移 DDL 应以受验证的租户 schema 为目标，默认不通过 `public` 回退解析业务表。需要共享的扩展函数显式限定 schema；租户拥有的函数与触发器随基线进入租户。标识符先经项目现有 schema-name 校验规则，再安全引用，不能将请求文本拼接进 SQL。

**普通业务事务**：事务开始时对同一 tenant ID 的锁键调用事务级*尝试获取*共享锁；拿不到即返回维护中，不等待迁移完成后继续使用旧上下文。拿到后，经显式限定的控制面查询核对 `public.tenants.status == active` 且 generation 与请求/worker 捕获值一致，再在该事务执行 `SET LOCAL search_path TO <validated tenant>, pg_catalog`，之后才允许业务 SQL。`commit`/`rollback` 释放共享锁和路径绑定；同一 `AsyncSession` 下一事务必须重来。连接 checkout 的 `RESET search_path` 只是兜底。平台操作使用独立 public 会话，不让租户业务表回退到 public。

**迁移维护事务**：协调器先凭 tenant ID 在**一条固定的数据库物理连接**上尝试取得同键的会话级独占锁（首版立即拒绝冲突，不等待）；然后在该连接上锁定平台租户行，核对状态和 schema，生成并提交唯一尝试 ID 与新 generation，记录后端 PID；在此之前不允许迁移或 seed。测试重建先停止应用与 worker 接收新工作、设置维护态（尚不更新 generation），等完或终止已进入执行的工作，再由持锁协调器更新 generation。竞争者拿不到独占锁时不得修改平台尝试状态。在持锁期间只向协调器提供受控维护上下文：`run_migration` 在内部将该连接注入独立 Alembic 环境；`seed_tenant` 在上下文内部使用绑定此连接且每次 `after_begin` 都复核的私有会话；结构对照通过上下文的受控只读事务执行。调用方既拿不到原始 `AsyncConnection`，也拿不到可经 `.bind` 取得该连接的 `AsyncSession`；只调用受控上下文方法。每个新事务先核对平台登记为当前尝试允许的 `provisioning/维护态`、尝试 ID、generation、当前连接 PID 和该 PID 持有的独占锁，再执行严格的 `SET LOCAL`，**不额外获取普通共享锁**。内部 Alembic 原始连接只能在已验证的上下文方法内使用，不能以它对外提供绕过接口。不能通过自报“内部调用”跳过这些校验；连接丢失、锁丢失或校验不符即中止尝试，不切换到另一个连接继续。连接从池中取出后须先确认同键会话锁**尚未由该后端持有**，避免 PostgreSQL 可重入锁叠加；不能证明干净就拒绝并使该物理连接失效。获取锁时若取消或结果不确定，也要使连接失效，不能将可能带锁的连接放回池。释放锁须确认解锁成功且无残留同键锁，否则使连接失效。当前 subprocess Alembic 调用须改为接受内部注入连接的进程内执行，不能在子进程里等待协调器自己的锁。最终校验通过并提交平台 `active` 后才释放会话锁和连接；新请求此后仍须逐事务按新 generation 获取共享锁。

旧请求/worker 即使在维护态之前已枚举该租户，下一事务也因 generation 或状态不符而拒绝。删除前还要确认应用/worker 已排空、相关在途工作无未确认执行及无旧租户事务持锁；不能确认即拒绝删除。迁移独占锁只保证数据库事务互斥，不代替业务执行静默确认。

现有直接使用 `async_session()` 的调用逐项分类：多租户 `DBLogHandler` 队列须携带服务端捕获的 tenant ID/schema/generation，而非仅 schema 字符串；drainer 使用绑定会话，状态或代际失效时丢弃该租户批次而不写入 public。独立 CP 同步循环按 active 租户调用 `run_for_each_tenant()` 并逐事务复核。AI 配置服务在多租户模式下须在读取/写入密钥或更新全局 `app.state` 之前拒绝；启动流程显式跳过全局 provider 恢复。`GraphProjectionService.full_rebuild` 在任何全局清除之前拒绝，CLI 的 full/retry 与 API 的重建请求也在接受任务之前拒绝；不能只在后台任务里延迟失败。未来要开放这些能力，须先定义每租户 provider 生命周期和 Neo4j 命名空间。

生成基线时记录来源代码提交、PostgreSQL 主版本、公共库 Alembic head、对象清单与快照 SHA-256。后续公共和租户业务变更各写向前迁移并通过 CI 结构对照，不能让快照随 ORM 模型自动漂移。固定基线的目标版本包含 R1 Task 1 的插件安装/授权表；后续 R1 表进入两条链各自的增量版本。

## 4. 新租户与测试租户重建流程

**新租户**：平台先登记稳定 tenant ID、schema 名及 `provisioning`，持锁后才确定 generation 与当前尝试 ID；按 `schema_created → migrated → verified → seeded → active` 保存阶段。创建空 schema → 执行独立链 → 校验结构 → 在严格租户事务中一次性 seed 角色/权限、默认工厂/产品线和首位管理员 → 校验关键读写与隔离 → 记录实际 schema 版本并将平台状态置为 `active`。现有 seed helper 的中间 `commit()` 必须改为调用方统一提交；失败整笔 seed 回滚。迁移、seed、校验都通过协调器受控维护上下文在同一持锁连接上逐事务绑定；仅最终校验通过才开放访问。

**现有测试租户重建**：读取平台登记与实际 schema，dry-run 输出精确租户 ID/slug/schema；要求非生产模式、独立 test-rebuild 开关、明确清单和丢弃确认。停用新请求与新任务、停止或等完应用/worker 在途工作，设置维护态但尚不更改 generation；在固定连接上获得独占迁移锁并提交新 generation/尝试 ID并确认无旧事务及未确认工作后，才逐个删除对应测试 schema；受控上下文贯穿重建、迁移、单事务 seed 和校验，不启动另一个取共享锁的子进程。保留平台 tenant ID/slug；首位管理员的新启动凭据由授权操作者本次交互提供，仅在内存中传递，不写入登记、清单或日志。若无法确认静默则**不删除**；一个租户失败不使其他租户被标成成功，失败时保持不可用状态和诊断信息。测试数据已获准丢弃，但不把部分完成展示为成功或可回滚快照。

**崩溃/重试入口**：提供以既有 tenant ID 为对象的显式 `resume`；不能再次 `provision` 同一个 slug 创建新行。在固定连接先取得同租户独占锁，并确认上次尝试不在运行；随后锁定平台行、创建新的恢复尝试 ID 并递增 generation，旧尝试的凭据随之失效。随后对账平台阶段、schema 是否存在、租户版本表、结构指纹和 seed 不变量：缺 schema 才创建；版本和结构一致则跳过已提交迁移；完整 seed 已提交而平台仍为 `provisioning` 时直接校验并推进状态，不重复插入。seed 不完整则按单事务回滚/幂等键规则重做；若首位管理员尚未建立，恢复调用须由有权操作者重新提供启动凭据并核对 tenant ID/slug，平台登记和日志不得保存明文密码。seed 已完整时无需再次提供密码。版本不明、部分 DDL 或来源不清时停下并报告，不自动 stamp。测试重建的部分 schema 只有在再次满足 test-only/清单/排空确认后才能丢弃重建；真实租户不自动重置。

运行前仍核对清单：若登记、schema、环境任一项不能证明目标只是获准的测试租户，停止并请人确认；不将“目前都为测试租户”写成永久的生产假设。未来真实租户的增量升级经版本校验与迁移事务执行，不能调用 test-rebuild 命令。

## 5. 失败处理与验收

- 空库公共 schema 迁移与空租户基线分别运行；已存在平台表时再建租户不得重复创建 `public.tenants`。不允许失败后自动 stamp 到目标版本。
- 从零创建的租户与受控公共基准按**同名业务对象**比较表及列类型/默认值/空值性、主外键与检查约束、唯一/普通/部分/GIN 索引、函数和触发器定义。明确记录可接受的租户专属对象（如版本表），其他差异为失败；兼测关键 D3、FMEA/CP 版本哈希与全文检索行为。
- 逐事务隔离测试：同一 `AsyncSession` 连续 `commit()` 两次、`rollback()` 后再查询、连接归还再复用、两租户交错运行，始终重新绑定目标 schema；读写只能命中正确租户，公共业务表行数/内容不变，缺失租户绑定直接拒绝。平台控制面 public 查询仍正常。
