# US-E2E-01.6 8D → 供应商风险评级输入 — Design

**日期**: 2026-07-16  
**状态**: 设计定稿（待实现）  
**子故事**: `docs/user-stories/US-E2E-01-capa-8d-closed-loop/US-E2E-01.6-supplier-risk-input.md`（定稿 v1，2026-07-08）  
**AI_REQUIRED**: false  
**Gap**: `docs/superpowers/specs/2026-07-08-us-e2e-01-gap-analysis.md` §01.6  

## 1. 目标

涉及供应商的来料不良 8D，在流转至 D7_COMPLETED 后，自动将其严重度、处置结果、是否重复发生传递给供应商风险模块，作为风险评级输入。评级结果（含自动评估建议与人工确认流）在 8D 侧可读可见并写审计，实现 8D 数据链路至供应商评级的单向可追溯。故事约定：仅验证输入传递、结构与关联是否通畅，**不验收风险评级算法的准确度**。

## 2. 已有基建（复用，不重造）

| 资产 | 用途 |
|---|---|
| `SupplierRiskAlert.linked_capa_id` | 现存 FK，指向 `capa_eightd.report_id`，`ON DELETE SET NULL` |
| `SupplierRiskInput` / `run_all_rules` / `evaluate_supplier_risk` | 现存规则引擎打分、评估工作流 |
| `capa_ppt_service._load_linked_risk_alerts` | 现存使用 `linked_capa_id` 反查预警的示例 |
| 审计事件 `SUPPLIER_RISK_INPUT_SENT` / `CHANGED` | 故事契约中预定的事件常量 |

**缺口**: 
- 无 8D 侧的自动触发调用点；
- 规则引擎 `SupplierRiskInput` 缺少 8D 输入，无匹配的规则消费此输入；
- 缺乏基于 `fmea_node_id` 的重复发生自动探测算法；
- 缺乏自动判定后的人工确认端点及 8D 侧投影 UI。

## 3. 决策摘要

| 决策 | 选择 | 理由 |
|---|---|---|
| 触发时机 | **advance_capa `D7_COMPLETED` 成功后自动触发** | 此时 severity、d4_root_cause、d7_prevention 均已落库，语义符合前置；失败不阻断。 |
| 是否重复判定来源 | **服务端自动查历史 (suggested) + 人工主动确认 (confirmed)** | 精确匹配已关闭历史单同 FMEA 节点，避免手误，但保留最终人工作用。 |
| 自动判定匹配口径 | **fmea_node_id 精确匹配** | 最严谨的结构化依据，不越界搞模糊相似计算。 |
| 数据传递承载方式 | 挂载于现有 JSONB `alert.rule_results._capa_input` | 不新增表结构字段，将传值与计分透明剥离。 |
| 规则消耗与计分 | **新增 R11，三字段均计分，配置默认阈值** | 最贴合故事“严重度+处置+是否重复作为输入”要求。 |
| 失败容错 | **吞掉异常，记录 FAILED 审计，不阻断 advance 事务** | 8D 的推进不受供应商服务不稳定影响，符合 AI_REQUIRED=false 容忍度。 |

## 4. 数据模型

### 4.1 SupplierRiskAlert 表（无改动，复用 JSONB）

复用现有的 `rule_results` 字段（JSONB），约定新增根键 `_capa_input` 保存传递的原始结构化数据：

```json
{
  "_capa_input": {
    "source_capa_id": "uuid-string",
    "severity": "严重",
    "disposition": "退货 / 报废等文本...",
    "repeat_suggested": true,
    "repeat_confirmed": null,            // 初始 null，确认后为 true/false
    "matched_capa_nos": ["8D-2025-001"]  // fmea_node_id 命中的同 supplier 历史单
  },
  "R11": { ... } // 规则计分结果
}
```

### 4.2 扩展 CAPAResponse 投影

在 CAPA 查询和响应模型中，根据 `linked_capa_id == report_id` 的 `SupplierRiskAlert` 行填充只读数据（与 01.5 投影 SCAR 一致）。

```ts
export interface LinkedRiskAlert {
  alert_id: string;
  risk_level: "low" | "medium" | "high" | "critical";
  status: string;
  repeat_suggested: boolean;
  repeat_confirmed: boolean | null;
  matched_capa_nos: string[];
}

// CAPAResponse
linked_risk_alert?: LinkedRiskAlert | null;
```

## 5. API / 服务逻辑

### 5.1 自动触发服务：`_trigger_supplier_risk_input`

**被调用位置**：`backend/app/services/capa_service.py:advance_capa`
在执行完 `capa = await capa_service.advance_capa(...)` 且目标状态为 `D7_COMPLETED` 时，处于 `db.commit()` **之前**调用。若遇到任何异常抛出，均 `except Exception` 吞掉并在同一事务内写 `SUPPLIER_RISK_INPUT_FAILED` 审计日志，从而**不阻断**原有的 8D 流转。

**执行步骤**：
1. **守卫**：若 `capa.supplier_id` 为空，直接返回（仅处理来料不良及有明确供应商的 8D）。
2. **自动探测 Repeat**：
   - 查 `CAPAEightD` 表，条件：`supplier_id == capa.supplier_id` 且 `product_line_code == capa.product_line_code` 且 `fmea_node_id == capa.fmea_node_id` 且 `fmea_node_id IS NOT NULL` 且 `status IN (D8_CLOSURE, ARCHIVED)` 且 `report_id != capa.report_id`。
   - 若存在则 `repeat_suggested = True` 且 `matched_capa_nos = [x.document_no for x in hits]`，否则 `False`。
3. **调用供应商预警模型**：
   - 将这套上下文组装放进 `SupplierRiskInput`。
   - 走 `run_all_rules`（其中包括新增加的规则 R11）。
   - 更新或创建 `SupplierRiskAlert`。设置 `linked_capa_id = capa.report_id`。
   - 将 `_capa_input` 序列化（UUID 转字符串）存入 `alert.rule_results`。
4. **审计**：
   - 写入一条 `SUPPLIER_RISK_INPUT_SENT`，挂在 CAPA 表上。`changed_fields` 包含 `severity`, `disposition`(`d7_prevention`), `repeat_suggested` 及 `alert_id`。

### 5.2 规则层 R11：CAPA Issue Impact

- 在 `app/services/supplier_risk/rule_engine.py` 定义并注册新规则 `R11`。
- 提取 `SupplierRiskInput` 传进来的 `capa_incidents`。
- 打分逻辑（极简）：若无 incident 跳过；否则基础触发分 10，若 severity 为“致命/严重”加 10，若 repeat (取 `repeat_confirmed`，若为 null 取 `repeat_suggested` 并标 `provisional: True`) 为 True 加 10。

### 5.3 新增接口：`POST /api/capa/{report_id}/confirm-repeat`

用户主动确认系统自动推荐的“是否重复”值。

**Request**:
```json
{
  "repeat_confirmed": true
}
```

**逻辑**：
1. 验权：`canEdit('capa')`，及有效工厂/产品线验证（与 advance 一致）。
2. `FOR UPDATE` 获取 CAPA 实体以及对应的 `SupplierRiskAlert` (`linked_capa_id == report_id`)。若无预警则 404。
3. 修改预警对象：`rule_results._capa_input.repeat_confirmed = body.repeat_confirmed`。
4. **重算预警**：带上修改后的 input 重跑一遍规则引擎计算（R11 读到已确认值，移除 provisional）；计算出新的 `risk_score` 与 `risk_level` 并覆盖更新 alert。
5. **审计**：若 `risk_level` 与计算前相比产生变化（或即便不变化只标记变更了 confirmed），则往 `capa_eightd` 写入 `SUPPLIER_RISK_CHANGED` 日志，`changed_fields` 含 `old_level`, `new_level`, `repeat_confirmed`。
6. Commit 返回刷新投影后的 CAPA 详情。

## 6. 前端 UI

**`CAPADetailPage` 右侧 DataCard（关联 SCAR 之下）**

- **供应商风险预警**：展示 `linked_risk_alert` 数据。
- **展示**：`Alert_No` 或 `Risk Level` Tag (`High`, `Critical` 标红)。
- **操作区（当 `repeat_confirmed === null` 且用户有写权限时）**：
  - 显示警示文字：“系统判定该失效曾发生过 (关联单号: 8D-xxx)，请确认是否复发？”
  - 显示按钮 `[是，属复发]` `[否，非复发]`。
  - 点击按钮调用 `confirm-repeat`，触发 Loading，刷新当前视图。
- 无投影时显示“无”。

## 7. 测试验收 (E2E)

**文件**：`frontend/e2e/specs/m1-core/capa-story-supplier-risk-input.spec.ts`

**流程**：
1. **Seed 准备**：准备一个来料不良 8D，并准备一个归档的历史 8D（共享相同的 `fmea_node_id` 和 `supplier_id`）。
2. **工程师操作**：推进 D6 验证通过、填完 D7 预防内容后，点击 advance 到 `D7_COMPLETED`。
3. **断言触发**：UI 刷新后，右侧面板出现“供应商风险预警”投影，并弹出“请确认是否复发”以及历史单号，断言自动携带的 `repeat_suggested: true` 及正确关联单号。
4. **断言后台**：通过 /admin/logs 接口检查是否产生 `SUPPLIER_RISK_INPUT_SENT`，并检阅 changed_fields。
5. **工程师确认**：在面板点击 `[是]` (confirm-repeat=true)。
6. **断言更新**：按钮消失，确认态固化，断言是否触发 `SUPPLIER_RISK_CHANGED`。
7. （无需在 e2e 中断言最终的 risk_score 为精确数字，只判断链路走通即符合“不验评级算法”故事契约）。

## 8. 注意与风险点

1. **自动调用的异常吞吐**：这是首次在 `advance` 高敏感事务中附带跨域逻辑，且使用“异常 swallow”确保 8D 强韧性。务必确保吞掉的 Exception 不会导致 sqlalchemy session 进入 `invalid` 状态而令整个最外层事务崩溃（必要时使用嵌套事务/savepoint或确保在 commit_before 前的操作均为安全读。更好是先从外部算好，最后将生成的对象 add 进 session 并与 advance 一起提交）。
2. **规则 R11 配置存在性**：确保后端迁移文件能把此基础规则配置默认启用插入库，否则 `run_all_rules` 会因为没有此规则而报错。
3. **`_capa_input` 持久化策略**：`rule_results` 已经是 JSONB，需小心 Dict 深拷贝和更新时的 MutableDict 状态捕获，建议全量覆盖赋值 `alert.rule_results = new_results_dict`。
