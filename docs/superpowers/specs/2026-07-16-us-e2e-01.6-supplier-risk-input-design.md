**状态**: 设计定稿（审查修订版 v3）  
**子故事**: `docs/user-stories/US-E2E-01-capa-8d-closed-loop/US-E2E-01.6-supplier-risk-input.md`（定稿 v1，2026-07-08）  
**AI_REQUIRED**: false  
**Gap**: `docs/superpowers/specs/2026-07-08-us-e2e-01-gap-analysis.md` §01.6  

## 1. 目标

涉及供应商的来料不良 8D，在流转至 D7_COMPLETED 后，自动将其严重度、处置结果、是否重复发生传递给供应商风险模块，作为风险评级输入。评级结果（含自动评估建议与人工确认流）在 8D 侧可读可见并写审计，实现 8D 数据链路至供应商评级的单向可追溯。故事约定：仅验证输入传递、结构与关联是否通畅，**不验收风险评级算法的准确度**。

## 2. 已有基建（复用，不重造）

| 资产 | 用途 |
|---|---|
| `SupplierRiskAlert.linked_capa_id` | 现存 FK，保留为历史兼容字段；**新流程不再写入**（§4.4） |
| `SupplierRiskInput` / `run_all_rules` / `evaluate_supplier_risk` | 现存规则引擎打分、评估工作流（将抽 out-commit 核心，§5.3） |
| `embedding_sync_worker.py` + `main.py` 的 `_mes_outbox_loop` | **可靠 Outbox Worker 模板**：`SELECT … FOR UPDATE SKIP LOCKED` 认领 + `recover_stale` + `next_attempt_at`/`retry_count` |
| `capa_ppt_service._load_linked_risk_alerts` | 现存使用 `linked_capa_id` 反查预警的示例（PPT 侧后续可改读 inputs 表） |
| 现有 audit 事件约定 | 故事契约 `SUPPLIER_RISK_INPUT_SENT` / `SUPPLIER_RISK_CHANGED` |

## 3. 核心挑战与架构修正（基于两轮 Review）

最初设计试图直接把 CAPA 输入挂在每天按供应商聚合的 `SupplierRiskAlert` 上，导致粒度冲突、Upsert 语义不符、CAPA 缺 `supplier_id` 三大阻断。第二轮引入输入事实表解决了粒度，但留下消费者机制未定稿、confirm 事务非原子、R11 不被配置加载、低风险无投影等 8 项问题。本版（v2）逐项定死：

**架构主线**：
1. **CAPA 实体补齐**：`capa_eightd.supplier_id` FK（`RESTRICT`）+ 生命周期约束（§4.1, §4.5）。
2. **输入事实表**：新增 `supplier_risk_capa_inputs`（1:1 绑 CAPA），含评估快照字段，是 CAPA 侧投影的**唯一确定性来源**（§4.2）。
3. **可靠 Outbox 消费者**：套用 `embedding_sync_worker` 模板，`SELECT … FOR UPDATE SKIP LOCKED` 认领 + `attempt_count`/`next_retry_at`/`recover_stale`，`main.py` 启动 `_risk_input_outbox_loop`（§5.2）。
4. **事务原子性**：抽 `evaluate_supplier_risk_in_tx()`（不 commit），消费者与 confirm-repeat 共用，锁顺序固定（§5.3, §5.4）。
5. **R11 全家桶**：`RULE_REGISTRY` 注册 + `config.py` 解析范围扩到 R11 + Alembic 插入全局默认配置（category/weight/thresholds）+ seed（§5.5）。
6. **不可判定态**：`repeat_suggested` 改 `bool | null` + `repeat_detection_status`（matched/not_matched/unavailable）（§4.2）。

## 4. 数据模型

### 4.1 `capa_eightd.supplier_id`

- 增列 `supplier_id UUID NULL REFERENCES suppliers(supplier_id) ON DELETE RESTRICT`。
- API Schema（`CAPACreate`, `CAPAUpdate`, `CAPAResponse`）增加该字段。
- 前端建单/编辑表单增加供应商选择器（可空，针对非来料 8D）。

### 4.2 新增表：`supplier_risk_capa_inputs`

风险模块的输入事实表，1:1 绑 CAPA，**CAPA 侧投影的唯一确定性来源**。

```python
class SupplierRiskCapaInput(Base):
    __tablename__ = "supplier_risk_capa_inputs"

    input_id: Mapped[uuid.UUID] = mapped_column(UUID(as_uuid=True), primary_key=True, default=uuid.uuid4)
    capa_id: Mapped[uuid.UUID] = mapped_column(UUID(as_uuid=True), ForeignKey("capa_eightd.report_id", ondelete="CASCADE"), unique=True)
    supplier_id: Mapped[uuid.UUID] = mapped_column(UUID(as_uuid=True), ForeignKey("suppliers.supplier_id", ondelete="RESTRICT"))  # RESTRICT: 删供应商不得删质量追溯
    factory_id: Mapped[uuid.UUID] = mapped_column(UUID(as_uuid=True), ForeignKey("factories.id"))
    product_line_code: Mapped[Optional[str]] = mapped_column(String(20), nullable=True)
    created_by: Mapped[uuid.UUID] = mapped_column(UUID(as_uuid=True), ForeignKey("users.user_id"), nullable=False)  # advance 触发用户，worker 写 SENT 审计时复用

    severity: Mapped[str] = mapped_column(String(20), nullable=False)
    disposition: Mapped[Optional[str]] = mapped_column(Text, nullable=True)
    repeat_suggested: Mapped[Optional[bool]] = mapped_column(Boolean, nullable=True)  # null=无法判定
    repeat_detection_status: Mapped[str] = mapped_column(String(20), nullable=False)  # matched | not_matched | unavailable
    repeat_confirmed: Mapped[Optional[bool]] = mapped_column(Boolean, nullable=True)  # null=待确认
    matched_capa_nos: Mapped[list] = mapped_column(JSONB, nullable=False, server_default=text("'[]'::jsonb"))  # list[str]

    # ── 评估快照（CAPA 侧投影的唯一确定性来源，即便低风险无 alert 也可读）──
    evaluated_risk_level: Mapped[Optional[str]] = mapped_column(String(10), nullable=True)  # low/medium/high/critical
    evaluated_risk_score: Mapped[Optional[float]] = mapped_column(Float, nullable=True)
    evaluated_at: Mapped[Optional[datetime]] = mapped_column(DateTime(timezone=True), nullable=True)

    # ── Outbox 消费状态 ──
    status: Mapped[str] = mapped_column(String(20), nullable=False, default="pending")  # pending | processing | processed | error
    linked_alert_id: Mapped[Optional[uuid.UUID]] = mapped_column(UUID(as_uuid=True), ForeignKey("supplier_risk_alerts.alert_id", ondelete="SET NULL"), nullable=True)
    attempt_count: Mapped[int] = mapped_column(Integer, nullable=False, default=0)
    max_attempts: Mapped[int] = mapped_column(Integer, nullable=False, default=5)
    last_error: Mapped[Optional[str]] = mapped_column(Text, nullable=True)
    next_retry_at: Mapped[Optional[datetime]] = mapped_column(DateTime(timezone=True), nullable=True)
    locked_at: Mapped[Optional[datetime]] = mapped_column(DateTime(timezone=True), nullable=True)

    created_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), server_default=func.now(), nullable=False)
    updated_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), server_default=func.now(), onupdate=func.now(), nullable=False)

    __table_args__ = (
        Index("ix_risk_input_status_retry", "status", "next_retry_at"),  # worker 扫描索引
    )
```

### 4.3 现有预警表 `SupplierRiskAlert` 改动
- `rule_results` 结构保持 `List[dict]`，R11 结果按既有数组对象格式追加，**不**塞 `_capa_input`。
- `linked_capa_id` 见 §4.4。

### 4.4 `SupplierRiskAlert.linked_capa_id` 解耦
- 保留列，**新流程不再写入**（避免第二套关联冲突）。
- 仅为历史数据兼容（如 seed `SCAR-2026-001` 反向链）。
- **权威关联统一走** `supplier_risk_capa_inputs.linked_alert_id`（input → alert）。
- PPT 服务 `_load_linked_risk_alerts` 后续改读 inputs 表（本故事范围外 follow-up，标记 TODO 但不阻塞）。

### 4.5 `capa_eightd.supplier_id` 生命周期约束
- **创建/修改时**：供应商必须与 CAPA 同厂（`supplier.factory_id == capa.factory_id`），否则 400。
- **D7_COMPLETED 后禁止修改 supplier_id**：`update_capa` 在 `capa.status` 已达 `D7_COMPLETED` 及之后状态时，拒绝修改 `supplier_id`（D 步锁定，避免 input 与实际供应商脱节）。
- 若业务确需换供应商：需新建 8D，旧 input 保留为历史。

## 5. 服务契约与触发路径

### 5.1 `advance_capa` 内写 Outbox（`D7_COMPLETED`）

在 `capa_service.advance_capa` 内部，确定即将过渡到 `D7_COMPLETED` 时（severity/d4_root_cause/d7_prevention 均在 `capa` 对象），在 L640 `await db.commit()` **之前**：

1. **守卫**：`capa.supplier_id` 为空 → 跳过（非来料 8D）。
2. **重复探测**（精确匹配）：
   - 查 `CAPAEightD`：`supplier_id == capa.supplier_id` 且 `product_line_code == capa.product_line_code` 且 `fmea_node_id == capa.fmea_node_id` 且 `fmea_node_id IS NOT NULL` 且 `status IN (D8_CLOSURE, ARCHIVED)` 且 `report_id != capa.report_id`。
   - `fmea_node_id` 为空 → `repeat_suggested=None`, `repeat_detection_status="unavailable"`, `matched_capa_nos=[]`。
   - 有命中 → `repeat_suggested=True`, `repeat_detection_status="matched"`, `matched_capa_nos=[hit.document_no ...]`。
   - 无命中 → `repeat_suggested=False`, `repeat_detection_status="not_matched"`, `matched_capa_nos=[]`。
3. **入 inputs 表**：`db.add(SupplierRiskCapaInput(capa_id=..., supplier_id=..., severity=capa.severity, disposition=capa.d7_prevention, repeat_suggested=..., repeat_detection_status=..., matched_capa_nos=..., repeat_confirmed=None, status="pending", attempt_count=0, max_attempts=5, created_by=user_id))`。
4. **审计**：`db.add(AuditLog(table_name="capa_eightd", record_id=capa.report_id, action="SUPPLIER_RISK_INPUT_QUEUED", operated_by=user_id, factory_id=capa.factory_id, changed_fields={capa_id, supplier_id, severity, repeat_suggested, repeat_detection_status, matched_capa_nos（UUID str 化）}))`。
   - **注**：此时记录 `QUEUED` 而非 `SENT`；消费成功后才写故事要求的 `SUPPLIER_RISK_INPUT_SENT`（§5.2 step 5）。

**不调用任何规则引擎**，纯插行 + 审计，与 advance 同事务 commit。advance 永不因风险模块故障失败。

### 5.2 可靠 Outbox 消费者

新建 `backend/app/services/supplier_risk/risk_input_worker.py`，套 `embedding_sync_worker.py` 模板：

1. **`recover_stale_inputs(db)`**：`status='processing' AND locked_at < NOW() - INTERVAL '10 minutes'` → reset `pending`, `locked_at=NULL`。
2. **`claim_batch(db, batch_size)`**：
   ```sql
   UPDATE supplier_risk_capa_inputs
   SET status='processing', locked_at=NOW(), attempt_count=attempt_count+1
   WHERE input_id IN (
     SELECT input_id FROM supplier_risk_capa_inputs
     WHERE status='pending' AND (next_retry_at IS NULL OR next_retry_at <= NOW())
     ORDER BY next_retry_at NULLS FIRST
     LIMIT :batch_size FOR UPDATE SKIP LOCKED
   ) RETURNING ...
   ```
3. **`process_one(db, claimed_input)`**（**独立事务 + 重新锁**，因 `claim_batch` 已 commit 释放行锁）：
   1. 新开事务：`SELECT supplier_risk_capa_inputs ... WHERE input_id=claimed FOR UPDATE`（重新锁，防与 confirm 并发）。
   2. **显式注入 trigger_input**（§5.3 关键修正）：`incidents = _gather_capa_inputs(...)` 读 processed/error 历史 + **追加本次 `trigger_input`**（`replace_or_append_by_input_id`，确保首条 input 在 processing 状态时 R11 也能消费它）。
   3. 调 `evaluate_supplier_risk_in_tx(db, input.supplier_id, input.product_line_code, force_update=True, trigger_input=input)`。
   4. 成功：回填 `status='processed'`, `evaluated_risk_level/score/evaluated_at`, `linked_alert_id`，写 `SUPPLIER_RISK_INPUT_SENT` 审计（§5.7 字段级契约），`db.commit()`。
   5. **失败**：先 `db.rollback()`（回滚 evaluate 半截事务），再以**新事务** `UPDATE ... SET status='error', last_error=...`；若 `attempt_count < max_attempts` 则回 `status='pending'` + `next_retry_at=NOW()+指数退避(2^attempt_count 秒)`，`db.commit()`。不阻断其他 input。
4. **幂等键**：`capa_id` UNIQUE（§4.2）保证同一 CAPA 不会有多条 input。
5. **启动**：`main.py` 仿 `_mes_outbox_loop` 加 `_risk_input_outbox_loop`（每 30s），启动时先 `recover_stale_inputs` 再 `claim_batch`。

### 5.3 `evaluate_supplier_risk_in_tx`（事务内核心，不 commit）

抽自现有 `evaluate_supplier_risk`，**不** `db.commit()`：

```python
async def evaluate_supplier_risk_in_tx(db, supplier_id, product_line_code=None, *, force_update=False, trigger_input=None):
    # 1. gather data (含新 _gather_capa_inputs，§5.5)
    # 2. **关键修正**：若 trigger_input 非 None，用 replace_or_append_by_input_id 把它注入 incidents
    #    （claim_batch 已把当前 input 改 processing，_gather_capa_inputs 读不到它，必须显式注入）
    # 3. run_all_rules (含 R11，消费注入后的 incidents)
    # 4. calculate_risk_score
    # 5. _upsert_alert(..., force_update=force_update)  # §5.6
    # 6. 若 trigger_input 非 None：回填 evaluated_risk_level/score/evaluated_at + linked_alert_id 到 input
    # 7. return (alert, risk_score)  # 不 commit，由调用方统一 commit
```

- 消费者：`process_one` 调它 → 自己 commit。
- `confirm-repeat` API：调它 → 同事务写审计 → commit。
- 既有 `evaluate_supplier_risk`（含 commit）保留给启动初始化评估，内部改为调 `_in_tx` 后 `db.commit()`。

### 5.4 `POST /api/capa/{report_id}/confirm-repeat`

**权限**：`canEdit('capa')` AND `canEdit('supplier_risk')` + 工厂/产品线校验。

**Request**: `{ "repeat_confirmed": true | false }`

**逻辑**（单一事务，锁顺序固定）：
1. `SELECT capa_eightd ... FOR UPDATE`（锁 1：capa）。
2. `SELECT supplier_risk_capa_inputs ... WHERE capa_id=report_id FOR UPDATE`（锁 2：input）；无行 → 404。
3. **状态门**：`input.status != 'processed'` → **409 Conflict**（pending/processing/error 不允许 confirm；worker 与 confirm 不会并发重算同一 input）。
4. 校验 `input.supplier_id` 与 `capa.supplier_id` 一致（防 supplier_id 生命周期篡改）。
5. **先读 old_level（重算前）**：`old_level = input.evaluated_risk_level`。
6. `input.repeat_confirmed = body.repeat_confirmed`。
7. 调 `evaluate_supplier_risk_in_tx(db, input.supplier_id, input.product_line_code, force_update=True, trigger_input=input)`。
8. **后读 new_level（重算后）**：`new_level = input.evaluated_risk_level`。
9. `db.add(AuditLog(..., action="SUPPLIER_RISK_CHANGED", changed_fields={old_level, new_level, repeat_confirmed, alert_id}))`。
10. **统一 `db.commit()`**（唯一 commit 点）。失败整体回滚。
11. 返回刷新投影的 `CAPAResponse`。

### 5.5 R11 全家桶

1. **`rule_engine.py`**：定义 `R11` 规则类，消费 `SupplierRiskInput.capa_incidents`。`_gather_capa_inputs` 读 `supplier_risk_capa_inputs` 表，该 supplier + 同 `product_line_code`，`status IN ('processed', 'error')`，`created_at >= NOW() - INTERVAL '90 days'`；**`trigger_input` 由 `evaluate_supplier_risk_in_tx` 显式注入**（§5.3 step 2），不依赖 gather 读到 processing 记录。
2. **incident 选择（确定性）**：
   - **窗口**：近 90 天（`created_at >= NOW() - 90d`）。
   - **严重度排序**：致命 > 严重 > 一般 > 轻微（映射到数值 4/3/2/1，取最高）。
   - **同级 tie-break**：`created_at DESC`，再 `input_id ASC`。
   - **trigger_input 必包含**：即使不在 90 天窗口或状态非 processed，也强制注入 incidents 列表参与评分。
   - **error 记录**：包含（保留为历史 incident，但 detail 标注曾失败）。
3. **打分**：取按上排序的最高严重度 incident；severity 映射（致命/严重 → 高分，一般 → 中，轻微 → 低）；repeat 取 `repeat_confirmed`，为 null 取 `repeat_suggested`（null→按 false），`provisional` 标记仅在 `repeat_confirmed is None` 时置 true。`disposition` 只入 `detail` 文本，**不**计分。
4. **`RULE_REGISTRY`**：注册 R11。
5. **`config.py`**：`get_effective_configs` / `get_effective_configs_batch` 的规则遍历范围从 R01–R10 扩到 R01–R11。
6. **Alembic（可执行数据来源）**：`SupplierRiskConfig.factory_id`/`updated_by` 均非空，不能写 `factory_id=<group>` 字面量。从现有全局 R01 配置复制 `factory_id` + `updated_by`：
   ```sql
   INSERT INTO supplier_risk_configs
     (config_id, rule_id, enabled, thresholds, weight, supplier_id, factory_id, category, product_line_code, updated_by, updated_at)
   SELECT gen_random_uuid(), 'R11', true, '{}'::jsonb, 1.0, NULL, factory_id, 'quality', NULL, updated_by, NOW()
   FROM supplier_risk_configs
   WHERE rule_id = 'R01' AND supplier_id IS NULL AND product_line_code IS NULL;
   ```
   - **找不到基准 R01 配置时**：迁移 `raise RuntimeError`（中止，人工先建 R01 基准），不静默跳过。
   - **多工厂**：若 R01 有多工厂的全局配置（supplier_id IS NULL），逐工厂复制一份 R11。
   - **downgrade**：`DELETE FROM supplier_risk_configs WHERE rule_id = 'R11'`。
7. **seed**：`seed.py`/`seed_e2e.py` 同步插 R11 默认配置（同样从 R01 复制或直接写已知 factory_id）。
8. **category/weight**：`category='quality'`（与 R01–R05 同类，纳入 `quality_score` 加权）, `weight=1.0`。

### 5.7 审计事件字段级契约

| action | record_id | operated_by | factory_id | changed_fields（UUID 一律 str，JSON 可序列化） |
|---|---|---|---|---|
| `SUPPLIER_RISK_INPUT_QUEUED` | capa.report_id | user_id | capa.factory_id | `capa_id`, `supplier_id`, `severity`, `disposition`, `repeat_suggested`, `repeat_detection_status`, `matched_capa_nos`（list[str]） |
| `SUPPLIER_RISK_INPUT_SENT` | capa.report_id | worker 系统用户或触发用户 | input.factory_id | `capa_id`, `input_id`, `supplier_id`, `severity`, `disposition`, `repeat_suggested`, `repeat_confirmed`, `repeat_detection_status`, `matched_capa_nos`, `risk_level`（= evaluated_risk_level）, `alert_id`（可 null） |
| `SUPPLIER_RISK_CHANGED` | capa.report_id | user_id | input.factory_id | `old_level`, `new_level`, `repeat_confirmed`, `alert_id` |

- **`operated_by`**：QUEUED/CHANGED 由实际用户；SENT 由 worker 写——若 worker 无用户上下文，用触发 advance 的 `user_id`（advance 时记录到 input 行的 `created_by`，worker 读取复用），避免 NULL 违反 `AuditLog.operated_by` 非空约束。
- **JSONB 序列化**：所有 UUID 字段 `str(...)`（对齐 01.5 / `scar_service`）；`matched_capa_nos` 本就是 `list[str]`。

### 5.6 `_upsert_alert` 加 `force_update`

现有 `_upsert_alert` 仅升级覆盖、降级/同级跳过、低风险不建。增可选 `force_update=False`：
- `force_update=True`：无论升降级，覆盖 `risk_level/score/quality_score/...`；低风险无既有 alert 时**也建一条** `alert_type='routine'`（保证 confirm 后 CAPA 可投影）。
- 消费者与 confirm-repeat 传 `force_update=True`；既有定时评估传 `False`（行为不变）。

- `supplier_risk_input` 为 null → 无。
- 非 null → 显示 `evaluated_risk_level` Tag（low 灰 / medium 橙 / high 红 / critical 深红），或 `status` 非 `processed`（pending/processing/error）时显示「评估中」/「评估失败」。
- **确认按钮门控**（与后端 409 一致）：仅当 `status === 'processed' && repeat_confirmed === null` 且 `canEdit('capa') && canEdit('supplier_risk')` 时显示 `[是，属复发]` `[否，非复发]`。`status` 非 processed 时**禁用按钮**（防 worker 与 confirm 并发）。
- `repeat_confirmed === null`（且 processed）时按 `repeat_detection_status` 分态显示提示：
  - `matched`：「系统判定曾复发（关联: 8D-xxx），请确认。」
  - `not_matched`：「系统未发现复发记录，请最终确认。」
  - `unavailable`：「未关联 FMEA，无法自动判定，请人工确认是否复发。」
- `repeat_confirmed !== null` → 固化显示「已确认：复发 / 非复发」。

### 6.3 E2E (`capa-story-supplier-risk-input.spec.ts`)

1. Seed：带 `supplier_id` + 关联 FMEA 的 8D + 同 FMEA 归档历史 8D + R11 默认配置（从 R01 复制）。
2. engineer 推进至 `D7_COMPLETED`。
3. **轮询** input `status` 至 `processed`（worker 30s 周期，测试可触发或等待）。
4. 详情断言：`supplier_risk_input.repeat_suggested === true` + `matched_capa_nos` 含历史单号 + `evaluated_risk_level` 非空（含 low 情形也可见）。
5. 后台 `/admin/logs/audit` 断言 `SUPPLIER_RISK_INPUT_SENT`，`changed_fields` 含 `severity`/`disposition`/`risk_level`/`alert_id`。
6. 有权角色点 `[是]`（confirm=true）。
7. 按钮消失固化；断言 `SUPPLIER_RISK_CHANGED` 且 `changed_fields` 含 `old_level`/`new_level`/`repeat_confirmed`，且 `old_level` ≠ 重算后值（验证 §5.4 step 5/8 读序正确）。
8. 消费者幂等：重复触发同 CAPA 不产生第二条 input（`capa_id` unique）。
9. **409 门控**：在 input 仍 `pending`/`processing` 时调 confirm → 409（worker 与 confirm 不并发）。
10. **首条 input 注入**：供应商首条 CAPA input 处于 processing 时，R11 必须消费它（断言 `evaluated_risk_level` 反映该 incident，非空列表降级）。

## 7. 风险与注意

- **R11 配置必须随迁移插入**，否则 `run_all_rules` 加载不到 R11 → input 永远停在 error。
- **`evaluate_supplier_risk_in_tx` 不 commit**：消费者与 confirm 共用，任一调用方忘记 commit 会导致脏读；单测须断言 commit 发生在调用方。
- **锁顺序**：confirm-repeat 固定 capa → input，与 advance（只锁 capa）不冲突。
- **worker 启动**：`_risk_input_outbox_loop` 需在 `main.py` startup 注册；e2e 环境需 worker 运行才能让 pending → processed，测试若不便等 30s 可加测试专用触发端点或缩短周期。
- **`linked_capa_id` 历史兼容**：不删列不写新值，PPT 服务 follow-up 改读 inputs 表（本故事不强制）。
