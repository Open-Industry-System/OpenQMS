## 1. 设计结论

**审核的是已经实施的措施及其结果，不是待验证的候选，也不是尚未执行的措施方案。**

业务流程为：

1. D4 分析候选原因，开展现场验证，确认经验证的根因。
2. D5 制定纠正措施。
3. D6 实施措施并记录效果验证结果。
4. D7 完成预防复发及相关文档工作，按现有规则通过 D8 文档门禁。
5. 在现有 D8 待审批节点，集中审核正式根因、实际措施、实施记录及效果验证材料。
6. 通过后结案；不通过则说明理由，按既有回退路径补充、整改后重新提交。

D4、D5、D6 不新增人工批准节点。工程师不必为每份候选、每次修改或每条验证记录单独申请审批。必要的权限、验证条件、文档检查和操作留痕仍然保留。

## 2. 审核位置与现有状态机

复用现有状态路径，不另建一套与 CAPA 并行的审批状态机：

```text
D4_ROOT_CAUSE
  -> D5_CORRECTION
  -> D6_VERIFICATION
  -> D7_PREVENTION
  -> D7_COMPLETED
  -> D8_GATE_PENDING
  -> D8_APPROVAL_PENDING
       -> D8_CLOSURE       审核通过
       -> D7_PREVENTION    驳回整改
```

各阶段的职责如下：

| 阶段 | 处理内容 | 是否新增人工审批 |
|---|---|---|
| D4 根因分析 | 候选讨论、现场验证、排除错误原因、确认根因 | 否；保留当前根因必须经验证的条件 |
| D5 永久措施 | 制定和完善措施方案 | 否；不把方案保存变成实施前审批 |
| D6 实施验证 | 记录实际实施情况及效果验证结果 | 否；结果材料纳入最终审核 |
| D7 预防复发 | 完成既有预防措施记录、关联与追溯工作 | 否；保留现有完成条件 |
| D8 文档门禁 | 检查受影响受控文档的更新情况 | 保留现有门禁，不另加一轮候选人工审批 |
| D8 待审批 | 对正式报告及措施实施结果作集中判断 | 复用现有审批节点 |

“集中审核”不等于取消所有业务门禁。现有文档延期仍不能直接放行结案；FMEA、控制计划自身的受控审批也不因 CAPA 集中审核而被绕过。

现有状态机见 `backend/app/state_machines/eightd_state.py`；审批壳和文档门禁分别归属 [US-E2E-01.3](../../user-stories/US-E2E-01-capa-8d-closed-loop/US-E2E-01.3-d4-verification-d7-node-action.md)与 [US-E2E-01.7](../../user-stories/US-E2E-01-capa-8d-closed-loop/US-E2E-01.7-doc-update-gate.md)。

## 3. D4 不审批，但仍须验证

D4 的候选、验证结论和最终结果审核是三件不同的事：

- **候选原因**：供分析和现场验证，可以被修改、排除或替换，不生成独立审批申请。
- **根因验证**：记录验证方法、结果、证据引用、验证人和时间。通过验证才能确认当前根因；验证失败可以继续分析和验证，不需要审核人逐次批准。
- **结果审核**：措施实施后，在 D8 对整份正式材料集中审核，不用它代替现场验证。

保留现有 D4→D5 条件：当前 `d4_root_cause` 必须与 `conclusion=passed` 的根因验证记录匹配，不能修改根因后继续使用不匹配的旧验证记录。没有经过验证的原因，不能仅凭“审核通过”变成已确认根因。

既有 [R4b-1 脱敏预览](2026-10-05-capa-d4-text-redaction-foundation-design.md)继续独立使用：它是短期、只读的受限候选，不因查看、修改显式词或现场验证而自动提交审批，也不自动写入正式 CAPA 根因或措施。

## 4. 最终审核看什么

审核对象是当前报告中的正式业务材料，而不是脱敏候选快照：

| 材料 | 审核关注点 | 当前依据 |
|---|---|---|
| 正式根因 | 原因是否有验证支持，是否与当前报告一致 | `d4_root_cause` 及 `CapaRootCauseVerification` |
| 实际措施 | 最终采取了什么措施，是否针对已验证根因 | `d5_correction` 及正式实施说明 |
| 实施和效果验证 | 实施了什么、结果如何、有哪些支持材料 | `d6_verification` 及合法证据引用 |
| 预防复发 | 后续预防和追溯工作是否按现有规则完成 | `d7_prevention`、既有 D7 node-action |
| 受控文档 | 相关 FMEA、控制计划是否通过现有更新门禁 | 既有文档分析、审核决策与版本记录 |
| 结案结论 | 是否可以接受实施结果并关闭报告 | 现有 D8 审批动作及审计 |

本轮审核覆盖 D4/D5/D6/D7 正式字段、根因验证记录集合及其方法/结果/结论/证据引用、D7 node-action，以及所依据的关联和文档版本。批准后，不能在保留原结案状态和批准记录的同时改写这些材料。既有 `d8_closure` 结案后补充报告不作为这一轮已审核结论，具体边界见 §5.4。

提交材料必须能区分“计划采取的措施”和“实际已经实施的措施”。只有方案文本、没有实施及效果材料时，不能将其标成实施结果已审核。

当前 `d5_correction`、`d6_verification` 等主要是文本字段，不代表系统已经具备结构化实施证据或自动判断效果的能力。审核人需要核对实际材料；不能仅因文本非空、状态已到 D6，或 AI 给出积极评价，就宣称措施已实施且有效。

D7 node-action 继续遵守已定稿故事的边界：目前的 pending 记录用于记录和追溯，不等同于已经执行或验证。本次不新增“全部 D7 node-action 都必须变成 verified 才能结案”的条件，也不自动修改 FMEA 图或伪造执行证据。

## 5. 提交、审核与整改

### 5.1 提交

工程师完成措施实施和结果记录，完成既有 D7 工作，并通过 D8 文档门禁后，沿现有路径进入 `D8_APPROVAL_PENDING`。

本次提交的是整份正式报告及结果材料，不是把 D4、D5、D6 各自提交一遍。此前保存和修改过程资料不产生新的审批任务。

结果提交人是实际将材料提交到待审批节点的当前用户，不应直接等同于报告的 `created_by`、某条根因的验证人或最早生成候选的人。沿用状态迁移的责任记录，不引入原方案的 D4 候选申请人。

### 5.2 审核通过

审核人检查当前材料及其来源，认可实际措施和结果后，调用现有审批入口进入 `D8_CLOSURE`。审批人、时间、结果和对应状态变化必须可追溯。

通过表示接受本轮审核覆盖的正式材料并结案；这份批准不能自动覆盖结案后的新增或更正内容。它不表示事前批准过措施执行，不替代现场验证，也不代表所有资料已降敏或可以外发。

### 5.3 审核不通过

沿现有路径从 `D8_APPROVAL_PENDING` 返回 `D7_PREVENTION`，必须填写驳回理由。工程师补充材料或整改后，重新完成必要检查并提交审核，不能沿用旧决定直接结案。

驳回不是撤销已实施措施，也不自动回滚现场操作、FMEA 文档或业务数据。涉及重新实施或再次验证时，应真实记录新增活动，不能靠改一个状态声称已经完成。

现有审批壳只提供返回 D7 的驳回边，不提供从待审批状态直接跳回 D4、D5、D6 的任意回退。若整改必须重新打开早期阶段，应另行设计合法的返工路径；本次不通过直接改状态绕过状态机。

### 5.4 结案及归档后的修改边界

报告处于 `D8_CLOSURE` 或 `ARCHIVED` 时，本轮已审核材料禁止原位修改；EDIT、APPROVE、ADMIN 权限都不豁免这一业务约束。保护至少覆盖：

- `d4_root_cause`、`d5_correction`、`d6_verification` 和已冻结的 `d7_prevention`。
- 根因验证记录的新增、修改和删除，包括根因文本、方法、结果、结论、`is_verified`、验证人/时间、证据清单及 `source_ref`；不能用新增记录或清空字段改变已审集合。
- D7 node-action 及审核依据的 CAPA 关联、证据引用和已绑定文档版本。禁止改绑、替换或删除引用来变相更换已审依据，也不允许通过删除报告级联清除这些已审记录。

上述规则覆盖普通编辑、建议采纳/追加、验证记录写入、关联维护、D7 确认/自动填充，以及已有批量、导入或内部工具中实际能写到这些材料的路径。只隐藏按钮、只约束普通 PUT 或只在某一 API 校验都不够；直接调用业务服务也必须受保护。本片不会因此新增任何写入口。

需要更正已审核核心材料时，必须另走能保留原材料、原决定和新旧关系的受控修订，并重新审核；不得直接解除冻结、重置状态后覆写，或继续展示原批准已覆盖新内容。本片不实现受控修订流程，因此在该流程另行设计、获批并实现之前，这类更正请求应拒绝。

不冻结 FMEA、控制计划等来源模块未来的正常修订。CAPA 应保留审核当时使用的受控文档版本和证据身份，不能把来源的“最新版本”静默替换成历史审核依据；冻结一个可变链接本身也不能证明其背后的内容不可变。

既有 `D8_CLOSURE` 允许补写 `d8_closure` 的例外仅保留为结案后未审补充，不能用于更正上述核心材料。补充报告必须明确显示“结案后补充，未纳入本次审核”，保留修改人和时间，不得作为已审核结论或反向改写已审字段；审核视图和派生结果也不能把它标为已审依据。`ARCHIVED` 对该字段的既有冻结继续保留。本版不把补写报告变成受控修订的替代入口。

## 6. 角色、权限与本人审批

### 6.1 角色不是固定审批人名单

继续使用角色的 CAPA 模块等级，不新增名为“候选申请人”或“候选批准人”的角色：

| 操作 | 权限原则 |
|---|---|
| 查看报告 | 当前 CAPA VIEW 及既有对象范围 |
| 编辑分析、措施、验证等业务材料 | 当前 CAPA EDIT 及对应阶段允许的操作 |
| 提交到待审批节点 | 当前 CAPA EDIT，并满足既有阶段与门禁条件 |
| D8 审批通过或驳回 | 当前 CAPA APPROVE，并满足当前对象范围 |
| 配置角色模块权限 | 既有 `permission_mgmt` ADMIN 权限 |

APPROVE、ADMIN 等级可以覆盖较低等级要求，但不能凭角色名称、历史权限或前端按钮判断当前资格。提交时校验提交人，审批时校验审批人；不能仅因原分析人员离职就删除正式质量记录，也不能因此向其他人扩大读取权限。

角色和工厂范围可在现有 `/admin/users` 页面分配。角色模块等级由现有 `/api/admin/roles`、`/api/admin/roles/{role_key}/permissions` 接口管理；目前没有独立的角色权限矩阵页面。接口修改是整组权限替换，不能仅提交 CAPA 一项而覆盖其他模块配置。产品线范围仍使用既有分配机制。

### 6.2 不把原候选自批规则搬到 D8

原方案“申请人一律不得自批”的限制属于被撤回的 D4 候选流程，不自动成为现有 D8 的新增规则。

当前 D8 接口按 CAPA APPROVE 等级校验，没有实现原候选方案的“申请人不能批准本人申请”判断；Agent 权限辅助函数中的禁止自批也不能被当成 D8 已有的实现。本次修订不改变该行为，不新增自批开关，也不将用户对审核时点的确认解释成已批准某种自批制度。

若后续采用“管理员配置允许本人审批、审批时警告确认”的选项，应仅针对这次正式结果审核单独确认策略。它仍不能赋予 EDIT 用户审批权限，不能只靠前端弹窗，也不能把本人审批显示为独立复核。该选项不再放在 D4 候选页面，本次不据此扩展通用审批配置平台。

## 7. 资料权限、分类与保留

### 7.1 结果审核不等于资料发布

正式报告仍通过现有 CAPA 业务入口受控读取，不新增独立的“已发布候选库”、共享 URL、静态文件或批量正文导出。

CAPA 本身使用当前角色、工厂和产品线范围。打开关联 FMEA、控制计划或其他证据时，仍按来源模块权限访问；若新增聚合审核视图，也不能借 CAPA VIEW 泄漏无权来源的正文、摘要或数量。审核人无法核对必要来源时，不能把该材料当成已经核对通过的依据。

审批通过不新增降敏、插件 grant 或模型外发许可，不改变既有 Agent baseline DENY。既有结案知识沉淀、横向扩散等服务按原业务与授权边界运行；本片不因此增加新的正文投递或绕过既有交付控制。

### 7.2 正式质量记录不适用候选的 7 天期限

原方案“从候选提交起保存正文和备注 7 天”的规则随候选审批流程撤回，不能应用到正式根因、实施记录、验证证据、驳回理由或结案审计。

本次不新设正式 CAPA 质量记录的保留年限，也不执行清理。正式记录沿用既有存储和归档规则；如需组织级保留期限、销毁或备份政策，应另行确定，不能从临时候选期限推导。

R4b-1 的 30 秒只读预览和 R4b-2 的任务私有附件保留策略保持不变。任务附件不会自动成为正式验证证据，也不能因为文件暂时可下载，就认为它已满足正式证据的长期留存要求。本次不解析附件、不接通新证据上传或复制通道。

租户 generation 仍用于阻断过期请求，不是删除正式记录、审批历史或附件的依据。保留数据的普通维护不能被解释为销毁授权。

## 8. 审核版本、并发与审计

旧待审批数据若缺少进入审批的审计，使用由服务端租户身份和报告 ID 派生的固定兼容轮次，不把更新时间或维护元数据作为轮次依据。此规则由用户于 2026-10-25 明确确认；正常重新提交后使用新的入审计身份，实际核心材料或来源变化仍须使所见版本失效。GET 不补写审计或新轮次，也不需要为此迁移数据库。

集中审核必须保证“所见即所审”：审核人看到的正式根因、措施、结果及必要证据，在决定时仍是同一版。不能只比较 CAPA 主表状态，而忽略验证记录或文档版本已变化。批准后还须按 §5.4 保护已审材料，不能让新内容继续沿用旧批准。

所有触及已审材料的写服务必须使用同一锁顺序：先检查当前权限与对象范围，再锁定 CAPA 父行并刷新，锁后重新检查当前状态、权限与范围，确认允许修改后才锁子记录和执行写入。审批持有同一父行锁直到事务结束；验证记录服务不能先锁子行再补锁父行。终态写保护必须在采纳幂等快速返回、子记录变更、flush、成功审计、embedding 或 outbox 等副作用之前执行，不能只在首次读取时检查。

若修改请求先读取到可编辑状态，随后等待审批事务的锁，锁后必须看到最新的 `D8_CLOSURE`/`ARCHIVED` 并拒绝修改。对已授权调用方统一返回固定冲突 `409 CAPA_REVIEWED_CONTENT_LOCKED`；事务不能留下文本变化、新增/删除的子记录、验证结论变化或新的成功写入副作用。反之，若修改先提交，审批必须识别其所见材料已变更，不得用旧画面批准。

设计要求如下：

- 提交和审批都先检查当前身份、权限及对象范围；锁后刷新状态并重查，不使用 ORM identity map 中的旧值。
- 保留现有报告行锁、显式状态迁移和批准/驳回权限检查，不能将 EDIT 用户的普通推进请求变成审批。
- 审阅期间关键材料变化时，旧画面不能直接批准；须重新加载并核对，必要时整改后重新提交。
- 当前根因仍须有匹配的通过验证记录。自然语言措施与效果是否充分，由审核人结合材料判断，不宣称系统已能自动证明。
- 文档门禁继续使用其既有新鲜度、版本及阻断规则，不能把历史通过当作永久有效。
- 同一待审批轮次的并发批准、驳回或重复请求不能生成两次有效决定、重复结案副作用或重复成功审计。提交失败不能提前显示已结案。

**设计期说明（历史）**：这些是后续实现与验收要求，不是对当前代码已具备完整审核版本绑定能力的声明。实现应优先复用现有报告、验证记录、文档版本和审计，不预设新建候选快照表或第二套审批账本；必要的版本条件应在实施计划中明确到接口与测试。

沿用 `TRANSITION`、`D8_APPROVED`、`D8_REJECTED` 等既有审计，记录实际操作人、时间、状态与决定。业务中的驳回理由按现有正式记录处理，不再作为 7 天候选 note。不得为追踪版本而将整份原文、候选、证据正文或任意请求 JSON 复制进新的通用审计字段。

## 9. 页面与操作方式

D4 保持“分析—验证—确认根因”的工作区，不新增“提交候选审核”“批准候选发布”“候选驳回”按钮或待审批列表。

D5、D6 用于记录措施及实际结果，不因为保存、修订或完成一次验证就要求审批人放行。界面应明确区分方案、实施情况和验证结果，不能将“已填写”显示成“已批准”或“已验证有效”。

在现有 D8 待审批页面集中展示正式根因、验证材料、实际措施、实施和效果结果，以及现有 D7/文档门禁信息。审核人从这里批准结案或填写理由驳回，不再要求先批准一份脱敏候选。

APPROVE 用户与 EDIT 用户的操作入口分开。结案、归档后的已审核核心材料只读，不显示编辑、采纳、验证新增/修改/删除等入口；保留的结案后补充报告单独标明未纳入本次审核，不能混用“已审核”标记。隐藏按钮不能替代后端鉴权和终态写保护；身份、租户、报告或权限变化时，旧审核请求和旧页面状态不能影响新身份。网络中断时显示结果未确认，先重查实际状态，不自动重放批准或触发第二次结案。

不把原预览的 30 秒展示期强加到普通 CAPA 正式报告页面，也不因审批将资料存入新的浏览器持久缓存。既有受限预览自身的失效和敏感词清空要求继续保留。

## 12. 验收要求

以下是修订后的验收范围，不代表本轮已经执行：

1. **过程不逐步审批**：具备当前 EDIT 的工程师可按现有规则分析、修改、验证和推进；D4 不出现候选申请/发布审批，D5/D6 不新增人工放行节点。
2. **验证不被取消**：未通过验证或与当前根因不匹配的记录，不能放行 D4→D5；失败可继续验证，不要求逐次审批。
3. **审核实际结果**：D8 展示已验证根因、实际措施和实施/效果材料，不能把只有计划或非空文本的材料自动认定为实施有效；D7 pending 记录不能伪装为已执行。
4. **复用唯一审批节点**：通过既有 D8 待审批入口批准或驳回；保留 D7、文档版本/延期阻断规则，不增加 D4 候选批准前置条件。
5. **权限与范围**：当前 CAPA EDIT 不能代替 APPROVE；跨租户、工厂、产品线及无权来源不能借审核视图越权。自批策略没有被悄悄新增、放宽或从 Agent 辅助函数移植到 CAPA。
6. **驳回与重提**：理由必填，按合法边返回 D7，整改后重走必要检查；不恢复旧批准，不回滚已经实施的现场措施，不直接改状态跳到早期阶段。
7. **所见版本一致**：关键材料或源版本变化后，旧审核画面不能批准。用真实独立数据库会话验证锁等待中变更、批准/驳回竞争、重复请求和提交失败，不能用 flush-only 或同一 identity map 模拟事务成立。
8. **结案后不可覆写**：分别在 `D8_CLOSURE` 和 `ARCHIVED` 下，从普通编辑、建议采纳、验证新增/修改/删除、D7 写入和关联维护等实际入口尝试改变已审材料，包括追加、清空、换引用、批量或直接服务调用；均须拒绝且材料不变。EDIT、APPROVE、ADMIN 都不豁免。对现存幂等采纳返回路径，也要证明不能绕过终态检查或产生新副作用。
9. **审批与修改竞态**：以真实独立会话和 Events 控制“修改已读旧状态→审批持锁并提交→修改获得父锁”的顺序，证明修改锁后失败且没有文本、验证、子记录或成功审计/outbox/embedding 变化；反向顺序证明修改先提交时旧审核版本不能批准。验证记录同时覆盖先锁父行、再锁子行的统一顺序。
10. **正式记录留存与补充边界**：根因、措施、验证、驳回及审批历史不执行原候选 7 天清理；原短期预览及任务附件策略不变，普通 generation 变化不误删数据。结案后补充报告明确标为未纳入本次审核，不能覆盖核心材料或派生成已审依据；归档后仍受其原有冻结限制。
11. **真实界面**：使用现有员工鉴权和已安装 Chromium，验证工程师完成前期过程后集中提交、审核人核对结果并批准或驳回，以及身份切换、失权、旧响应和网络结果不确定的处理。批准后核心材料只读；绕过 UI 直接请求仍受写保护。不伪造审批结果或来源权限。
12. **回归与完成证据**：后续实施后运行相关后端、前端、现有 CAPA 用户故事以及 R4a/R4b-1/R4b-2 受影响回归，再执行最终 `make check`、文档/差异检查并清理自有资源。历史 R4b-2 的 2999 项通过不能代替本片验证。
