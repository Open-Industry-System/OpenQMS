# US-E2E-01.7 D8 文档更新审核门禁设计

**日期**: 2026-07-13
**范围**: US-E2E-01.7 子故事「D8 关闭前文档更新审核门禁」
**依据**:
- 子故事: `docs/user-stories/US-E2E-01-capa-8d-closed-loop/US-E2E-01.7-doc-update-gate.md`（v1，2026-07-08）
- 状态机基座: `docs/superpowers/specs/2026-07-08-us-e2e-01.3-state-machine-refinement-design.md`（01.3 已就绪两条 edge + per-edge gate 占位）

## 目标

在 8D 状态机的 `D8_GATE_PENDING→D8_APPROVAL_PENDING` 边接入文档更新审核门禁：D7 完成后系统（经显式 POST）用 LLM 分析受影响受控文档（控制计划、FMEA），D8 关闭审批前自动审核这些文档的版本更新与关键点覆盖情况，未通过则阻断推进；延期记录待办但仍阻断。镜像 D3 的生成-审核-决策链与 BLOCKED/重生成/failed 回读语义。

## 非目标（本子故事不做）

- SOP / 检验 SOP / 其他受控文档实体的版本管理（系统无此模型，本故事不新建——见「契约修订」）
- 受影响文档本身的更新操作（在 FMEA/控制计划模块完成，本故事只识别+审核+门禁）
- 文档更新内容的质量审核（只验「是否更新到位」，内容质量归各模块）
- 延期处理的到期跟踪闭环（后续迭代）
- 审批壳（01.3 负责；本故事只衔接 D8_GATE_PENDING→D8_APPROVAL_PENDING 门禁）

## 数据模型（3 张新表，前缀 `capa_docg_`）

镜像 D3 表族：所有表 `factory_id NOT NULL` + 复合 FK（parent+factory）+ `is_current` partial-UQ + `status` enum CHECK + `attempt_token` CAS。迁移文件 `backend/alembic/versions/20260713_doc_gate.py`。

### `capa_docg_analysis`（影响分析生成根）

镜像 `capa_d3_impact_report`。LLM 产出受影响文档清单 + 每项关键更新点。

| 字段 | 类型 | 约束 |
|---|---|---|
| `analysis_id` | UUID PK | default uuid4 |
| `capa_id` | UUID | FK capa_eightd.report_id, NOT NULL |
| `factory_id` | UUID | FK factories.id, NOT NULL（复合 FK `(capa_id,factory_id)` → capa_eightd）|
| `is_current` | bool | NOT NULL default false；partial-UQ `uq_docg_analysis_current` (capa_id WHERE is_current=true) |
| `status` | str(10) | NOT NULL default 'running'；CHECK ∈ {running,done,failed}；**partial-UQ `uq_docg_analysis_running` (capa_id WHERE status='running')**（同 D3 report，串行化并发生成——见 review P1#5）；状态机 CHECK（同 D3 report：running→is_current=false+completed_at NULL；failed→is_current=false+completed_at NOT NULL；done→completed_at NOT NULL）|
| `affected_docs` | JSONB | done 时 NOT NULL；结构见下 |
| `analysis_input_hash` | str(64)? | done 时 NOT NULL；分析输入指纹（factory_id+product_line_code+根因+d5+d7+severity+fmea_ref_id+候选文档集及各自版本 ID/hash 的规范化哈希）。gate 新鲜度校验用——见 C9 |
| `llm_available` | bool | NOT NULL default false |
| `model` | str(40)? | — |
| `prompt_stats` | JSONB? | — |
| `error` | Text? | failed 时填 |
| `attempt_token` | UUID | NOT NULL default uuid4（CAS 防迟到结果覆盖；**串行化靠 running partial-UQ**，非 token）|
| `started_at` | tz | server_default now() |
| `completed_at` | tz? | done/failed 时填 |
| `generated_by` | UUID | FK users, NOT NULL |
| `generated_at` / `created_at` | tz | server_default now() |

done 完备性 CHECK（同 D3 report done_complete + 输入指纹）：`status='done'` 要求 `affected_docs IS NOT NULL AND analysis_input_hash IS NOT NULL AND llm_available=true AND completed_at IS NOT NULL`。

**baseline 语义（review P0#1）**：`baseline_version` = 该 doc **`created_at <= capa.created_at` 的最后一个版本**（即 CAPA 发起时的状态），**不是**分析生成时的最新版本。`version_after` = 审核时 **`created_at > capa.created_at` 的最新版本**。这样若文档在 CAPA 创建后、分析生成前已更新，`version_after` 会捕获到它（合格 bump），而非与 analysis-time-latest 比较（会误判 false）。规则：
- baseline：`ORDER BY created_at DESC` 取第一个 `created_at <= capa.created_at` 的版本；若无（文档首次创建于 CAPA 之后）→ baseline=NULL，`version_after` 取最新版本即视为 bump
- version_after：`ORDER BY created_at DESC LIMIT 1` 且 `created_at > capa.created_at`
- 相同 `created_at` 时间戳时，次级排序 `(major_no DESC, minor_no DESC, version_id)` 保证确定性

**`affected_docs` JSONB 结构**（done 时）：
```json
[{
  "doc_type": "control_plan",
  "doc_id": "<uuid>",
  "doc_name": "控制计划-DC-DC-100",
  "baseline_version_id": "<uuid|null>",   // created_at <= capa.created_at 的最后版本
  "baseline_version": {"major": 1, "minor": 0, "sha256_8": "a1b2c3d4"} | null,
  "key_points": [
    {
      "target_kind": "cp_item",            // fmea_node | cp_item
      "target_key": "node-5",              // fmea_node: graph node_id; cp_item: source_fmea_node_id（新增项的稳定键，非 item_id）
      "field": "control_method",           // 真实字段名（CP: control_method/reaction_plan/special_class...；FMEA: prevention_control/detection_control...）
      "expected_action": "modify"          // add | modify | delete
    }
  ],
  "update_suggestion": "建议在控制方法列新增防错检测"
}]
```

`target_key` 用 `source_fmea_node_id`（CP）而非 `item_id`：新增 CP item 在分析时尚不存在 item_id，但 `source_fmea_node_id` 是稳定的 FMEA 派生键，`diff_cp_items` 的 `added_items` 保留此字段可匹配（review P1#3）。

`doc_id`/`doc_name`/`baseline_version_id` **不由 LLM 决定**——见 C7（候选 allowlist）。LLM 只决定哪些候选受影响 + key_points + update_suggestion；服务层从 allowlist 回填 doc_id/doc_name/baseline。

### `capa_docg_decision`（门禁决策，含新鲜度指纹）

| 字段 | 类型 | 约束 |
|---|---|---|
| `decision_id` | UUID PK | default uuid4 |
| `analysis_id` | UUID | FK, NOT NULL（复合 FK `(analysis_id,factory_id)` → analysis）|
| `audit_run_id` | UUID? | nullable（`run_audit` 产生时指向本批次；`confirm_no_affected`/`record_defer` 时 NULL——无关联审核批次）。应用层校验：非 NULL 时 (analysis_id, audit_run_id) 须对应实际存在的批次且批次覆盖全部受影响文档 |
| `revision` | int | NOT NULL default 0（单调递增计数器，每次插入新 decision 行 +1；`ORDER BY revision DESC` 作主排序，`decided_at DESC` 作次排序——避免时间戳相同不确定，review 小问题#3）|
| `factory_id` | UUID | FK factories.id, NOT NULL |
| `decision` | str(10) | NOT NULL；CHECK ∈ {passed,blocked,deferred} |
| `no_affected_confirmed` | bool | NOT NULL default false |
| `version_snapshot` | JSONB | NOT NULL default []；`[{doc_type, doc_id, version_after_id, sha256_8}]` 审核通过时各 doc 的最新版本指纹（新鲜度校验用，见 C8）|
| `defer_reason` | Text? | deferred 时 NOT NULL；passed/blocked 时 NULL（CHECK）|
| `defer_owner` | UUID? | FK users; deferred 时 NOT NULL |
| `defer_deadline` | date? | deferred 时 NOT NULL |
| `decided_by` | UUID | FK users, NOT NULL |
| `decided_at` / `created_at` | tz | server_default now() |

**decision 读取语义**：decision 行 append-only（每次 `run_audit`/`record_defer`/`confirm_no_affected` 各插一行，`revision` 自增）。`_d8_doc_gate_gate` 与 `GET /decision` 读**最新行**（`ORDER BY revision DESC LIMIT 1`，次排序 `decided_at DESC`），与 `get_latest_analysis` 的 latest 模式一致。不做 `is_current` partial-UQ（避免同一 analysis 的多次 decision 互相冲突；append-only + revision-latest 更简单且可审计历史）。

**decision 派生规则**（`run_audit` 插入新 decision 行时）：
- 全 audit 行 `status=passed` → decision=passed，`version_snapshot` = 各 doc 的 version_after 指纹
- 任一 audit 行 `status ∈ {pending_update, incomplete}` → decision=blocked，`version_snapshot=[]`
- 空清单 + 工程师 `confirm_no_affected` → 插 decision=passed(`no_affected_confirmed=true`, `audit_run_id=NULL`) 行
- 工程师 `record_defer` → 插 decision=deferred 行（`audit_run_id=NULL`；**门禁 edge 仍 raise**，C5；latest-read 读到 deferred 仍阻断）

## 服务层：`backend/app/services/capa_doc_gate_service.py`

镜像 `capa_d3_containment_service.py` 结构。

### `generate_impact_analysis(db, capa, user_id)` — POST，LLM
1. `pc = build_client(...)`；`pc is None` → 写 `status='failed'`+`error='LLM 未配置'`+`llm_available=False`+`completed_at=now()` 行（`is_current` 不置；failed 行须填 completed_at 以满足 CHECK）+ raise `ValueError("BLOCKED: 无 LLM 凭证")` → API 映射 **422 + `detail.blocked=True`**（同 D3/D4 BLOCKED 模式）
2. **锁定 capa 行 FOR UPDATE**（同 D3 report phase1），在 savepoint 内完成「旧 current 失效 + running 创建」——串行化靠 `uq_docg_analysis_running` partial-UQ（review P1#5），不靠 attempt_token
3. 旧 current analysis（若有）置 `is_current=false`
4. 建 `status='running'`+`is_current=false` 行（**running 态 is_current 恒 false**，满足状态机 CHECK：running→is_current=false+completed_at NULL）。`attempt_token` 仅防迟到 CAS 覆盖
5. **构建候选 allowlist + 计算输入指纹**（C7+C9）：查 `capa.factory_id` + `capa.product_line_code` 下的 CP + FMEA 文档，对每个算 **baseline_version**（`created_at <= capa.created_at` 的最后版本；见「baseline 语义」）+ 最新版本 → allowlist `[(doc_type, doc_id, doc_name, baseline_version, latest_version)]`。同时算 `analysis_input_hash` = 规范化哈希(factory_id, product_line_code, d4_root_cause, d5_correction, d7_prevention, severity, fmea_ref_id, fmea_node_id, 候选文档集及各自 baseline/latest 版本 ID+hash)
6. 组 prompt（8D 根因/d5/d7/severity + allowlist）→ `provider_adapter.complete_json`，要求 LLM 仅从 allowlist 选 doc 并产统一结构 key_points（`{target_kind, target_key, field, expected_action}`）+ update_suggestion
7. 服务层校验 LLM 返回的 doc_id **全部在 allowlist 内**（C7）；越界 → `status='failed'`+`error='LLM 输出含非法 doc_id'`+completed_at
8. 成功 → `status='done'` + `affected_docs`（回填 doc_id/doc_name/baseline）+ `analysis_input_hash` + `is_current=true`（CAS：UPDATE WHERE status='running' AND attempt_token=? SET ...）+ `completed_at`
9. LLM 失败 → `status='failed'`+`error`+`completed_at`，`is_current` 不置（GET 回读可查失败态，同 D3 终审第五轮）
10. 写审计 `DOC_IMPACT_ANALYZED`（`affected_doc_count`, `llm_available`, `status`）

### `get_latest_analysis(db, capa)` — GET，latest-by-created_at
镜像 D3 GET：返回最新 analysis（含 `status='failed'`），前端据此渲染重试按钮。

### `run_audit(db, capa, user_id)` — POST，同步 DB 查询，无 LLM
1. 查 `capa_docg_analysis` current 行（无 → raise "未生成影响分析"）
2. 生成 `audit_run_id`（uuid4，本次审核所有 audit 行共享）
3. 遍历 `affected_docs`，对每项（doc_id 已由 allowlist 校验，可信）：
   - **baseline = affected_docs.baseline_version**（生成时已算，`created_at <= capa.created_at` 的最后版本）
   - 查该 doc 当前最新版本（`version_service.get_latest_cp_version`/`get_latest_fmea_version`，**叠加 factory_id 过滤**——C7 防御性），作为 `version_after` 候选
   - `version_after` = 最新版本且 `created_at > capa.created_at`（无此类版本 → NULL → pending_update）
   - `version_bump` = `version_after` 非空 且 `sha256_hash != baseline.sha256_8`（baseline 为 NULL 时，version_after 存在即 bump）
   - **用 `diff_engine.diff_fmea_graphs`（FMEA）/`diff_cp_items`+`diff_cp_headers`（CP）比较 baseline snapshot 与 version_after snapshot**（C3，非 build_sync_preview）；得 `added/deleted/modified_nodes`（FMEA）或 `added/deleted/modified_items`（CP）
   - 逐个 key_point：按 `target_key` 匹配——fmea_node 用 node_id 命 added/deleted/modified_nodes；cp_item 用 `source_fmea_node_id` 命 added/deleted/modified_items（**新增项无 item_id，用 source_fmea_node_id 稳定匹配**，review P1#3）；`field` 与 `expected_action` 一致 → `covered=True` + evidence
   - status = passed（version_bump 且所有 key_point covered）/ pending_update（无 version_after）/ incomplete（有 version_after 但 key_point 未全覆盖）
4. insert 本批次 `capa_docg_audit` 行（共享 audit_run_id，UQ (audit_run_id, doc_type, doc_id)）+ insert `capa_docg_decision` 行（revision+1；派生：全 passed→passed+version_snapshot；否则 blocked；见「decision 派生规则」）
5. 写审计 `DOC_UPDATE_AUDITED`（`per_doc_status`, `audit_run_id`）+ `DOC_GATE_PASSED`/`DOC_GATE_BLOCKED`

### `record_defer(db, capa, reason, owner, deadline, user_id)` — POST
defer 仍阻断（decision=deferred，门禁 edge 仍 raise，C5）。**`defer_owner` 校验**（review P1#6）：`check_factory_access` 校验的是当前请求用户，不是指定 owner。须直接查 `User.factory_id`（或 `user_factories` 多工厂关系）+ `is_active`，确认 owner 属于当前 CAPA 工厂且激活；否则 raise。写审计 `DOC_GATE_DEFERRED`（reason/owner/deadline）。

### `confirm_no_affected(db, capa, user_id)` — POST
空清单确认：analysis.current.affected_docs 为空时，工程师手动确认 → decision=passed(`no_affected_confirmed=true`, `audit_run_id=NULL`)。写审计 `DOC_GATE_PASSED(reason="空清单人工确认")`。**注意**：此路径仍受 C9 输入新鲜度约束（候选集变化则需重新生成分析）。

## 门禁 edge 接入

`backend/app/services/capa_service.py` `advance_capa`，把 01.3 的占位改为真实 gate：

```python
elif current == EightDState.D8_GATE_PENDING and target == EightDState.D8_APPROVAL_PENDING:
    await _d8_doc_gate_gate(db, capa)   # 替换 01.3 的 pass 占位
```

`_d8_doc_gate_gate(db, capa)`：
1. 查 `capa_docg_analysis` 的 current 行（`is_current=true`）；无 → raise "请先生成文档影响分析"
2. **输入新鲜度校验（C9，先于 decision 检查）**：用当前 capa（根因/d5/d7/severity/product_line_code/fmea_ref_id/fmea_node_id）+ 当前候选文档集（factory_id+product_line 下 CP/FMEA 及各自版本 ID/hash）重算 `analysis_input_hash`，与 analysis 行记录值比对；不一致 → raise `ValueError("分析输入已变更，请重新生成影响分析")` → API 400
3. 在该 analysis 下查 `capa_docg_decision` 最新行（`WHERE analysis_id=? ORDER BY revision DESC, decided_at DESC LIMIT 1`）
4. 无 decision 行 → raise "请先运行文档审核"
5. `decision != 'passed'`（含 deferred）→ raise `ValueError("文档门禁未通过：<原因>")` → API 400
6. **版本新鲜度校验（C8）**：`decision == 'passed'` 时，遍历 `version_snapshot`，对每个 doc 取当前最新版本，比对 `version_after_id`/`sha256_8` 是否等于 decision 记录值；任一不一致 → raise `ValueError("文档已变更，请重新审核：<doc_name>")` → API 400
7. 全部一致 → 通过（advance 继续 mutation + TRANSITION 审计）

## 风险与取舍

- **C1 窄范围 vs 故事「≥3 类」**：契约修订（见上）。SOP 无实体，新建 SOP 版本表超本故事范围；保留枚举供前向兼容是诚实做法，不伪造第三类。
- **baseline 时点语义（C3 + review P0#1）**：baseline = `created_at <= capa.created_at` 的最后版本（CAPA 发起时状态），非分析生成时最新版本。否则 CAPA 后已更新的文档会被误判 version_bump=false。无 baseline（文档首建于 CAPA 后）时 version_after 存在即 bump。相同时间戳用 (major_no, minor_no, version_id) 确定性排序。
- **关键点覆盖判定用版本间 diff（C3 + review P1#3）**：`diff_engine.diff_fmea_graphs`/`diff_cp_items` 比较 baseline snapshot vs version_after snapshot，产出 added/deleted/modified 三类。统一 key_point 结构 `{target_kind: fmea_node|cp_item, target_key, field, expected_action: add|modify|delete}`：FMEA 用 node_id，**CP 用 source_fmea_node_id**（非 item_id——新增项分析时尚无 item_id，source_fmea_node_id 是稳定派生键，diff_cp_items 的 added_items 保留此字段可匹配）。覆盖 added/deleted/modified 全部，能审核故事要求的「新增控制特性」。无法匹配 → covered=false → incomplete。注意 `build_sync_preview` **不适用**（CP↔FMEA 同步预览，方向相反）。
- **LLM 输出不可信 + allowlist（C7）**：LLM 幻觉可能输出跨工厂/跨产品线 doc_id。服务层先建 allowlist（factory_id+product_line_code 过滤），LLM 只能选候选，越界即 failed。`defer_owner` 须直接查 `User.factory_id`/`user_factories` + `is_active` 校验（非 `check_factory_access`——后者校验当前请求用户，review P1#6）。安全边界不靠 LLM 自律。
- **decision 版本新鲜度（C8）**：审核通过后文档再改 → 旧 passed 不再放行（edge 重核 version_snapshot）。代价：每次推进查一遍最新版本（轻量 DB 查询）。重新生成 analysis 时旧 current 置 false，其 decision 不再被 gate 读取。
- **analysis 输入新鲜度（C9 + review P0#2 第二轮）**：C8 只覆盖「已识别文档改版」，无法发现 CAPA 输入变化或候选集变化。D8_GATE_PENDING 仅冻结 d7_prevention/d8_closure，根因/d5/severity/product_line/fmea_ref 可改 → analysis 存 `analysis_input_hash`，gate 在 decision 检查前重算比对。此校验也保护空清单确认路径（候选集变化则空清单确认失效）。
- **running 并发串行化（review P1#5）**：靠 `uq_docg_analysis_running` partial-UQ（status='running' per capa_id），非 attempt_token。phase1 在锁 capa 行的 savepoint 内完成「旧 current 失效 + running 创建」。token 仅防迟到 CAS 覆盖。与 D3 report 一致。
- **空清单人工确认的风险**：C4 防漏报，但依赖人工诚实。审计留痕（`no_affected_confirmed=true` + `decided_by`）可追溯；C9 输入新鲜度防候选集变化后空确认失效。
- **defer 仍阻断**：C5 与故事一致，但 deferred 状态下 8D 长期卡在 D8_GATE_PENDING——到期跟踪归后续迭代（故事第 90 行明确排除）。
- **门禁 edge 同步审核无 LLM**：`run_audit` 是纯 DB 查询 + diff，快且不阻塞 advance；但须先 POST /audit 生成 decision 行，否则 edge raise "请先运行文档审核"。前端按钮门控（含全局推进按钮 D8_GATE_PENDING 排除）保证顺序。
- **audit_run_id 分组 + decision 引用（review P1#4）**：audit 行按 run_id 分组（UQ (audit_run_id, doc_type, doc_id)），GET /audit 取最新批次。decision.audit_run_id **nullable**（confirm/defer 时 NULL），用列而非新表（YAGNI）；非 NULL 时应用层校验 (analysis_id, audit_run_id) 对应实际批次且批次覆盖全部受影响文档。
- **decision 确定性排序（review 小问题#3）**：用 `revision` 单调自增主排序 + `decided_at` 次排序，避免时间戳相同不确定。
- **复用 D3 模式的一致性收益**：BLOCKED/重生成/failed 回读/partial-UQ/CAS/审计事件全套复用，降低复审摩擦（D3 已 6 轮硬化）。表前缀 `capa_docg_` 与 D3 `capa_d3_` 平行，命名清晰。
