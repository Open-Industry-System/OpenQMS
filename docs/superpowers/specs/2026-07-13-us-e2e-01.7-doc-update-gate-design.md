**日期**: 2026-07-13

**依据**:

## 目标

在 8D 状态机的 `D8_GATE_PENDING→D8_APPROVAL_PENDING` 边接入文档更新审核门禁：D7 完成后系统（经显式 POST）用 LLM 分析受影响受控文档（控制计划、FMEA），D8 关闭审批前自动审核这些文档的版本更新与关键点覆盖情况，未通过则阻断推进；延期记录待办但仍阻断。镜像 D3 的生成-审核-决策链与 BLOCKED/重生成/failed 回读语义。

## 非目标（本子故事不做）

- SOP / 检验 SOP / 其他受控文档实体的版本管理（系统无此模型，本故事不新建——见「契约修订」）
- 受影响文档本身的更新操作（在 FMEA/控制计划模块完成，本故事只识别+审核+门禁）
- 文档更新内容的质量审核（只验「是否更新到位」，内容质量归各模块）
- 延期处理的到期跟踪闭环（后续迭代）
- 审批壳（01.3 负责；本故事只衔接 D8_GATE_PENDING→D8_APPROVAL_PENDING 门禁）

## 数据模型（3 张新表，前缀 `capa_docg_`）

镜像 D3 表族：所有表 `factory_id NOT NULL` + 复合 FK（parent+factory）+ `is_current` partial-UQ + `status` enum CHECK + `attempt_token` CAS。迁移文件 `backend/alembic/versions/20260713_doc_gate.py`。

### `capa_docg_analysis`（影响分析生成根）

镜像 `capa_d3_impact_report`。LLM 产出受影响文档清单 + 每项关键更新点。

| 字段 | 类型 | 约束 |
|---|---|---|
| `analysis_id` | UUID PK | default uuid4 |
| `capa_id` | UUID | FK capa_eightd.report_id, NOT NULL |
| `factory_id` | UUID | FK factories.id, NOT NULL（复合 FK `(capa_id,factory_id)` → capa_eightd）|
| `is_current` | bool | NOT NULL default false；partial-UQ `uq_docg_analysis_current` (capa_id WHERE is_current=true) |
| `status` | str(10) | NOT NULL default 'running'；CHECK ∈ {running,done,failed}；**partial-UQ `uq_docg_analysis_running` (capa_id WHERE status='running')**（同 D3 report，串行化并发生成——见 review P1#5）；状态机 CHECK（同 D3 report：running→is_current=false+completed_at NULL；failed→is_current=false+completed_at NOT NULL；done→completed_at NOT NULL）|
| `affected_docs` | JSONB | done 时 NOT NULL；结构见下 |
| `analysis_input_hash` | str(64)? | done 时 NOT NULL；分析输入指纹。**范围（C9）**：CAPA 语义输入（factory_id+product_line_code+根因+d5+d7+severity+fmea_ref_id+fmea_node_id）+ 候选文档**身份集** `(doc_type, doc_id)` + 各 doc **baseline 版本 ID/hash**。**不含 latest version**（否则正常更新流程让 hash 失效）。gate 新鲜度校验用——见 C9 |

| `started_at` | tz | server_default now() |
| `completed_at` | tz? | done/failed 时填 |

done 完备性 CHECK（同 D3 report done_complete + 输入指纹）：`status='done'` 要求 `affected_docs IS NOT NULL AND analysis_input_hash IS NOT NULL AND llm_available=true AND completed_at IS NOT NULL`。

**baseline 语义（review P0#1）**：`baseline_version` = 该 doc **`created_at <= capa.created_at` 的最后一个版本**（即 CAPA 发起时的状态），**不是**分析生成时的最新版本。`version_after` = 审核时 **`created_at > capa.created_at` 的最新版本**。这样若文档在 CAPA 创建后、分析生成前已更新，`version_after` 会捕获到它（合格 bump），而非与 analysis-time-latest 比较（会误判 false）。规则：
- baseline：`ORDER BY created_at DESC` 取第一个 `created_at <= capa.created_at` 的版本；若无（文档首次创建于 CAPA 之后）→ baseline=NULL，`version_after` 取最新版本即视为 bump
- version_after：`ORDER BY created_at DESC LIMIT 1` 且 `created_at > capa.created_at`
- 相同 `created_at` 时间戳时，次级排序 `(major_no DESC, minor_no DESC, version_id DESC)` 保证确定性（version_id DESC：同时间戳取较新创建的版本，review 小问题#3）
- **baseline=NULL 时 diff 输入规范化（review P1#6）**：`diff_fmea_graphs`/`_diff_cp_items_for_gate` 不接受 None。baseline=NULL → FMEA 用 `{"nodes":[],"edges":[]}`、CP 用 `header={}`+`items=[]`；整份新文档的节点/items 全归 added。

**`affected_docs` JSONB 结构**（done 时）：
```json
[{
  "doc_type": "control_plan",
  "doc_id": "<uuid>",
  "doc_name": "控制计划-DC-DC-100",
  "baseline_version_id": "<uuid|null>",   // created_at <= capa.created_at 的最后版本
  "baseline_version": {"major": 1, "minor": 0, "sha256": "<完整 64 位>"} | null,
  "key_points": [                          // 非空（见 done CHECK，review P0#2）
    {
      // 判别联合：modify/delete 用 target_key，add 用 add_anchor，二者互斥（review 第六轮 P1）
      "target_kind": "cp_item",            // fmea_node | cp_item | document
      "expected_action": "modify",         // add | modify | delete
      "field": "control_method",           // 真实字段名（CP: control_method/reaction_plan/special_class...；FMEA: prevention_control/name...）
      "target_key": "node-5"              // modify/delete 必填：fmea_node=graph node_id；cp_item=item_id（版本内唯一；CP 保存保留合法 item_id）。add 时省略
    },
    {
      "target_kind": "fmea_node",
      "expected_action": "add",
      "field": "name",
      "add_anchor": {                     // add 必填（fmea_node/cp_item），modify/delete 时省略（与 target_key 互斥）
        "parent_node_id": "step-3",        // 必须在 baseline 已存在的节点 ID（add_anchors allowlist 校验）
        "node_type": "FailureMode",        // 枚举：FailureMode/FailureEffect/FailureCause/ProcessStep/Function...
        "business_key": "过压"             // 规范化非空（如 trim+lowercase），用于匹配新节点 name
      }
    }
  ],
  "update_suggestion": "建议在控制方法列新增防错检测"   // 非空（见 done CHECK）
}]
```

**key_point 判别联合契约（review 第六轮 P1）**：`expected_action ∈ {add,modify,delete}` 决定字段：
- **modify/delete**：必有 `target_key`（现存节点标识），无 `add_anchor`
- **add（fmea_node/cp_item）**：必有 `add_anchor`（parent_node_id+node_type+business_key），无 `target_key`
- **add（document）**：仅 baseline=NULL，无 `target_key` 无 `add_anchor`（文档级，version_bump 即 covered）
应用层校验互斥：`target_key` 与 `add_anchor` 不可同存；违反 → analysis failed。

**存储用完整 SHA-256（review 小问题）**：`baseline_version.sha256` / `version_snapshot.sha256` / `analysis_input_hash` 均存完整 64 位十六进制；`sha256_8`（前 8 位）仅用于 UI 展示，不进指纹/比对。

`target_key` 对 **cp_item 用 `item_id`**（版本内唯一、可改 product/process 不改身份）。`update_control_plan` 必须保留请求中合法的既有 `item_id`，仅真正新增项生成 UUID；整表删建会破坏门禁身份。请求侧：**无条件**先做 ID 规范化与校验（重复含 UUID canonical 等价形式 / 非本 CP UUID / 非法字符串 → 400；仅空 ID 或 `temp-*` 表示新增）。**上线 preflight**：`python -m app.services.capa_doc_gate_preflight`（或 `--json`）扫描所有 current analysis 的 CP baseline item_ids 与 latest version item_ids 的交集，零交集即断链——阻止部署并要求人工确认该 CAPA 重新生成 analysis 或接受 delete+add 语义（历史整表 UUID 重建无身份迁移，只能显式人工处置）。前端保存后须回写服务端 `items`（含正式 UUID）。add 仍用 `add_anchor`（parent_node_id+business_key）。`_diff_cp_items_for_gate` **仅按 item_id 配对**（无内容指纹 heuristic remap——「删全部+重建相同指纹」与「整表 UUID 重建」内容形状无法区分，且 product/process 可变会使指纹失配；历史整表重建须重新保存 CP 保留 item_id 或由 `DOC_GATE_CONTRACT_VERSION` 失效后重新生成 analysis）。`DOC_GATE_CONTRACT_VERSION` 纳入 C9 hash。

`doc_id`/`doc_name`/`baseline_version_id`/`key_points` 的 `target_key`+`field` **不由 LLM 自由生成**——见 C7（文档级 + 目标级 allowlist）。服务层从 allowlist 回填 doc_id/doc_name/baseline，并校验完整 `(doc_type, doc_id, target_kind, target_key, field, expected_action)` 元组合法性（review P1#5）。

**target allowlist（review P1#5 + 第四/五轮 P1#5）**：每个候选文档附裁剪后的 target inventory 进 prompt。**allowlist 定义为「允许的父节点 + node type」组合**（非要求完整 target_key 预先存在——新增节点的 target_key 在分析时尚无法合成）：
```json
{
  "doc_id": "...", "doc_type": "fmea", "baseline_version_id": "<uuid|null>",
  "existing_targets": [
    {"target_kind": "fmea_node", "target_key": "node-5", "allowed_fields": ["prevention_control"]}
  ],
  "add_anchors": [
    {"parent_node_id": "step-3", "node_type": "FailureMode", "allowed_fields": ["*"]}
  ]
}
```
- **现存项**（modify/delete）：`existing_targets`，target_key = baseline snapshot 的 node_id（FMEA）/ **item_id（CP）**，审核时命中 modified/deleted
- **新增节点**（add）：用 `add_anchors` —— `parent_node_id`（必须在 baseline 已存在的节点 ID 内）+ `node_type`（枚举：FailureMode/FailureEffect/FailureCause/ProcessStep/Function...）+ LLM 产 `business_key`（规范化非空，如「过压」）。审核时在 `added_nodes` 里按 **父节点 + node_type + business_key 匹配**（不能只检查 version bump——review 第五轮 P1#1）
- **`target_kind='document'`（收窄，review 第五轮 P1#1）**：仅允许 **baseline=NULL + expected_action=add**，表示整份文档首次创建（如 CAPA 后新建的 FMEA）；任意 version_bump 即 covered。**已有 FMEA 的「新增失效模式」不得用 document 退化**（会把无关 bump 当 covered）——必须用 add_anchors
- 服务层校验：modify/delete 的 target_key ∈ existing_targets；add 的 (parent_node_id, node_type) ∈ add_anchors 且 parent 在 baseline 存在、node_type ∈ 允许枚举、business_key 非空规范化；document 仅当 baseline=NULL；doc_type/target_kind 错配 → analysis failed

**done 完备性 CHECK（review P0#2 — 防 vacuous pass）**：`status='done'` 要求
- `affected_docs IS NOT NULL AND analysis_input_hash IS NOT NULL AND llm_available=true AND completed_at IS NOT NULL`
- `affected_docs` 非空时每项 `key_points` 长度 ≥ 1 且 `update_suggestion` 非空（空 key_points 让 `all([])==true` 绕过覆盖门禁）
- `affected_docs` 为空数组（空清单）时不走 key_points 约束，但只能经 `confirm_no_affected` 人工确认后 passed，不可自动 passed

JSONB 内嵌数组非空 CHECK 无法用 SQL 表达，用**应用层入库前断言**（`generate_impact_analysis` 内校验：每项 key_points ≥1、四字段齐全、`expected_action` ∈ {add,modify,delete}、`target_kind` ∈ {fmea_node,cp_item,document} 且与 doc_type 一致、modify/delete 的 target_key ∈ existing_targets、add 的 (parent_node_id,node_type) ∈ add_anchors 且 business_key 非空规范化、document 仅 baseline=NULL+add、重复 key_point 去重或拒绝；违反 → `status='failed'`+error）+ 测试覆盖。

### `capa_docg_audit`（审核记录，每受影响文档一行，按审核批次分组）

| 字段 | 类型 | 约束 |

| `doc_id` | UUID | NOT NULL |

### `capa_docg_decision`（门禁决策，含新鲜度指纹）

| 字段 | 类型 | 约束 |
|---|---|---|
| `decision_id` | UUID PK | default uuid4 |

| `revision` | int | NOT NULL default 0（单调递增计数器，每次插入新 decision 行 +1；`ORDER BY revision DESC` 作主排序，`decided_at DESC` 作次排序——避免时间戳相同不确定，review 小问题#3）。**UQ `(analysis_id, revision)`**（review P1#7：防并发请求读同 max revision 后插相同 revision+1）。所有 decision 写入（`run_audit`/`record_defer`/`confirm_no_affected`）须先 `SELECT ... **decision 读取语义**：decision 行 append-only（每次 `run_audit`/`record_defer`/`confirm_no_affected` 各插一行，`revision` 自增）。`_d8_doc_gate_gate` 与 `GET /decision` 读**最新行**（`ORDER BY revision DESC LIMIT 1`，次排序 `decided_at DESC`），与 `get_latest_analysis` 的 latest 模式一致。不做 `is_current` partial-UQ（避免同一 analysis 的多次 decision 互相冲突；append-only + revision-latest 更简单且可审计历史）。

**decision 派生规则**（`run_audit` 插入新 decision 行时）：
- 全 audit 行 `status=passed` → decision=passed，`version_snapshot` = 各 doc 的 version_after 指纹
- 任一 audit 行 `status ∈ {pending_update, incomplete}` → decision=blocked，`version_snapshot=[]`
- 空清单 + 工程师 `confirm_no_affected` → 插 decision=passed(`no_affected_confirmed=true`, `audit_run_id=NULL`) 行
- 工程师 `record_defer` → 插 decision=deferred 行（`audit_run_id=NULL`；**门禁 edge 仍 raise**，C5；latest-read 读到 deferred 仍阻断）

### `generate_impact_analysis(db, capa, user_id)` — POST，LLM，三阶段事务边界（review P1#4）

**Phase 1（事务内：锁 + 失效旧 current + stale recovery + 建 running + commit）**——镜像 D3 `_report_phase1_create_running:431-477` + `_recover_stale_report:804`：
1. **锁定 capa 行 FOR UPDATE**
2. **旧 current analysis 失效**（若有，置 `is_current=false`）——**先于凭证检查**（review P1#3 fail-closed：重新生成即旧 decision 失效，无论后续是否 BLOCKED）
3. **stale recovery（review 第四轮 P1#4）**：CAS 把超阈值（started_at 超 2x 阈值）的 running 行 → `status='failed'`+`error='stale'`+`completed_at`（同 D3 `_recover_stale_report:804`）
4. **existing running 检查**：若仍有有效 running（非 stale）→ 返回 `{status:'running', analysis_id, retry_after: RETRY_AFTER_SECONDS}`（同 D3 `_running_report:449-455`，第二个请求不重复创建）。**只有无 running 时才建新行**；`uq_docg_analysis_running` partial-UQ 作最后竞态保护
5. `pc = build_client(...)`；`pc is None` → 写 `status='failed'`+`error='LLM 未配置'`+`llm_available=False`+`completed_at=now()` 行（`is_current` 不置）+ commit + raise `ValueError("BLOCKED: 无 LLM 凭证")` → API 映射 **422 + `detail.blocked=True`**（旧 current 已在步骤 2 失效，无 stale passed 残留）
6. 建 `status='running'`+`is_current=false` 行 + `attempt_token`。**`flush` + `commit`**——事务结束，capa 行锁释放（不持锁跨 LLM，同 D3 phase1 `:476-477`）

**Phase 2（读事务：查询 + 复制纯 dict 上下文 → 显式结束 → 无事务调 LLM）**——review 第四轮 P1#3 SQLAlchemy autobegin：
7. 查候选 CP/FMEA + 每 doc 算 **baseline_version**（`created_at <= capa.created_at` 最后版本）+ target allowlist。**把结果复制为纯 dict 脱离 ORM session**（避免 lazy load 跨事务）
8. 算 `analysis_input_hash` = 规范化哈希(factory_id, product_line_code, d4_root_cause, d5_correction, d7_prevention, severity, fmea_ref_id, fmea_node_id, **候选身份集** `(doc_type, doc_id)` + 各 baseline 版本 ID/hash)。**不含 latest version**（review 第三轮 P0#1）
9. **`await db.commit()`（或显式结束读事务）**——释放 autobegin 的读事务，确保 phase2 LLM 调用不持有任何 DB 事务
10. 组 prompt（8D 根因/d5/d7/severity + 文档 allowlist + target allowlist）→ `provider_adapter.complete_json`（无 DB 事务），要求 LLM 仅从 allowlist 选 doc/target，产统一 key_points + update_suggestion

**Phase 3（事务内：re-lock + C9 重算 + CAS promote + commit）**——所有终态统一 CAS（review 第五轮 P1#2，同 D3 `_report_phase3_cas:599`）：
11. **re-lock capa 行** + **C9 重算**（review 第五轮 P1#2）：用当前 capa + 当前候选身份集 + 重算 baseline 重算 `analysis_input_hash`，与 phase2 算的值比对；不一致（LLM 执行期间 CAPA 输入或候选集变化）→ 直接 CAS 标 `status='failed'`+`error='input_changed'`+completed_at，**不晋升 current**，写审计后返回（不等 /audit 或 gate 发现过期）
12. 服务层校验 LLM 输出：doc_id 全在 allowlist 内（C7）；每项 key_points ≥1 且四字段合法且 (target_kind,target_key,field) 在 target allowlist 内且 doc_type/target_kind 一致（review P0#2+P1#5）；update_suggestion 非空。违反 → CAS 标 failed（见下统一 CAS）
13. **统一 CAS（成功/失败/LLM 异常都走）**：`UPDATE capa_docg_analysis SET status=:st, error=:err, affected_docs=..., analysis_input_hash=..., completed_at=now() [, is_current=true] WHERE analysis_id=? AND attempt_token=? AND status='running'`。成功 → `:st='done', is_current=true`；LLM 异常/校验失败 → `:st='failed', error=..., is_current 不置`。**`rowcount==0`** → 该 running 已被 stale recovery 标 failed 或被 superseded → 返回 `{status:'superseded'}`，**不覆盖状态、不重复写审计**（同 D3 `:635/:661`）
14. 写审计 `DOC_IMPACT_ANALYZED`（`affected_doc_count`, `llm_available`, `status`；superseded 不写）

### `run_audit(db, capa, user_id)` — POST，同步 DB 查询，无 LLM
1. 查 `capa_docg_analysis` current 行（无 → raise "未生成影响分析"）。**C9 预检查（小问题#2）**：重算 `analysis_input_hash` 与 current 行比对；不一致 → raise "分析输入已变更，请重新生成影响分析"（避免为陈旧 analysis 写无效 audit/decision）
2. **空清单守卫（review 第四轮 P0#1）**：`if not analysis.affected_docs: raise ValueError("空影响清单须人工确认，不可运行自动审核")`——空清单 `all([])==True` 会让「全 audit 行 passed→passed」派生 vacuous passed 绕过 `confirm_no_affected`。空清单只能走 `/confirm-no-affected` 人工确认路径。
3. 生成 `audit_run_id`（uuid4，本次审核所有 audit 行共享）
4. 遍历 `affected_docs`，对每项（doc_id 已由 allowlist 校验，可信）：
   - **baseline = affected_docs.baseline_version**（生成时已算，`created_at <= capa.created_at` 的最后版本）
   - 查该 doc 当前最新版本（`version_service.get_latest_cp_version`/`get_latest_fmea_version`，**叠加 factory_id 过滤**——C7 防御性），作为 `version_after` 候选
   - `version_after` = 最新版本且 `created_at > capa.created_at`（无此类版本 → NULL → pending_update）
   - `version_bump` = `version_after` 非空 且 `sha256 != baseline.sha256`（baseline 为 NULL 时，version_after 存在即 bump）
   - **用 `diff_engine.diff_fmea_graphs`（FMEA）/`_diff_cp_items_for_gate`+`diff_cp_headers`（CP）比较 baseline snapshot 与 version_after snapshot**（C3，非 build_sync_preview）；得 `added/deleted/modified_nodes`（FMEA）或 `added/deleted/modified_items`（CP）
   - 逐个 key_point 匹配（按 expected_action）：
     - **modify/delete**：fmea_node 用 node_id 命 modified/deleted_nodes；cp_item 用 **item_id** 命 modified/deleted_items；`field` 一致 → covered
     - **add（节点级）**：`diff_fmea_graphs().added_nodes` 只返回节点无父边信息——审核时须先从 `version_after.snapshot.edges` 建 parent lookup（target→[sources]），再在 `added_nodes` 里按 **(parent_node_id, node_type, business_key)** 匹配：added 节点的父边 source == add_anchor.parent_node_id、节点 type == node_type、节点 name 规范化后 == business_key；三者全中即 covered（**同名新节点但父节点不同不可通过**——review 第六轮 P1，需测试覆盖）
     - **add（document 级，仅 baseline=NULL）**：version_bump 即 covered
   - status = passed（version_bump 且所有 key_point covered）/ pending_update（无 version_after）/ incomplete（有 version_after 但 key_point 未全覆盖）
5. insert 本批次 `capa_docg_audit` 行（共享 audit_run_id，UQ (audit_run_id, doc_type, doc_id)）+ insert `capa_docg_decision` 行（revision+1；派生：全 passed→passed+version_snapshot；否则 blocked；见「decision 派生规则」）
6. 写审计 `DOC_UPDATE_AUDITED`（`per_doc_status`, `audit_run_id`）+ `DOC_GATE_PASSED`/`DOC_GATE_BLOCKED`

### `record_defer(db, capa, reason, owner, deadline, user_id)` — POST
defer 仍阻断（decision=deferred，门禁 edge 仍 raise，C5）。**`defer_owner` 校验**（review P1#6）：`check_factory_access` 校验的是当前请求用户，不是指定 owner。须直接查 `User.factory_id`（或 `user_factories` 多工厂关系）+ `is_active`，确认 owner 属于当前 CAPA 工厂且激活；否则 raise。写审计 `DOC_GATE_DEFERRED`（reason/owner/deadline）。

### `confirm_no_affected(db, capa, user_id)` — POST
空清单确认：analysis.current.affected_docs 为空时，工程师手动确认 → decision=passed(`no_affected_confirmed=true`, `audit_run_id=NULL`)。**先做 C9 预检查**（重算 `analysis_input_hash` 比对；不一致 → raise "分析输入已变更"，避免为陈旧 analysis 写无效确认，小问题#2）。写审计 `DOC_GATE_PASSED(reason="空清单人工确认")`。候选身份集变化（新增/删除 CP/FMEA）→ C9 失败 → 须重新生成分析。

## 门禁 edge 接入

`_d8_doc_gate_gate(db, capa)`：
1. 查 `capa_docg_analysis` 的 current 行（`is_current=true`）；无 → raise "请先生成文档影响分析"
2. **输入新鲜度校验（C9，先于 decision 检查）**：用当前 capa（根因/d5/d7/severity/product_line_code/fmea_ref_id/fmea_node_id）+ 当前**候选身份集** `(doc_type, doc_id)` + **按 `created_at <= capa.created_at` 重算的 baseline version ID/hash** 重算 `analysis_input_hash`，与 analysis 行记录值比对；不一致 → raise `ValueError("分析输入已变更，请重新生成影响分析")` → API 400。**不得使用当前 latest version**（否则正常更新流程让 hash 失效——见 C9）
3. 在该 analysis 下查 `capa_docg_decision` 最新行（`WHERE analysis_id=? ORDER BY revision DESC, decided_at DESC LIMIT 1`）
4. 无 decision 行 → raise "请先运行文档审核"
5. `decision != 'passed'`（含 deferred）→ raise `ValueError("文档门禁未通过：<原因>")` → API 400
6. **版本新鲜度校验（C8）**：`decision == 'passed'` 时，遍历 `version_snapshot`，对每个 doc 取当前最新版本，比对 `version_after_id`/`sha256`（完整 64 位）是否等于 decision 记录值；任一不一致 → raise `ValueError("文档已变更，请重新审核：<doc_name>")` → API 400
7. 全部一致 → 通过（advance 继续 mutation + TRANSITION 审计）

## 风险与取舍

- **analysis 输入新鲜度 hash 范围（C9 + review 第三轮 P0#1）**：hash **只含 CAPA 语义输入 + 候选身份集 (doc_type,doc_id) + 各 baseline ID/hash，不含 latest version**。若含 latest，正常「分析→更新文档→审核」流程里 latest 必变 → hash 失效 → C8 永远没机会发挥 → 门禁对正常更新假阻断。候选身份集新增/删除仍失效；已识别文档审核后变化由 C8 负责。
- **防 vacuous pass（review 第三轮 P0#2）**：done CHECK + 应用层校验要求 affected_docs 非空时每项 key_points ≥1 且 update_suggestion 非空。否则空 key_points 让 `all([])==true` 绕过覆盖门禁。空 affected_docs 只能走 confirm_no_affected 人工确认。
- **C1 窄范围 vs 故事「≥3 类」**：契约修订（见上）。SOP 无实体，新建 SOP 版本表超本故事范围；保留枚举供前向兼容是诚实做法，不伪造第三类。
- **baseline 时点语义（C3 + review P0#1）**：baseline = `created_at <= capa.created_at` 的最后版本（CAPA 发起时状态），非分析生成时最新版本。否则 CAPA 后已更新的文档会被误判 version_bump=false。无 baseline（文档首建于 CAPA 后）时 version_after 存在即 bump，diff 输入规范化为空结构（review P1#6）。相同时间戳用 (major_no, minor_no, version_id) 确定性排序。
- **关键点覆盖判定用版本间 diff（C3 + review P1#3 + 第四/五轮 P1#5）**：`diff_engine.diff_fmea_graphs` / doc-gate 专用 `_diff_cp_items_for_gate` 比较 baseline vs version_after。modify/delete 用现存 node_id（FMEA）/**item_id（CP）**匹配；**add 用 (parent_node_id, node_type, business_key) 在 added 匹配**（不能只查 version bump）。CP 保存须保留合法 item_id。`target_kind=document` **仅 baseline=NULL+add**（FMEA/CP 新文档）。无法匹配 → covered=false → incomplete。`build_sync_preview` **不适用**。
- **Phase 3 统一 CAS + C9 重算（review 第五轮 P1#2）**：成功/失败/LLM 异常都走 `WHERE analysis_id=? AND attempt_token=? AND status='running'`，rowcount==0 → superseded 不覆盖不重复审计（同 D3 `_report_phase3_cas:599`）。re-lock 后重算 C9 hash：LLM 执行期间 CAPA 输入/候选集变化 → 标 failed/input_changed 不晋升 current（不等 /audit 或 gate 发现过期）。
- **LLM 输出不可信 + 文档/目标/锚点三级 allowlist（C7 + review P1#5 + 第五轮 P1#1）**：LLM 幻觉可能输出跨工厂 doc_id 或编造 node_id。服务层先建文档 allowlist（factory_id+product_line_code 过滤）+ 每 doc 的 existing_targets（现存 node_id / **item_id（CP）**）+ add_anchors（允许的 parent_node_id+node_type 组合）。modify/delete 命中 existing_targets；add 命中 add_anchors 且 business_key 非空规范化；document 仅 baseline=NULL+add。越界/错配/编造 → analysis failed。`defer_owner` 须直接查 `User.factory_id`/`user_factories` + `is_active`（非 `check_factory_access`，review P1#6）。安全边界不靠 LLM 自律。
- **decision 版本新鲜度（C8）**：审核通过后文档再改 → 旧 passed 不再放行（edge 重核 version_snapshot，完整 64 位 sha256）。代价：每次推进查一遍最新版本（轻量 DB 查询）。重新生成 analysis 时 phase1 先失效旧 current，其 decision 不再被 gate 读取。
- **analysis 输入新鲜度（C9 + review P0#2 第二轮）**：C8 只覆盖「已识别文档改版」，无法发现 CAPA 输入变化或候选集变化。D8_GATE_PENDING 仅冻结 d7_prevention/d8_closure，根因/d5/severity/product_line/fmea_ref 可改 → analysis 存 `analysis_input_hash`，gate 在 decision 检查前重算比对。此校验也保护空清单确认路径（候选身份集变化则空清单确认失效）。
- **running 并发串行化 + 三阶段事务（review P1#4+P1#5）**：靠 `uq_docg_analysis_running` partial-UQ（status='running' per capa_id），非 attempt_token。Phase1 锁 capa 行 + 失效旧 current + 建 running + **commit**（释放锁，不持锁跨 LLM，同 D3 `_report_phase1_create_running:476-477`）；Phase2 无事务调 LLM；Phase3 re-lock + CAS promote + commit。token 仅防迟到 CAS 覆盖。
- **重新生成 fail-closed（review P1#3 第三轮）**：phase1 先失效旧 current（无论后续是否 BLOCKED），再检测凭证。无凭证时旧 passed 不残留 → 门禁不放行。与 C8/C9「重新生成即旧 decision 失效」承诺一致。
- **decision revision 并发约束（review P1#7）**：UQ (analysis_id, revision) + 所有 decision 写入先 SELECT analysis FOR UPDATE 锁内读 max(revision) 再 insert revision+1。防并发 /audit//defer//confirm 读同 max 后插相同 revision。
- **空清单人工确认的风险**：C4 防漏报，但依赖人工诚实。审计留痕（`no_affected_confirmed=true` + `decided_by`）可追溯；C9 输入新鲜度防候选身份集变化后空确认失效。
- **defer 仍阻断**：C5 与故事一致，但 deferred 状态下 8D 长期卡在 D8_GATE_PENDING——到期跟踪归后续迭代（故事第 90 行明确排除）。
- **门禁 edge 同步审核无 LLM**：`run_audit` 是纯 DB 查询 + diff，快且不阻塞 advance；但须先 POST /audit 生成 decision 行，否则 edge raise "请先运行文档审核"。前端按钮门控（含全局推进按钮 D8_GATE_PENDING 排除）保证顺序。
- **audit_run_id 分组 + decision 引用（review P1#4）**：audit 行按 run_id 分组（UQ (audit_run_id, doc_type, doc_id)），GET /audit 取最新批次。decision.audit_run_id **nullable**（confirm/defer 时 NULL），用列而非新表（YAGNI）；非 NULL 时应用层校验 (analysis_id, audit_run_id) 对应实际批次且批次覆盖全部受影响文档。
- **decision 确定性排序（review 小问题#3）**：用 `revision` 单调自增主排序 + `decided_at` 次排序，避免时间戳相同不确定。
- **存储用完整 SHA-256（review 小问题）**：指纹/比对字段存完整 64 位，sha256_8（前 8 位）仅 UI 展示。
- **复用 D3 模式的一致性收益**：BLOCKED/重生成/failed 回读/partial-UQ/CAS/审计事件全套复用，降低复审摩擦（D3 已 6 轮硬化）。表前缀 `capa_docg_` 与 D3 `capa_d3_` 平行，命名清晰。
