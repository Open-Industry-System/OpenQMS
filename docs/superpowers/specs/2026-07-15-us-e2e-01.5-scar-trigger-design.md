# US-E2E-01.5 8D → SCAR 触发与回写 — Design

**日期**: 2026-07-15  
**状态**: 设计定稿（待实现）  
**子故事**: `docs/user-stories/US-E2E-01-capa-8d-closed-loop/US-E2E-01.5-scar-trigger.md`（定稿 v1，2026-07-08）  
**AI_REQUIRED**: false  
**Gap**: `docs/superpowers/specs/2026-07-08-us-e2e-01-gap-analysis.md` §01.5  

## 1. 目标

现场质量工程师在来料不良 8D 的 D3 及之后阶段，可一键发起 SCAR，携带 8D 上下文；SCAR 单号回写 8D；SCAR 状态变更在 8D 侧可读可见并写同步审计。不改造 SCAR 模块自身全流程。

## 2. 已有基建（复用，不重造）

| 资产 | 用途 |
|---|---|
| `SupplierSCAR.capa_ref_id` → `capa_eightd.report_id` | SCAR → 8D 外键已存在 |
| `scar_service._create_scar_without_commit` | 与客诉/RMA/风险告警同路径建 SCAR |
| `create_scar_from_complaint` / `create_scar_from_rma` / IQC `trigger_scar` | 源实体「一键建 SCAR + 回写 ref」模式 |
| `POST /scars/{id}/link-capa` | 既有 SCAR→CAPA 关联（本设计补双向一致） |
| `listSuppliers` + SCAR 详情页 `/scars/{id}` | UI 选供应商 + 跳转 |
| D3 E2E supplier seed | E2E 可复用供应商 |

**缺口**: CAPA 无 `scar_ref_id`；无 8D 侧触发入口；无 8D 侧 SCAR 状态投影；`transition_scar` 不通知 CAPA；`source_type` schema 未含 `capa`。

## 3. 决策摘要

| 决策 | 选择 | 理由 |
|---|---|---|
| 关联基数 | **1:1** | 与客诉/RMA 一致；故事契约 `capa.scar_ref_id` |
| 1:1 强约束 | **双侧 partial unique 约束 + CAPA 行 `FOR UPDATE`** | DB 兜底并发；服务层先检后建的竞态由约束拒绝 |
| 状态同步 | **读时投影** `linked_scar` + transition 写 `SCAR_STATUS_SYNCED` | 无双写列；满足「创建/关闭可见」 |
| 供应商来源 | **请求体必填 `supplier_id`** | CAPA 无 supplier_id；不猜 |
| 受影响批次 | **从当前 D3 impact report 确定性读取并预填** | 故事验收「携带受影响批次」须有可断言路径 |
| 实现路径 | **对齐客诉模式** `POST …/trigger-scar` | 最小增量、模式成熟 |
| 触发窗口 | **D3+ 且非 ARCHIVED**（拒 D1/D2/ARCHIVED） | 覆盖故事 D3/D4，避免后续 D 步卡死 |
| `source_type` | **`capa`**（扩 Pydantic/TS Literal；DB 无 CHECK） | 可区分来源；与 iqc/complaint/rma/manual 并列 |
| 换绑 | **禁止**（`scar.capa_ref_id` 已指向他 CAPA -> 400） | 1:1 下换绑会留旧 CAPA 脏指针；故事无换绑需求 |

## 4. 数据模型

### 4.1 迁移

- 表 `capa_eightd` 新增：
  - `scar_ref_id UUID NULL REFERENCES supplier_scars(scar_id) ON DELETE SET NULL`
  - 部分唯一索引（**1:1 兜底**）：
    `CREATE UNIQUE INDEX uq_capa_eightd_scar_ref_id ON capa_eightd (scar_ref_id) WHERE scar_ref_id IS NOT NULL`
- 表 `supplier_scars` 新增部分唯一索引（**1:1 兜底，反向**）：
  `CREATE UNIQUE INDEX uq_supplier_scars_capa_ref_id ON supplier_scars (capa_ref_id) WHERE capa_ref_id IS NOT NULL`
  > 注：`capa_ref_id` 已存在且为 `ON DELETE SET NULL`；此索引跨所有 `source_type` 生效，即同一 CAPA 至多被一个 SCAR（任何来源）反向指向，与 1:1 一致。
- **历史反向关联回填（建索引前必做）**: 库中已存在 `supplier_scars.capa_ref_id` 数据（如 seed `SCAR-2026-001` → `capa1`）。既有 `link-capa` 无跨厂/跨 PL 校验，**不能假定**历史关联同厂同 PL。迁移须按序：
  1. **查重**: `SELECT capa_ref_id, count(*) FROM supplier_scars WHERE capa_ref_id IS NOT NULL GROUP BY capa_ref_id HAVING count(*) > 1`
  2. **跨厂脏关联**:  
     `SELECT s.scar_id, s.factory_id, c.report_id, c.factory_id FROM supplier_scars s JOIN capa_eightd c ON c.report_id = s.capa_ref_id WHERE s.capa_ref_id IS NOT NULL AND s.factory_id <> c.factory_id`  
     若有行 → **迁移报错并中止**（不静默回填，避免把跨厂 SCAR 投影到 CAPA `linked_scar` 泄漏他厂信息）。人工清理：置脏 `s.capa_ref_id=NULL` 或纠正厂属后再跑迁移。
  3. **跨产品线脏关联**:  
     `SELECT s.scar_id, s.product_line_code, c.report_id, c.product_line_code FROM supplier_scars s JOIN capa_eightd c ON c.report_id = s.capa_ref_id WHERE s.capa_ref_id IS NOT NULL AND s.product_line_code IS DISTINCT FROM c.product_line_code`  
     若有行 → **迁移报错并中止**（同理：避免 CAPA 侧 PL 只读用户经 `linked_scar` 读到他 PL 的 SCAR 单号/状态/供应商）。人工裁定：清 `capa_ref_id` 或对齐 PL 后再跑。
  4. **1:1 冲突策略**: 若步骤 1 存在重复（同一 CAPA 被多 SCAR 指向），**迁移报错并中止**（不静默选一个）——人工裁定保留哪条 SCAR 的反向指针，其余置 `capa_ref_id=NULL`。生产库上线前由人工/DBA 处理；本故事 seed 假设无重复/无跨厂/无跨 PL。
  5. **回填**（仅在 1–4 均通过后）:  
     `UPDATE capa_eightd c SET scar_ref_id = s.scar_id FROM supplier_scars s WHERE s.capa_ref_id = c.report_id AND c.scar_ref_id IS NULL AND s.factory_id = c.factory_id AND s.product_line_code IS NOT DISTINCT FROM c.product_line_code`
  6. **再建唯一索引**: 步骤 1–4 干净 + 步骤 5 回填后，双侧 partial unique 才能成功创建。
- revision 挂在实现时 parent 真 head 之后（合并前再确认，禁止复制 parent 迁移进 feature 分支）
- 不改 `supplier_scars` 表结构（`capa_ref_id` 已在）

### 4.2 不变量

1. **1:1（DB 兜底）**: 双侧 partial unique 约束（§4.1）保证无论并发或绕过服务层，一个 CAPA 至多一个 `scar_ref_id`、至多一个 SCAR 反向指向它。服务层 trigger 时对 CAPA 行 `SELECT ... FOR UPDATE`（见 §5.1），使并发 trigger 之一拿到 400 而非 `IntegrityError`。
2. **同厂**:
   - trigger：`supplier.factory_id == capa.factory_id`，且 `scar.factory_id = capa.factory_id`
   - link-capa：`scar.factory_id == capa.factory_id`，否则 400
3. **同产品线**:
   - trigger：`scar.product_line_code = capa.product_line_code`（从 CAPA 拷贝）
   - link-capa：`scar.product_line_code == capa.product_line_code`，否则 400  
   - 理由：多 PL 权限用户若可跨 PL 关联，仅有 CAPA 所属 PL 的 viewer 会经 `linked_scar` 读到另一 PL 的 SCAR 单号/状态/供应商（越权读投影）
4. **权限**: `canEdit('capa')`（与 D 步编辑同级）
5. **状态门**: `capa.status ∉ {D1_TEAM, D2_DESCRIPTION, ARCHIVED}`（注：实际状态字面以 `eightd_state.py` 为准；D2 正式枚举名为 `D2_DESCRIPTION`）
6. **双向一致**（触发路径）:
   - `scar.capa_ref_id = capa.report_id`
   - `scar.source_type = "capa"`
   - `scar.source_id = capa.report_id`
   - `scar.factory_id = capa.factory_id`
   - `scar.product_line_code = capa.product_line_code`
   - `capa.scar_ref_id = scar.scar_id`
7. **禁止换绑**: `scar.capa_ref_id` 已指向某 CAPA 时，`link-capa` 拒绝（400）；trigger 路径因 1:1 也不会产生换绑。无换绑即无旧 CAPA 脏指针。
8. **`source_type="capa"` 仅专用 trigger 路径可写**: 公开 `POST /scars`（`SCARCreate`）**不得**接受 `"capa"`，防止绕过 CAPA EDIT / 状态门 / 双向指针 / `SCAR_TRIGGERED`（见 §5.5）。

### 4.3 描述拼装

- Body `description` 若提供则原样使用
- 否则**组合**所有非空 D 步字段（不是二选一，避免 D2 已存在时漏掉 D4 根因）：
  ```
  {document_no} {title}
  [问题描述] {d2_description}      # 非空才拼
  [根因] {d4_root_cause}           # 非空才拼
  ```
  逐段跳过空值；整体合理截断（对齐 `SupplierSCAR.description` 容量）
- **受影响批次（确定性来源）**: 从当前 D3 impact report 读取
  - 查询：`CapaD3ImportRun.is_current AND capa_id=report.id` -> `CapaD3ImpactReport.is_current` -> `batches` JSONB
  - 每个 batch dict 含 `material_code` / `lot_no`（见 `capa_d3_containment_service._compute_batches`）
  - 取 `lot_no` 非空者，去重；拼入 description 尾部 `受影响批次: LOT-A, LOT-B, …`
  - **无当前 D3 report 或 batches 为空**: 不拼批次段（不阻断 trigger；批次为「尽力携带」），但 E2E seed 必须提供含已知 lot 的 D3 report 以保证验收可断言
- 可选 Body `affected_batches: string[]`（用户在 Modal 可编辑/补充）**覆盖**从 D3 读取的批次；为空数组表示清空批次段

> 故事验收「携带受影响批次（受影响批次等上下文）」: 实现路径 = D3 当前 report batches 确定性预填 + 可覆盖；E2E 断言已知 lot 出现在 SCAR description（见 §8.3）。

## 5. API / 服务

### 5.1 `POST /api/capa/{report_id}/trigger-scar`

**Request**

```json
{
  "supplier_id": "uuid",
  "description": "optional",
  "requested_action": "optional",
  "due_date": "YYYY-MM-DD | null",
  "affected_batches": ["optional lot codes — overrides D3-derived batches when provided"]
}
```

**行为**

1. **加载 CAPA（工厂可见性 → 404）**:
   - 按 `report_id` 加载；无行 → 404。
   - **工厂可见性**（与 `apply_scope_filter` / SCAR 路由本地 helper 同语义，返回 **404** 不泄存在性）:
     - 若 `scope.effective_factory_id` 非空：要求 `capa.factory_id == scope.effective_factory_id`，否则 404
     - 否则若 `scope.factory_scope.accessible_factory_ids` 非 `None`：要求 `capa.factory_id in accessible`，否则 404
     - 否则（group admin，accessible=None）：不限工厂
   - **禁止**只写 `factory_id IN accessible` 而忽略 `effective_factory_id`——多工厂用户选定有效工厂后不得凭 UUID 操作其他可访问工厂的 CAPA。
   - **禁止** `check_factory_access(capa.factory_id, scope)` 作为本路径的唯一门禁：该函数抛 **403** 且不处理 effective 优先语义。
   - 实现可抽 `_capa_visible_or_404(capa, scope)` 小 helper，或用 `select(CAPAEightD).where(report_id=...).where(factory_clause)` 一次查出。
2. **`SELECT ... FOR UPDATE`** 重新加载并**锁定** CAPA 行；使用 `execution_options(populate_existing=True)` 或直接用该查询返回的实例（**不要**复用 identity map 中 `scar_ref_id=None` 的旧实例）。锁定使并发 trigger 之一在行锁上等待，醒来后读到对方已写的 `scar_ref_id` → 400。
3. **产品线校验（403）**: `check_product_line_access(capa.product_line_code, scope)`  
   - **不在** step 1 的工厂查询里过滤 PL——否则 PL 无权会变成 404，与「同厂 PL 无权 → 403」测试不可达。统一契约：**工厂不可见/不存在 → 404；PL 无权 → 403**。
4. `canEdit('capa')`（403）
5. 状态门 / 已关联（`scar_ref_id` 非空 → 400）/ supplier 存在且同厂（`supplier.factory_id == capa.factory_id`，否则 400）
6. 读当前 D3 impact report batches（§4.3）；Body `affected_batches` 语义：省略/null → 用 D3 结果；提供数组（含 `[]`）→ **覆盖** D3 结果（`[]` = 不拼批次段）
7. 拼装 description（§4.3）
8. 同一事务：
   - `scar = await _create_scar_without_commit(...)`（**需先扩展 helper，见 §5.6**）  
     `source_type="capa"`, `source_id=report_id`, `capa_ref_id=report_id`,  
     `factory_id=capa.factory_id`, `product_line_code=capa.product_line_code`,  
     `issued_by=user_id`
   - `capa.scar_ref_id = scar.scar_id`
   - `AuditLog(table_name="capa_eightd", record_id=report_id, action="SCAR_TRIGGERED", operated_by=user_id, factory_id=capa.factory_id, changed_fields={capa_id, scar_id, scar_no, supplier_id, source_type: "capa", affected_batches: [...]})`
   - **捕获唯一冲突转 400**: flush/commit 撞 `uq_supplier_scars_capa_ref_id` / `uq_capa_eightd_scar_ref_id` → 捕获 `IntegrityError`，rollback，返回 400「已关联 SCAR」
   - `commit`（与 complaint 路径一致：源侧审计 + 一次 commit；SCAR 侧不另写 CREATE，跟随 `_create_scar_without_commit` 现状）
9. 返回 `SCARResponse`（与 `/scars` 创建响应同形）

**错误**

| 条件 | 语义 |
|---|---|
| CAPA 不存在 / 工厂不可见（含 effective 不匹配） | **404** |
| 同厂但 PL 无权（`check_product_line_access`） | **403** |
| 无编辑权限 | 403 |
| D1/D2/ARCHIVED | 400 |
| 已有 `scar_ref_id`（含并发唯一冲突） | 400 |
| supplier 缺失 / 跨厂 | 400 |

### 5.2 CAPA 读模型投影

`CAPAResponse`（及 list item 若已含详情字段则同形；至少 **GET by id** 必含）增加：

```ts
scar_ref_id?: string | null;
linked_scar?: {
  scar_id: string;
  scar_no: string;
  status: string;       // open | in_progress | responded | verified | closed
  supplier_id: string;
} | null;
d3_affected_lots?: string[];  // 当前 D3 impact report 中非空 lot_no 去重列表；无 report 则为 []
```

- `linked_scar` 由 `scar_ref_id` join `supplier_scars`；无则 `null`
- `d3_affected_lots` 供 Modal 预填（§4.3 / §6.3）；GET 时读当前 D3 report，**不**缓存到 CAPA 表
- **不**在 CAPA 表镜像 `scar_status` 列

### 5.3 `transition_scar` 同步审计

在 `scar_service.transition_scar`，状态变更成功后、commit 前：

- 若 `scar.capa_ref_id` 非空：
  - `AuditLog(table_name="capa_eightd", record_id=scar.capa_ref_id, action="SCAR_STATUS_SYNCED", operated_by=user_id, factory_id=scar.factory_id, changed_fields={capa_id, scar_id, scar_no, scar_status: new_status, old_status, new_status})`
  - `operated_by` / `factory_id` **必填**：`AuditLog` 模型有这两列（`operated_by` 可空但 SCAR 既有路径如 `create_scar`/`transition_scar` 均写 `operated_by=user_id`；本故事 CAPA 侧两条审计对齐该惯例，且写 `factory_id` 以便按厂过滤审计）
- 不更新 CAPA 行字段
- 既有 SCAR 侧 `TRANSITION` 审计保留

故事「至少创建/关闭可见」：创建靠 `linked_scar.status=open` 投影；关闭靠 transition→`closed` 后投影 + `SCAR_STATUS_SYNCED`。中间态（in_progress 等）同样投影，不额外裁剪。

### 5.4 `POST /scars/{id}/link-capa` 一致性修补

**现有缺陷（本故事一并修）**: API 仅校验 SCAR 工厂可见性；service 按 UUID 全局 `db.get(CAPAEightD, …)`，**不**校验目标 CAPA 的工厂/产品线。按原设计仅加「目标已关联」检查仍允许跨厂回写。

**修补后成功路径**:

1. **源 SCAR 可见性（路由层，404）**: 保持现有 SCAR 路由本地 helper 语义——`effective_factory_id` 优先，否则 `accessible_factory_ids`；不可见 → **404**。
2. **源 SCAR 产品线（403）**: `check_product_line_access(scar.product_line_code, scope)`——**现有 link-capa 缺此校验**；同厂但 PL 无权用户不得改绑。与 CAPA 突变路径一致：**工厂不可见 → 404；PL 无权 → 403**。
3. **目标 CAPA 可见性（404 口径，同 §5.1 step 1）**: 按 `report_id` 加载；无行 → 404。工厂可见性用 **effective_factory_id 优先** 规则（与 §5.1 / `apply_scope_filter` 同语义），不可见 → **404**。  
   - **禁止**只写 `factory_id IN accessible` 而忽略 effective。  
   - **禁止**在工厂查询里夹 PL 过滤（会把 PL 无权变成 404）。  
   - **禁止** `db.get` + `check_factory_access`（403 + 无 effective 优先）。
4. **同厂**: `capa.factory_id == scar.factory_id`，否则 400
5. **同产品线**: `scar.product_line_code == capa.product_line_code`，否则 400（§4.2 不变量 3；防多 PL 用户建跨 PL 关联后的越权读投影）
6. **目标产品线权限（403）**: `check_product_line_access(capa.product_line_code, scope)`（操作者对目标 CAPA 所属 PL 须有权；与 step 5 实体同 PL 不变量互补）
7. **锁定目标 CAPA**: `SELECT ... FOR UPDATE` + `populate_existing=True`（与 trigger 同口径，防并发抢绑）
8. **目标 1:1**: 若目标 CAPA 已有 `scar_ref_id` 且 ≠ 当前 `scar_id` → 400（避免抢绑）
9. **禁止换绑**: 若 `scar.capa_ref_id` 已指向 **另一** CAPA → 400（避免旧 CAPA 脏指针；1:1 下无换绑需求）
10. 写双向指针: `scar.capa_ref_id = capa.report_id`；`capa.scar_ref_id = scar.scar_id`
11. **捕获唯一冲突转 400**: commit 撞双侧 partial unique → rollback + 400
12. 既有 SCAR 侧 `LINK_CAPA` 审计保留（写 `operated_by=user_id` 跟随既有路径）

本故事主路径是 trigger；link-capa 修补防止历史半关联 + 关跨厂/跨 PL 漏洞。

### 5.5 Schema 扩展（**公开创建拒绝 `capa`**）

- **后端 `SCARCreate.source_type`：不增加 `"capa"`**  
  公开 `POST /scars` 仅需 SCAR CREATE 权限，不校验 CAPA EDIT、状态门，也不设 `capa_ref_id` / 不写 `SCAR_TRIGGERED`。若 Literal 接受 `"capa"`，用户可造伪 CAPA 来源 SCAR（任意 `source_id`）。  
  - trigger 走专用 body + `_create_scar_without_commit(..., source_type="capa")`，**不经** `SCARCreate`  
  - 既有 `SCARResponse` / 列表过滤若已是 `str` 则无需改；若为 Literal 白名单则 **仅 Response 侧**（及 list filter 入参）增加 `"capa"`，与 Create 分离  
  - 单测：`POST /scars` body `source_type=capa` → **422**（校验拒绝）
- **前端**:
  - `SupplierSCAR.source_type`（实体/响应类型）联合增加 `'capa'`
  - 若存在 `SCARCreate` 请求类型的 `source_type` Literal，**不**加 `'capa'`（与后端 Create 对齐）
- DB：`source_type` 为 `String(20)`，**无** CHECK — 无需迁移改约束；服务层约定 `source_type="capa"` 仅 helper 内部路径写入

### 5.6 扩展 `_create_scar_without_commit`（**实现前置，不可跳过**）

当前签名（`scar_service.py`）**不**接受 `capa_ref_id`，构造 `SupplierSCAR(...)` 时也不写该列。若直接按 §5.1 传入会 `TypeError: unexpected keyword argument 'capa_ref_id'`。

**实现步骤（单列 task）**:

1. 为 `_create_scar_without_commit` 增加可选参数 `capa_ref_id: uuid.UUID | None = None`
2. 构造 `SupplierSCAR(..., capa_ref_id=capa_ref_id)`
3. 既有调用方（complaint / RMA / risk_alert）不传则保持 `None`，行为不变
4. 单测：传入 `capa_ref_id` 后 flush 的 SCAR 行该列非空；不传仍为 `None`
5. **不**改 `create_scar`（公开创建 API）接受 `capa_ref_id`；**不**让公开 Create 写 `source_type=capa`（§5.5）

`create_scar`（带 commit 的公开路径）本故事不扩 `capa_ref_id`；trigger 只走 without_commit。

## 7. 审计契约

| action | table_name | record_id | operated_by | factory_id | changed_fields（关键） |
|---|---|---|---|---|---|
| `SCAR_TRIGGERED` | `capa_eightd` | CAPA `report_id` | `user_id`（必填） | `capa.factory_id` | `capa_id`, `scar_id`, `scar_no`, `supplier_id`, `source_type`, `affected_batches`（实际写入 description 的 lot 列表，可空数组） |
| `SCAR_STATUS_SYNCED` | `capa_eightd` | CAPA `report_id` | `user_id`（必填） | `scar.factory_id`（= capa 同厂） | `capa_id`, `scar_id`, `scar_no`, `scar_status`（= new_status）, `old_status`, `new_status` |

> 字段级契约对齐故事：`SCAR_TRIGGERED` 显式含 `capa_id` + `scar_id`；`SCAR_STATUS_SYNCED` 显式含 `scar_status`（取 new_status）。`record_id` 仍为 CAPA `report_id`，但 `capa_id` 也写入 `changed_fields` 以便按字段名验收。  
> **列级**: `AuditLog.operated_by` / `factory_id` 必须写入（对齐 `scar_service` 既有 CREATE/TRANSITION 路径写 `operated_by`；`factory_id` 便于按厂过滤审计日志）。测试断言两条 CAPA 侧审计的 `operated_by` 非空且 `factory_id` 等于业务实体厂。

既有 SCAR 表上的 `CREATE`/`TRANSITION`/`LINK_CAPA` 行为不删除。

## 8. 测试

### 8.1 Backend

- **helper 扩展**: `_create_scar_without_commit(capa_ref_id=…)` flush 后列非空；不传保持 `None`；既有 complaint/RMA 调用不回归
- trigger 成功：指针双向 + `source_type=capa` + `SCAR_TRIGGERED`（`changed_fields` 含 `capa_id` + `scar_id`）；description **同时**含 d2 与 d4（当两者都非空）；description 含 D3 已知 lot
- 无 D3 report 时 trigger 仍成功（批次段空）
- 重复 trigger → 400
- **并发 trigger**（两会话同时 FOR UPDATE / 或第二个撞 partial unique）→ 恰好一个成功、一个 400；最终 1:1 成立；**不**出现未映射 `IntegrityError` 500
- 跨厂 CAPA UUID → 404（不泄存在性）
- **effective 工厂**: 多厂用户 `effective_factory_id=A` 时，对 factory=B 的 CAPA UUID（即使 B 在 accessible 内）→ **404**（非 403）
- 同厂但 PL 无权 → **403**（非 404；PL 不进工厂查询）
- 跨厂 supplier → 400
- D1 / D2 / ARCHIVED → 400
- 无编辑权限 → 403
- GET CAPA 含 `linked_scar` + `d3_affected_lots` 投影
- `transition_scar` 在 `capa_ref_id` 存在时写 `SCAR_STATUS_SYNCED`（`changed_fields` 含 `scar_status`；`operated_by` 非空；`factory_id` = scar 厂）；无关联不写
- `SCAR_TRIGGERED` 断言 `operated_by` 非空 + `factory_id` = capa 厂
- `link-capa`：
  - 回写 `scar_ref_id` 双向
  - 源 SCAR / 目标 CAPA 工厂不可见（含 effective 不匹配）→ **404**
  - 源 SCAR 同厂 PL 无权 → **403**
  - 目标 CAPA 同厂 PL 无权 → **403**
  - **跨产品线**（`scar.product_line_code != capa.product_line_code`，即使用户两 PL 均有权）→ **400**
  - 目标 CAPA 已被其他 SCAR 占用 → 400
  - 当前 SCAR 已绑其他 CAPA（换绑）→ 400
  - 并发抢绑撞唯一约束 → 400（非 500）
- 公开 `POST /scars`：`source_type=capa` → **422**（Create Literal 拒绝；不写伪 CAPA 来源）
- migration：列可空 + FK + **双侧 partial unique** + 历史回填前 **查重 / 跨厂中止 / 跨 PL 中止** + 回填 WHERE 同厂同 PL

### 8.2 Frontend (vitest)

- 按钮门控（状态 / 权限 / 已关联）
- Modal 打开时 `d3_affected_lots` 预填到批次输入
- Modal 提交调用 `triggerScar`（含 supplier_id + affected_batches）
- linked tag 展示与导航

### 8.3 E2E

`frontend/e2e/specs/m1-core/capa-story-scar-trigger.spec.ts`：

1. Seed：来料向 8D 处于 D3 或 D4 + 已知供应商（复用 D3 E2E supplier）+ **当前 D3 impact report 含已知 lot**（如 `LOT-E2E-SCAR-001`）
2. engineer 登录 → 详情 → 发起 SCAR（供应商选 seed 供应商；批次预填可见）→ 见 `capa-linked-scar` / scar_no
3. **结构断言批次上下文**：GET SCAR 的 `description` 包含已知 lot（`LOT-E2E-SCAR-001`）——这是故事「携带受影响批次」的可观察验收，不是文案质量主观判断
4. 将 SCAR 推进至 closed（UI 或经 API 捷径，与既有 e2e 风格一致）
5. 回 8D 详情：`linked_scar.status === closed`
6. admin 审计日志客户端过滤：存在 `SCAR_TRIGGERED`（`changed_fields` 含该 lot）与至少一条 `SCAR_STATUS_SYNCED`（关闭时）

## 11. 风险与注意

- **Alembic head**: feature 分支实现时必须 `alembic heads` 对 parent tip 链式挂接；禁止把 parent 上已有 revision 文件拷进分支（01.4 教训）
- **状态字面量**: 以 `backend/app/state_machines/eightd_state.py` 为准（D2 为 `D2_DESCRIPTION` 等）
- **`_create_scar_without_commit` 当前不接受 `capa_ref_id`**: 必须先做 §5.6 扩展，否则 trigger 实现直接 TypeError
- **`_create_scar_without_commit` 不写 CREATE 审计**: 与 complaint 一致，源侧 `SCAR_TRIGGERED` 为故事主审计
- **循环 FK 语义**: CAPA→SCAR 与 SCAR→CAPA 双指针；删除 SCAR 时 CAPA `scar_ref_id` SET NULL；删除 CAPA 时 SCAR `capa_ref_id` 既有 SET NULL 行为保持
- **历史脏关联**: 既有 `link-capa` 无跨厂/跨 PL 校验 → 迁移必须查重 + 跨厂中止 + 跨 PL 中止，再回填；不可静默投影脏关联到 `linked_scar`
- **`uq_supplier_scars_capa_ref_id` 跨 source_type**: 上线前需确认历史数据无同一 `capa_ref_id` 被多个 SCAR 占用；若有脏数据先清洗再加唯一索引
- **公开 Create 不得写 `source_type=capa`**: 防止绕过 CAPA EDIT/状态门/双指针/`SCAR_TRIGGERED`（§5.5）
- **D3 report 依赖**: 批次「尽力携带」——无 report 不阻断 trigger；E2E seed 必须造出含 lot 的 current report 才能验故事上下文
