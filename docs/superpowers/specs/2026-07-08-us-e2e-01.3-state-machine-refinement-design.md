## 目标

把 8D 状态机从 `D7_PREVENTION→D8_CLOSURE` 直连细化为带审批壳的 5 段路径，并给 `capa_d7_node_action` 加 `status` 字段（本切片止于 `pending` 创建）。本切片**只做状态机 + node-action.status**，不验 D8 文档门禁内容（归 01.7）、不验 method 枚举与回退计数器（同属 01.3 但另立切片）、不验 FMEA 反查（归 01.4）。

## 非目标（本切片不做）

- D8 文档更新审核门禁（01.7；本切片 `D8_GATE_PENDING` 为直通占位，01.7 接入门禁逻辑）
- D4 验证 method 枚举化（measurement/observation/reproduction）+ 回退计数器（01.3 另一切片）
- FMEA 反查覆盖 Prevention 节点 + 审计（01.4）
- node-action 状态流转 `pending→已执行→已验证`（01.3 行 124，归后续故事）
- node-action 执行后 FMEA 图自动更新（FMEA 模块职责）
- D7→D8 审批流的 RBAC 角色拆分（8D 团队负责人作为独立角色，epic 范围外；当前用 manager 账号代表）

## 当前状态机

`backend/app/state_machines/eightd_state.py`：

```
D1_TEAM → D2_DESCRIPTION → D3_INTERIM → D4_ROOT_CAUSE → D5_CORRECTION
  → D6_VERIFICATION → D7_PREVENTION → D8_CLOSURE → ARCHIVED
```

部分回退边：D4→D3、D6→D5。`D7_PREVENTION→D8_CLOSURE` 单跳直连，无中间状态、无驳回回退。

## 设计

### 1. 状态机与状态语义

新增 3 个状态枚举：

- `D7_COMPLETED` — D7 node-action 处置完成，待文档门禁（01.7）
- `D8_GATE_PENDING` — 文档更新门禁处理中（01.7 负责推进；本切片直通占位）
- `D8_APPROVAL_PENDING` — 门禁已过，待 8D 团队负责人审批

新迁移路径：

```
D7_PREVENTION → D7_COMPLETED → D8_GATE_PENDING → D8_APPROVAL_PENDING → D8_CLOSURE → ARCHIVED
                     ↑                                                              │
                     └─────────────────── 驳回（reject）────────────────────────────┘
```

迁移表变更：

| 当前状态 | 原 | 新 |
|---|---|---|
| `D7_PREVENTION` | `[D8_CLOSURE]` | `[D7_COMPLETED]` |
| `D7_COMPLETED` | — | `[D8_GATE_PENDING]` |
| `D8_GATE_PENDING` | — | `[D8_APPROVAL_PENDING]`（01.7 接入后此处插门禁） |
| `D8_APPROVAL_PENDING` | — | `[D8_CLOSURE, D7_PREVENTION]`（关闭 or 驳回） |
| `D8_CLOSURE` | `[ARCHIVED]` | `[ARCHIVED]`（不变） |

#### 新增辅助函数 `is_capa_open(status) -> bool`

`status` 为 `D8_CLOSURE` 或 `ARCHIVED` 时返回 `False`，其余（含 3 个新状态）返回 `True`。语义：未审批、待文档门禁 = 未关闭。

替换约 12 处硬编码字面量（dashboard/group/quality_trend/management_review/customer_audit/version/capa_service 等的 `.notin_(["D8_CLOSURE","ARCHIVED"])` / `!= "D8_CLOSURE"`）。

**例外：** `recommendation_sources.py:297/376/480` 与 `lessons_learned/sources/historical_capa.py:67` 的历史 CAPA 过滤（限 `D8_CLOSURE`/`ARCHIVED`）**保持精确**——只有真正关闭的 CAPA 才进历史推荐源池；`D8_APPROVAL_PENDING` 尚未关闭，不入池。这些过滤器**不**用 `is_capa_open`。

#### D7 写入冻结

`capa_d7_action_service.py:91` `_assert_d7_stage` 现仅允许 `D7_PREVENTION`。新状态 `D7_COMPLETED`+ 自然被 `!= D7_PREVENTION` 拦截，D7 编辑被冻结。**无需改动。**

#### 审批权限闸

`backend/app/api/capa.py:191` `require_close_permission` 现仅对 `["D7_PREVENTION","D8_CLOSURE"]` 校验 APPROVE 权限。新增 `D8_APPROVAL_PENDING`（审批动作需 APPROVE）。`D7_COMPLETED`/`D8_GATE_PENDING` 由 field_qe 推进（仅需 edit 权限），不入 APPROVE 闸。

### 2. 闸口逻辑与 `advance_capa` 服务重构

`advance_capa` 现为「线性 next + D7→D8 特殊闸 + D4→D5 已验证根因检查」。引入 3 个新状态 + 驳回分支后，改为**显式 `target_state` 驱动的 per-edge 闸口分发**，弃用无法表达分支的 `transitions` 索引列表。

#### `advance_capa(db, capa, user_id, req)` 新结构

```python
current = EightDState(capa.status)
target = req.target_state  # 显式；None = 线性 next（D1→D6→D7_PREVENTION、D8→ARCHIVED 便利）

if target is None:
    target = _linear_next(current)  # D1→D2→...→D6→D7_PREVENTION、D8→ARCHIVED

if not can_transition(current, target):
    raise ValueError(f"Cannot transition from {capa.status} to {target.value}")

# per-edge 闸口分发
if current == D7_PREVENTION and target == D7_COMPLETED:
    await _d7_completion_gate(db, capa)           # node-action 完整性（原 _d7_to_d8_gate 逻辑）
    # savepoint 内抽 d7 lessons（fail-closed）
elif current == D8_GATE_PENDING and target == D8_APPROVAL_PENDING:
    pass                                           # 01.7 接入文档门禁；本切片直通
elif current == D8_APPROVAL_PENDING and target == D8_CLOSURE:
    pass                                           # 权限由 require_close_permission 强制；闸口即「审批」
elif current == D8_APPROVAL_PENDING and target == D7_PREVENTION:
    if not req.reject_reason or not req.reject_reason.strip():
        raise ValueError("驳回需填写理由")
    # 状态回退在下方统一 mutation
elif current == D4_ROOT_CAUSE and target == D5_CORRECTION:
    # 现有已验证根因检查（is_verified=True 且 root_cause_text 绑定当前 d4_root_cause），逻辑不变
    ...
# D1→D2、D2→D3、D3→D4、D5→D6、D6→D7_PREVENTION、D8→ARCHIVED：无闸口

# 状态 mutation + TRANSITION 审计（现有）
old_status = capa.status
capa.status = target.value
db.add(AuditLog(action="TRANSITION", changed_fields={old, new}, operated_by=user_id))

# 审批/驳回专项审计
if current == D8_APPROVAL_PENDING and target == D8_CLOSURE:
    db.add(AuditLog(action="D8_APPROVED", operated_by=user_id))
elif current == D8_APPROVAL_PENDING and target == D7_PREVENTION:
    db.add(AuditLog(action="D8_REJECTED",
                    changed_fields={"reject_reason": req.reject_reason},
                    operated_by=user_id))
```

> **审计命名与故事契约的对齐范围**：故事 01.3 契约（行 112）列了 `D4_VERIFICATION_PASSED`/`D4_VERIFICATION_FAILED`、`D7_NODE_ACTION_CREATED`、`D8_APPROVAL_PENDING`、`D8_APPROVED`/`D8_REJECTED`。本切片只**新增** `D8_APPROVED`/`D8_REJECTED`（与契约一致）。其余命名（`RC_VERIFY` vs `D4_VERIFICATION_*`、`D7_NODE_CONFIRMED/SKIPPED` vs `D7_NODE_ACTION_CREATED`、`TRANSITION` vs `D8_APPROVAL_PENDING`）是**全 01.3 故事范围内的既有差异**，不属本状态机切片——归 01.3 的 method 枚举/回退计数器切片统一对齐审计命名。本切片不擅自改既有审计字面量，避免跨切片语义混乱。

#### `_d7_to_d8_gate` 重命名

`_d7_to_d8_gate` → `_d7_completion_gate`，挂载点从 `D7_PREVENTION→D8_CLOSURE` 改为 `D7_PREVENTION→D7_COMPLETED`。其逻辑（FMEA 完整性 + per-rec action 处置 + stale hash 检测）完全不变——这正是故事要求的「D7 node-action 完整性」闸口。原 D7→D8 分支整段删除。D7 lessons 抽取随之移到 D7 完成时。

#### `AdvanceRequest` schema 变更

`backend/app/schemas/capa.py`：

```python
class AdvanceRequest(BaseModel):
    target_state: EightDState | None = None   # 显式；None = 线性 next（D1→D6→D7_PREVENTION、D8→ARCHIVED）
    reject_reason: str | None = None          # target=D7_PREVENTION（自 D8_APPROVAL_PENDING）时必填
    d7_skip_reasons: list[dict] | None = None  # 不变
```

`target_state=None` 时服务用线性 next（D1→D2→...→D6→D7_PREVENTION、D8→ARCHIVED）。分支流（D7_PREVENTION→D7_COMPLETED、D7_COMPLETED→D8_GATE_PENDING、D8_GATE_PENDING→D8_APPROVAL_PENDING、D8_APPROVAL_PENDING→D8_CLOSURE、→D7_PREVENTION 驳回）前端必须显式传 `target_state`。

### 3. `node-action.status` 字段 + 迁移

**语义区分**（故事行 54、92）：

- `action`（现有）= 工程师对推荐的*处置*：`confirmed`/`skipped`/`auto_filled`
- `status`（新）= node-action 的*执行生命周期*：`pending` → `executed` → `verified`

两者正交。本切片止于 `pending` 创建（故事行 54、92 明确）。

#### 模型变更

`backend/app/models/capa.py` `CapaD7NodeAction`：

```python
status: Mapped[str] = mapped_column(String(20), default="pending", nullable=False)
```

#### 迁移 `backend/alembic/versions/20260708_d7_node_action_status.py`

1. `ALTER TABLE capa_d7_node_action ADD COLUMN status VARCHAR(20) NOT NULL DEFAULT 'pending';`
   - PostgreSQL 在单语句内加 `NOT NULL DEFAULT` 列时，用默认值回填所有现存行，无需单独 backfill。
2. 降级：`DROP COLUMN status`。

#### Schema 变更

`backend/app/schemas/capa_verification.py`：

- `D7NodeActionResponse`：加 `status: str` 字段
- `D7NodeActionCreate`：**不改**——`status` 不由客户端创建时设置，恒由模型默认 `pending`
- `status` 用 `str`（非 `Literal["pending"]`），为后续故事 `executed`/`verified` 留扩展，避免过早枚举（YAGNI）

#### 服务层

`capa_d7_action_service.py` `record_d7_action`：**无需改动**——模型默认值在 insert 时置 `pending`。现有审计 `D7_NODE_CONFIRMED`/`D7_NODE_SKIPPED` 不变。

#### 闸口交互

`_d7_completion_gate` 查 `action.in_(["confirmed","skipped","auto_filled"])`，**不查 `status`**。符合故事行 58：「01.7 的 D8 门禁只查文档更新，不查 node-action 验证状态。」`status`-agnostic 行为已正确。

## 风险与取舍

- **`is_capa_open` 替换范围**：~12 处字面量替换为函数调用，降低未来加状态时漏改风险；但需逐一核对替换不改变既有查询语义（特别是 `customer_audit_service.py:314` 要求 linked CAPA 必须 `D8_CLOSURE`——此处是「必须已关闭」的断言，**不**用 `is_capa_open`，保持精确）。
- **`D8_GATE_PENDING` 直通**：01.7 接入前为占位；若 01.7 延期，存在「文档门禁空转」窗口。可接受——本切片不验门禁内容。
- **`target_state` 显式化**：分支流强制前端传显式状态，比隐式 `next` 更安全（防误推进），但前端调用点增多。线性流仍可用 `null` 便利。
- **`status` 字段不用 Literal**：为后续故事留扩展，但本切片无运行时枚举校验（仅模型 default）。可接受——本切片只要求 `pending` 存在。
