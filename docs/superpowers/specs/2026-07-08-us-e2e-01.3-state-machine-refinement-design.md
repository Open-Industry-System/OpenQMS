## 当前状态机

`backend/app/state_machines/eightd_state.py`：

```
D1_TEAM → D2_DESCRIPTION → D3_INTERIM → D4_ROOT_CAUSE → D5_CORRECTION
  → D6_VERIFICATION → D7_PREVENTION → D8_CLOSURE → ARCHIVED
```

## 设计

### 1. 状态机与状态语义

新增 3 个状态枚举：

- `D7_COMPLETED` — D7 node-action 处置完成，待文档门禁（01.7）
- `D8_GATE_PENDING` — 文档更新门禁处理中（01.7 负责推进；本切片直通占位）
- `D8_APPROVAL_PENDING` — 门禁已过，待 8D 团队负责人审批

新迁移路径：

```
D7_PREVENTION → D7_COMPLETED → D8_GATE_PENDING → D8_APPROVAL_PENDING → D8_CLOSURE → ARCHIVED
                     ↑                                                              │
                     └─────────────────── 驳回（reject）────────────────────────────┘
```

迁移表变更：

| 当前状态 | 原 | 新 |
|---|---|---|
| `D7_PREVENTION` | `[D8_CLOSURE]` | `[D7_COMPLETED]` |
| `D7_COMPLETED` | — | `[D8_GATE_PENDING]` |
| `D8_GATE_PENDING` | — | `[D8_APPROVAL_PENDING]`（01.7 接入后此处插门禁） |
| `D8_APPROVAL_PENDING` | — | `[D8_CLOSURE, D7_PREVENTION]`（关闭 or 驳回） |
| `D8_CLOSURE` | `[ARCHIVED]` | `[ARCHIVED]`（不变） |

#### 新增辅助函数（值 + SQL 子句双 API）

「未关闭」语义在两处用到：Python 值判断（如服务层分支）与 SQLAlchemy 查询表达式（如 `.where(...)`）。一个 `bool` helper 无法同时服务两者——`CAPAEightD.status.notin_(["D8_CLOSURE","ARCHIVED"])`（capa_service.py:52/56/62/65 等）是 SQL 表达式，不是 Python bool。故拆成两个 API：

```python
# backend/app/state_machines/eightd_state.py

_CLOSED_STATES = {EightDState.D8_CLOSURE, EightDState.ARCHIVED}

def is_capa_open_value(status: str | EightDState) -> bool:
    """Python 值判断：D8_CLOSURE/ARCHIVED → False，其余（含 3 新状态）→ True。"""
    return EightDState(status) not in _CLOSED_STATES

def capa_open_clause(column):
    """SQLAlchemy 查询表达式：column NOT IN ('D8_CLOSURE','ARCHIVED')。
    用法：query.where(capa_open_clause(CAPAEightD.status))"""
    return column.notin_([EightDState.D8_CLOSURE.value, EightDState.ARCHIVED.value])
```

替换约 12 处硬编码字面量（dashboard/group/quality_trend/management_review/version/capa_service 等的 `.notin_(["D8_CLOSURE","ARCHIVED"])` → `capa_open_clause(CAPAEightD.status)`；Python 值判断处用 `is_capa_open_value(status)`）。`!= "D8_CLOSURE"` 的单值断言按语义判断：表示「必须已关闭」（如 `customer_audit_service.py:314` 要求 linked CAPA 必须 `D8_CLOSURE`）**保持精确不换**；表示「未关闭」计数的才换。

**例外（保持精确，不用 helper）：** `recommendation_sources.py:297/376/480` 与 `lessons_learned/sources/historical_capa.py:67` 的历史 CAPA 过滤（限 `D8_CLOSURE`/`ARCHIVED`）——只有真正关闭的 CAPA 才进历史推荐源池；`D8_APPROVAL_PENDING` 尚未关闭，不入池。

#### D7 写入冻结

`capa_d7_action_service.py:91` `_assert_d7_stage` 现仅允许 `D7_PREVENTION`。新状态 `D7_COMPLETED`+ 自然被 `!= D7_PREVENTION` 拦截，D7 编辑被冻结。**无需改动。**

#### 审批权限闸（改为基于边的检查）

`backend/app/api/capa.py:182` `require_close_permission` 现在解析 body **之前**按「当前状态」拦截（行 191：`capa.status in ["D7_PREVENTION","D8_CLOSURE"]` 需 APPROVE）。这会错误地把 `D7_PREVENTION→D7_COMPLETED`（field_qe 可推进）也锁成 APPROVE。改为**解析 `AdvanceRequest.target_state` 后基于边做权限检查**：

```python
# require_close_permission 改为 require_advance_permission
async def require_advance_permission(
    report_id, body: AdvanceRequest | None = None,
    scope = Depends(get_request_scope), db = Depends(get_db),
) -> tuple[RequestScope, Any]:
    capa = await capa_service.get_capa(db, report_id)
    if capa is None: raise HTTPException(404, ...)
    check_factory_access(capa.factory_id, scope)
    target = body.target_state if body else None
    # APPROVE 边：D8_APPROVAL_PENDING→D8_CLOSURE（审批）、→D7_PREVENTION（驳回）、D8_CLOSURE→ARCHIVED（归档）
    approve_edges = (
        (EightDState.D8_APPROVAL_PENDING.value, EightDState.D8_CLOSURE.value),
        (EightDState.D8_APPROVAL_PENDING.value, EightDState.D7_PREVENTION.value),
        (EightDState.D8_CLOSURE.value, EightDState.ARCHIVED.value),
    )
    if (capa.status, target) in approve_edges:
        level = await get_user_permission(scope.user, Module.CAPA, db)
        if level < PermissionLevel.APPROVE:
            raise HTTPException(403, "审批权限不足")
    else:
        # 所有其他 advance 边至少需 EDIT
        level = await get_user_permission(scope.user, Module.CAPA, db)
        if level < PermissionLevel.EDIT:
            raise HTTPException(403, "编辑权限不足")
    return scope, capa
```

> **D8_CLOSURE→ARCHIVED 的 `target` 解析**：此边 `target_state` 可为 `None`（线性，`_LINEAR_NEXT` 含此边）。`require_advance_permission` 在 `target is None` 时需先用 `_linear_next` 算出 `target=ARCHIVED` 再判边——否则 `(D8_CLOSURE, None)` 不在 `approve_edges`。实现时在权限判断前 `target = target or _linear_next_safe(capa.status)`（`_linear_next_safe` 对无线性边的状态返回 `None`，触发下方 EDIT 默认分支；D8_CLOSURE 返回 ARCHIVED 命中 APPROVE）。

权限矩阵：
- D7_PREVENTION→D7_COMPLETED、D7_COMPLETED→D8_GATE_PENDING、D8_GATE_PENDING→D8_APPROVAL_PENDING：**EDIT**（field_qe 可）
- D8_APPROVAL_PENDING→D8_CLOSURE（审批）、D8_APPROVAL_PENDING→D7_PREVENTION（驳回）：**APPROVE**（8D 团队负责人 / manager）
- D8_CLOSURE→ARCHIVED（归档）：**APPROVE**（归档是严肃操作，沿用现有 `require_close_permission` 对 D8_CLOSURE 的 APPROVE 闸）
- D1→...→D6→D7_PREVENTION：**EDIT**

### 2. 闸口逻辑与 `advance_capa` 服务重构

`advance_capa` 现为「线性 next + D7→D8 特殊闸 + D4→D5 已验证根因检查」。引入 3 个新状态 + 驳回分支后，改为**显式 `target_state` 驱动的 per-edge 闸口分发**，弃用无法表达分支的 `transitions` 索引列表。

#### `advance_capa(db, capa, user_id, req)` 新结构

```python
current = EightDState(capa.status)
target = req.target_state  # 显式；None = 线性 next（D1→D6→D7_PREVENTION、D8→ARCHIVED 便利）

if target is None:
    target = _linear_next(current)  # 仅 D1→D2→...→D6→D7_PREVENTION、D8→ARCHIVED；壳/分支状态 raise
```

`_linear_next` 对壳/分支状态（`D7_PREVENTION`、`D7_COMPLETED`、`D8_GATE_PENDING`、`D8_APPROVAL_PENDING`）**直接 raise**，强制前端显式传 `target_state`：

```python
_LINEAR_NEXT = {
    EightDState.D1_TEAM: EightDState.D2_DESCRIPTION,
    EightDState.D2_DESCRIPTION: EightDState.D3_INTERIM,
    EightDState.D3_INTERIM: EightDState.D4_ROOT_CAUSE,
    EightDState.D4_ROOT_CAUSE: EightDState.D5_CORRECTION,
    EightDState.D5_CORRECTION: EightDState.D6_VERIFICATION,
    EightDState.D6_VERIFICATION: EightDState.D7_PREVENTION,
    EightDState.D8_CLOSURE: EightDState.ARCHIVED,
}
def _linear_next(current: EightDState) -> EightDState:
    if current not in _LINEAR_NEXT:
        raise ValueError(f"状态 {current.value} 需显式传 target_state，不可线性推进")
    return _LINEAR_NEXT[current]

if not can_transition(current, target):
    raise ValueError(f"Cannot transition from {capa.status} to {target.value}")

# per-edge 闸口分发
if current == D7_PREVENTION and target == D7_COMPLETED:
    await _d7_completion_gate(db, capa)           # node-action 完整性（原 _d7_to_d8_gate 逻辑）
    # savepoint 内抽 d7 lessons（fail-closed）
elif current == D8_GATE_PENDING and target == D8_APPROVAL_PENDING:
    pass                                           # 01.7 接入文档门禁；本切片直通
elif current == D8_APPROVAL_PENDING and target == D8_CLOSURE:
    pass                                           # 权限由 require_advance_permission 强制；闸口即「审批」
elif current == D8_APPROVAL_PENDING and target == D7_PREVENTION:
    if not req.reject_reason or not req.reject_reason.strip():
        raise ValueError("驳回需填写理由")
    # 状态回退在下方统一 mutation
elif current == D4_ROOT_CAUSE and target == D5_CORRECTION:
    # 现有已验证根因检查（is_verified=True 且 root_cause_text 绑定当前 d4_root_cause），逻辑不变
    ...
# D1→D2、D2→D3、D3→D4、D5→D6、D6→D7_PREVENTION、D8→ARCHIVED：无闸口

# 状态 mutation + TRANSITION 审计（现有）
old_status = capa.status
capa.status = target.value
db.add(AuditLog(action="TRANSITION", changed_fields={old, new}, operated_by=user_id))

# 审批/驳回专项审计
if current == D8_APPROVAL_PENDING and target == D8_CLOSURE:
    db.add(AuditLog(action="D8_APPROVED", operated_by=user_id))
elif current == D8_APPROVAL_PENDING and target == D7_PREVENTION:
    db.add(AuditLog(action="D8_REJECTED",
                    changed_fields={"reject_reason": req.reject_reason},
                    operated_by=user_id))
```

> **审计命名与故事契约的对齐范围**：故事 01.3 契约（行 112）列了 `D4_VERIFICATION_PASSED`/`D4_VERIFICATION_FAILED`、`D7_NODE_ACTION_CREATED`、`D8_APPROVAL_PENDING`、`D8_APPROVED`/`D8_REJECTED`。本切片只**新增** `D8_APPROVED`/`D8_REJECTED`（与契约一致）。其余命名（`RC_VERIFY` vs `D4_VERIFICATION_*`、`D7_NODE_CONFIRMED/SKIPPED` vs `D7_NODE_ACTION_CREATED`、`TRANSITION` vs `D8_APPROVAL_PENDING`）是**全 01.3 故事范围内的既有差异**，不属本状态机切片——归 01.3 的 method 枚举/回退计数器切片统一对齐审计命名。本切片不擅自改既有审计字面量，避免跨切片语义混乱。

#### `_d7_to_d8_gate` 重命名

`_d7_to_d8_gate` → `_d7_completion_gate`，挂载点从 `D7_PREVENTION→D8_CLOSURE` 改为 `D7_PREVENTION→D7_COMPLETED`。其逻辑（FMEA 完整性 + per-rec action 处置 + stale hash 检测）完全不变——这正是故事要求的「D7 node-action 完整性」闸口。原 D7→D8 分支整段删除。D7 lessons 抽取随之移到 D7 完成时。

#### `AdvanceRequest` schema 变更

`backend/app/schemas/capa.py`：

```python
class AdvanceRequest(BaseModel):
    target_state: EightDState | None = None   # 显式；None = 线性 next（D1→D6→D7_PREVENTION、D8→ARCHIVED）
```

### 3. `node-action.status` 字段 + 迁移

**语义区分**（故事行 54、92）：

- `action`（现有）= 工程师对推荐的*处置*：`confirmed`/`skipped`/`auto_filled`
- `status`（新）= node-action 的*执行生命周期*：`pending` → `executed` → `verified`

两者正交。本切片止于 `pending` 创建（故事行 54、92 明确）。

#### 模型变更

`backend/app/models/capa.py` `CapaD7NodeAction`：

```python
status: Mapped[str] = mapped_column(String(20), default="pending", nullable=False)
```

#### 迁移 `backend/alembic/versions/20260708_d7_node_action_status.py`

   - PostgreSQL 在单语句内加 `NOT NULL DEFAULT` 列时，用默认值回填所有现存行，无需单独 backfill。
2. 降级：`DROP COLUMN status`。

#### Schema 变更

`backend/app/schemas/capa_verification.py`：

- `D7NodeActionCreate`：**不改**——`status` 不由客户端创建时设置，恒由模型默认 `pending`
- `status` 用 `str`（非 `Literal["pending"]`），为后续故事 `executed`/`verified` 留扩展，避免过早枚举（YAGNI）

#### 服务层

#### 闸口交互

`_d7_completion_gate` 查 `action.in_(["confirmed","skipped","auto_filled"])`，**不查 `status`**。符合故事行 58：「01.7 的 D8 门禁只查文档更新，不查 node-action 验证状态。」`status`-agnostic 行为已正确。

#### `update_capa` 冻结字段后端约束（防 direct API 修改）

### 4. 前端状态处理

#### `stepIndex` 映射（折叠壳状态到 D7/D8 主步骤）

### 5. 状态→步骤与草稿映射（`available_steps` + `_STEP_PRECONDITIONS`）

3 个新状态进入后，现有映射会返回空或不认识状态：

- `backend/app/api/capa.py:550` `status_to_steps`：新状态无条目 → `available_steps: []`
- `backend/app/services/capa_draft_service.py:33` `_STEP_PRECONDITIONS` + 行 43 `_STATUS_ORDER`：新状态无条目 → 草稿 min-status 查找失败

**决策（D8 冻结口径）**：`D8_APPROVAL_PENDING` 期间 `d8_closure` 文本**冻结**（已提交审批，不可改；要改先驳回回 D7_PREVENTION）。故新状态的 `available_steps` 返回 `[]`（无步骤可编辑）：

```python

    "D2_DESCRIPTION": ["d2"], "D3_INTERIM": ["d3"], "D4_ROOT_CAUSE": ["d4"],
    "D5_CORRECTION": ["d5"], "D6_VERIFICATION": ["d6"], "D7_PREVENTION": ["d7"],
    "D8_CLOSURE": ["d8"],
    # 新壳状态：无可用编辑步骤（D7 已冻结、D8 待审批冻结）
    "D7_COMPLETED": [], "D8_GATE_PENDING": [], "D8_APPROVAL_PENDING": [],
}
```

`_STATUS_ORDER` 加入 3 个新状态（插在 D7_PREVENTION 之后、D8_CLOSURE 之前），保持线性序：

```python
_STATUS_ORDER = [
    "D1_TEAM", "D2_DESCRIPTION", "D3_INTERIM", "D4_ROOT_CAUSE",
    "D5_CORRECTION", "D6_VERIFICATION", "D7_PREVENTION",
    "D7_COMPLETED", "D8_GATE_PENDING", "D8_APPROVAL_PENDING",
    "D8_CLOSURE", "CLOSED", "ARCHIVED",

```

`_STEP_PRECONDITIONS` 的 `d7`/`d8` `min_status` 不变（`d7` 仍 `D7_PREVENTION`、`d8` 仍 `D8_CLOSURE`）——因 D7_COMPLETED+ 时 `available_steps=[]`，草稿入口在前端已被隐藏，min-status 查找不会触发。若后续 01.7 要在 `D8_GATE_PENDING` 允许编辑 d8，再放宽 `d8.min_status`。

## 风险与取舍

- **`is_capa_open` 双 API**：拆 `is_capa_open_value(status)`（Python bool）+ `capa_open_clause(column)`（SQL 表达式），因 `.notin_(...)` 是 SQL 表达式非 Python bool。替换约 12 处时需逐一核对语义：表示「未关闭」计数的换 helper；表示「必须已关闭」的断言（如 `customer_audit_service.py:314` 要求 linked CAPA 必须 `D8_CLOSURE`）保持精确不换。
- **基于边的权限检查**：`require_close_permission` → `require_advance_permission`，解析 `target_state` 后按边判 EDIT/APPROVE。APPROVE 边：`D8_APPROVAL_PENDING→D8_CLOSURE`（审批）、`→D7_PREVENTION`（驳回）、`D8_CLOSURE→ARCHIVED`（归档）；其余 advance 需 EDIT。比按当前状态拦更精确，但依赖需读 body（FastAPI 依赖可解析同路径 body），且 `target_state=None` 时需先 `_linear_next` 算出 target 再判边。
- **`update_capa` 冻结字段后端约束**：`update_capa` 现对任意 `hasattr` 字段直接 `setattr`，仅靠 `available_steps: []` + 前端隐藏不能防 direct API 修改。补 `_FROZEN_FIELDS_BY_STATUS` 守卫：`d7_prevention` 在 D7_COMPLETED+ 冻结、`d8_closure` 在 D8_GATE_PENDING/D8_APPROVAL_PENDING 冻结。D8_CLOSURE 态 `d8_closure` 不冻结（关闭后可补报告）。是真正的安全边界，前端隐藏只是 UX。
- **`_linear_next` 对壳/分支状态 raise**：强制 D7_PREVENTION/D7_COMPLETED/D8_GATE_PENDING/D8_APPROVAL_PENDING 显式传 `target_state`，杜绝「恰好返回 D7_COMPLETED」的隐式依赖。D8_CLOSURE→ARCHIVED 仍走线性（`_LINEAR_NEXT` 含此边），但权限判 APPROVE。
- **D8_CLOSURE→ARCHIVED 走 UI 归档按钮 + APPROVE**：不再 hide D8_CLOSURE，详情页对 `canApprove` 显示「归档」按钮；归档是严肃操作沿用 APPROVE（与现有 `require_close_permission` 对 D8_CLOSURE 的闸一致）。
- **Steps 折叠而非扩展**：壳状态（D7_COMPLETED/D8_GATE_PENDING/D8_APPROVAL_PENDING）+ ARCHIVED 折叠到 D7/D8 主步骤索引（`stepIndex`），`stepItems` 维持 8 项，用 `stepSubStatus` 标记「待审批」/「已归档」等子状态。避免 Steps 变 9+ 碎步；`currentStep` 恒在 0..7 对 8 项数组不越界。
- **D8_APPROVAL_PENDING 冻结 d8_closure**：已提交审批不可改，要改先驳回回 D7_PREVENTION。`available_steps` 对 3 个壳状态返回 `[]`。语义更严，审批者补充内容须先驳回——可接受，避免审批中内容漂移。
- **D7 面板只读扩展**：渲染条件从 `status === "D7_PREVENTION"` 扩到 `D7_PREVENTION..D8_APPROVAL_PENDING`，编辑控件仅 D7_PREVENTION 启用。审批者在 D8_APPROVAL_PENDING 可见 D7 内容。
- **`D8_GATE_PENDING` 直通**：01.7 接入前为占位；若 01.7 延期，存在「文档门禁空转」窗口。可接受——本切片不验门禁内容。
- **`target_state` 显式化**：分支流强制前端传显式状态，比隐式 `next` 更安全（防误推进），但前端调用点增多。线性流仍可用 `null` 便利。D7 skip 路径也须显式传 `target_state: "D7_COMPLETED"`。
- **`status` 字段不用 Literal**：为后续故事留扩展，但本切片无运行时枚举校验（仅模型 default）。可接受——本切片只要求 `pending` 存在。
- **审计命名与故事契约既有差异**：故事 01.3 契约（行 112）的审计事件名（`D4_VERIFICATION_*`、`D7_NODE_ACTION_CREATED`、`D8_APPROVAL_PENDING`）与现有代码（`RC_VERIFY`、`D7_NODE_CONFIRMED/SKIPPED`、`TRANSITION`）不一致。本切片只新增 `D8_APPROVED`/`D8_REJECTED`（与契约一致），不对齐其余既有命名——归 01.3 的 method 枚举/回退计数器切片统一处理，避免跨切片语义混乱。
