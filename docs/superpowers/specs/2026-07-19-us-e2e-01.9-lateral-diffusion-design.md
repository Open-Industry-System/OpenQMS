# US-E2E-01.9 横向扩散预警与通知 — Design

**日期**: 2026-07-19  
**状态**: 设计定稿 v4（复查：decide/rerun `FOR UPDATE` 串行化；E2E 独立 CAPA seed；文档笔误）  
**子故事**: `docs/user-stories/US-E2E-01-capa-8d-closed-loop/US-E2E-01.9-lateral-diffusion.md`（定稿 v2，2026-07-21）  
**AI_REQUIRED**: true（有类似产品命中时：无 LLM 凭证 → BLOCKED 阻断 D8 关闭；LLM 调用失败 → FAILED 阻断关闭。无命中时不调 LLM，关闭可成功——与子故事 v2 一致）  
**Gap**: `docs/superpowers/specs/2026-07-08-us-e2e-01-gap-analysis.md` §01.9  
**架构**: 方案 A — 同步检查 + 决策 API（fail-closed；通知只落库，不发渠道）

> v2 修订：decide 全量一次；收件人真实角色；四依据钉死；E2E 四依据；空命中契约。  
> v3 修订：UserFactory 收件人；依据 4 A∪B；E2E 四值并集；SKIPPED 含 skip_reason；故事 v2。  
> v4 修订（复查）：  
> 1. decide/rerun 同事务 `SELECT check … FOR UPDATE`，锁后重读 notifications；并发 notify-vs-skip、decide-vs-rerun 测试必做。  
> 2. E2E 至少 **三张** 四依据命中 CAPA（notify / skip / blocked 各一）+ EMPTY；禁止单单顺序耦合。  
> 3. 决策摘要去掉「须同步故事」过时措辞；§16 表格 `skipped / error` 修 Markdown。

## 1. 目标

D8 审批关闭且 01.8 知识沉淀成功后，系统在**同一事务**内自动检查是否存在可能受同一根因/失效模式影响的**类似产品**（4 依据并集），有则：

1. 落库检查结果（含命中依据 + LLM 建议更新方向）
2. 关闭响应/详情投影可驱动前端弹窗，询问是否通知相关产品负责人
3. 用户确认通知或不通知均留痕；通知状态可追踪

形成「当前 8D 关闭 → 横向评估 → 可选通知」闭环，避免同类风险在其他产品线上重蹈覆辙。

**非目标**（本轮不做）：

- 通知真实渠道（邮件 / webhook / 站内信发送）——只生成可追踪记录
- 类似产品负责人的后续更新闭环跟踪
- 横向扩散的自动强制更新（不改他线 FMEA/CP）
- 语义/向量相似度匹配（依据 2 仅规范化精确文本匹配）
- 改动 01.2 `SameTypeProductKBSource` 行为（可复用 SQL 片段，独立服务）
- verify skill 拆分（另任务）
- 按 type 分批 decide（本轮一次全量决策）

## 3. 决策摘要

| 决策 | 选择 | 理由 |
|---|---|---|
| 架构 | **方案 A：同步检查 + 决策 API** | 与 01.8 fail-closed 一致；本轮无真实渠道 |
| 触发 | **`D8_APPROVAL_PENDING→D8_CLOSURE` 同事务**；顺序 01.8 → 01.9 → 置状态 | 关闭即有完整结果 |
| 产品粒度 | **按 `product_type` 聚合**；`product_lines[]` 展开 | 系统无独立 products 表 |
| 工厂范围 | **同租户跨工厂** | 横向扩散才有意义 |
| 收件人 | **`UserProductLine` ∩ 角色白名单 ∩ 工厂范围（`UserFactory`/`get_user_factory_ids`）** | 对齐 `factory_scope.py`；角色 `field_qe`/`planning_qe`/`manager` via `users.role_id` |
| LLM 职责 | **仅 `suggestion_direction`**；4 依据全确定性 | 可测 |
| 空命中 | **`status=empty`，不调 LLM，关闭成功** | 无 AI 工作可做 ≠ blocked；与子故事 v2 一致（§16） |
| 有命中无 LLM / LLM 失败 | **阻断关闭**；`outcome=blocked` vs `failed`，`stage=lateral_diffusion` | AI_REQUIRED |
| Decide | **全量一次**：body **无** `product_type_codes`；覆盖 check 全部 type | 禁止部分决策锁死剩余 type |
| Decide / Rerun 并发 | **同事务 `SELECT … FOR UPDATE` check 行**；锁后重读 notifications / status | 防 notify∥skip 双成功、decide∥rerun 脏写 |
| Decide 幂等 | 锁后已有 notification → 409；rerun 锁后已 decide → 409 | 与并发锁配合 |
| 命中上限 | type 组 ≤50，每组 PL ≤30，`truncated` | 防跨厂爆炸 |

## 4. 数据模型

### 4.1 `capa_lateral_diffusion_checks`

一次 D8 关闭对应一次检查（按 `capa_id` 幂等）。

```python
class CapaLateralDiffusionCheck(Base):
    __tablename__ = "capa_lateral_diffusion_checks"
    __table_args__ = (
        UniqueConstraint("capa_id", name="uq_lateral_check_capa"),
    )

    check_id: Mapped[uuid.UUID]  # uuid5(NAMESPACE_URL, f"lateral_check:capa:{capa_id}")
    capa_id: Mapped[uuid.UUID]   # FK capa_eightd.report_id ON DELETE CASCADE
    factory_id: Mapped[uuid.UUID]  # 源 8D 工厂

    source_product_line_code: Mapped[str]
    source_product_type_code: Mapped[str | None]

    similar_products: Mapped[list]  # JSONB, 见 4.3
    status: Mapped[str]             # done | empty
    llm_status: Mapped[str]         # done | skipped（empty 时）
    truncated: Mapped[bool] = False
    created_at / updated_at: timestamptz
```

### 4.2 `capa_lateral_notifications`

```python
class CapaLateralNotification(Base):
    __tablename__ = "capa_lateral_notifications"

    notification_id: Mapped[uuid.UUID]
    check_id: Mapped[uuid.UUID]  # FK checks
    capa_id: Mapped[uuid.UUID]

    product_type_code: Mapped[str]
    product_line_code: Mapped[str | None]
    # notify：具体 PL；skip：NULL（每个 type 一行）

    factory_id: Mapped[uuid.UUID | None]  # 目标 PL 厂；skip 可 null

    recipient_user_id: Mapped[uuid.UUID | None]
    recipient_label: Mapped[str]

    decision: Mapped[str]   # notified | skipped
    status: Mapped[str]     # notified | pending | processed
    # notify+有人 → notified；notify+无人 → pending；skip → processed

    skip_reason: Mapped[str | None]
    payload: Mapped[dict]   # JSONB

    decided_by: Mapped[uuid.UUID]
    decided_at: Mapped[datetime]
    created_at: Mapped[datetime]
```

**唯一性**：

- notify：`UNIQUE NULLS NOT DISTINCT (check_id, product_type_code, product_line_code, recipient_user_id)`
- skip：`UNIQUE (check_id, product_type_code) WHERE decision = 'skipped'`（部分唯一索引）

### 4.3 `similar_products[]` 元素

故事 `product_id` → **`product_type_code`**。

```json
{
  "product_type_code": "DC-DC",
  "product_type_name": "DC-DC 转换器",
  "hit_criteria": ["same_product_type", "shared_fmea_mode"],
  "suggestion_direction": "…",
  "product_lines": [
    {"code": "DC-DC-200", "factory_id": "<uuid>", "name": "…"}
  ],
  "evidence": {
    "shared_fmea_mode": [
      {"fmea_id": "<uuid>", "node_id": "…", "node_type": "FailureMode", "matched_text": "…"}
    ],
    "shared_control_plan": [
      {"cp_id": "<uuid>", "characteristic_keys": ["…"]}
    ],
    "same_supplier_material": [
      {"supplier_id": "<uuid>", "material_code": "…"}
    ]
  }
}
```

- 排除源 `product_line_code`。
- 无 type 的 PL：`product_type_code = "unknown"`，`product_type_name = "未分类"`。
- `hit_criteria` 枚举：`same_product_type` | `shared_fmea_mode` | `shared_control_plan` | `same_supplier_material`。

### 4.4 CAPA 投影 `lateral_diffusion`

```json
"lateral_diffusion": {
  "check_id": "<uuid>",
  "status": "done | empty",
  "llm_status": "done | skipped",
  "truncated": false,
  "similar_products": [ /* 4.3 */ ],
  "decision": null | "notified" | "skipped",
  "notifications": [
    {
      "notification_id": "<uuid>",
      "product_type_code": "DC-DC",
      "product_line_code": "DC-DC-200",
      "recipient_label": "engineer",
      "decision": "notified",
      "status": "notified"
    }
  ]
}
```

- 无 check → `null`。
- `decision`：无 notification → `null`；存在任一行 `decision=notified` → `notified`；否则全为 skip → `skipped`。  
  （因 decide 全量一次，不存在「部分完成」中间态。）

## 5. 关闭钩子与错误契约

### 5.1 顺序

```
advance_capa(D8_APPROVAL_PENDING → D8_CLOSURE):
  1. sink_capa_on_close(...)                          # 01.8
  2. run_lateral_diffusion_check(db, capa, user_id)   # 01.9
  3. capa.status = D8_CLOSURE
  4. AuditLog TRANSITION + D8_APPROVED
  5. LATERAL_DIFFUSION_CHECKED（step 2 内）
```

任一步抛错 → 整笔回滚。

### 5.2 异常

| 异常 | API | body |
|---|---|---|
| `LateralBlockedError` | 422 | `{ "outcome": "blocked", "stage": "lateral_diffusion", "message": "…" }` |
| `LateralFailedError` | 422 | `{ "outcome": "failed", "stage": "lateral_diffusion", "message": "…" }` |

| 条件 | 结果 |
|---|---|
| 确定性匹配异常 | `failed` |
| `similar_products` 非空且无 LLM 凭证 / `build_client` 失败 | `blocked` |
| `similar_products` 非空且 LLM 调用/JSON 校验失败 / 缺 type 项 | `failed` |
| `similar_products` 为空 | 不调 LLM；`status=empty`；**不抛** |

### 5.3 幂等

- `check_id = uuid5(NAMESPACE_URL, f"lateral_check:capa:{report_id}")`
- upsert 同一 check 行
- 已有 notification 时：advance 路径仍可刷新 check（少见）；**decide 409**；**rerun 409**

## 6. 四依据算法（确定性，全部钉死）

### 6.1 文本规范化

所有参与精确匹配的字符串统一：

```
normalize(s) = collapse_whitespace(s.strip().lower())
```

空串规范化后丢弃，不进入集合。

### 6.2 输入快照（源 8D）

| 输入 | 精确定义 |
|---|---|
| `source_pl` | `capa.product_line_code` |
| `source_factory` | `capa.factory_id` |
| `source_type` | `SELECT product_type_code FROM product_lines WHERE code = source_pl`（可 null） |
| `source_supplier` | `capa.supplier_id`（可 null） |
| `fmea_mode_texts` | §6.2.1 |
| `cp_keys` | §6.2.2 |
| `material_codes` | §6.2.3 |

#### 6.2.1 源失效模式/根因文本 `fmea_mode_texts`

1. 收集关联 FMEA id 集合（与 01.4 同源，三者并集）：  
   - `capa.fmea_ref_id`（若非空）  
   - D4 推荐采纳 / 验证记录中可解析的 `source_ref` FMEA id（若实现侧已有 01.4 解析 helper 则复用；无则仅 header `fmea_ref_id` + D7 node-action 的 `fmea_id`）  
   - `capa_d7_node_action` 中 `action ∈ {confirmed, auto_filled}` 的 `fmea_id`
2. 对这些 FMEA 读 `fmea_documents.graph_data.nodes`：  
   - 仅 `node["type"] ∈ {"FailureMode", "FailureCause"}`  
   - 取 `node.get("name")`（**不用** description，避免噪声；实现锁死 name-only）  
   - `normalize` 后加入集合
3. 集合空 → 依据 2 对源侧跳过

#### 6.2.2 源控制计划特性键 `cp_keys`

1. 源 PL 上 `control_plans`：`product_line_code = source_pl` 且 `status = 'approved'`（**仅 approved**；draft/rework 不参与）  
2. 其 `control_plan_items` 每行生成 **一个** 特性键（非空字段才拼接）：

```
key = normalize(
  "|".join(filter(None, [
    item.characteristic_no,
    item.product_characteristic,
    item.process_characteristic,
    item.special_class,
  ]))
)
```

3. 丢弃空 key；集合空 → 依据 3 跳过

#### 6.2.3 源物料码 `material_codes`

**唯一权威源**：当前 CAPA 最新 D3 影响报告批次。

1. 取 `CapaD3ImportRun`：`capa_id = capa.report_id` 且 `factory_id = capa.factory_id` 且 `is_current = true`  
2. 取 `CapaD3ImpactReport`：`run_id` 同上且 `is_current = true` 且 `status = 'done'`  
3. 对 `report.batches[]` 每项：取 `batch["material_code"]`，`normalize` 后加入集合  
   - D3 服务已把 inventory/shipment 的 `material_code` 与 IQC 的 `part_no` **统一写入** `batches[].material_code`（见 `capa_d3_containment_service._material_of` / `_compute_batches`）  
   - **禁止**再从 `d3_affected_lots`（仅 lot_no 列表投影）反推物料  
4. 集合空 → 依据 4 跳过（即使有 `supplier_id`）

### 6.3 范围

- 当前租户 schema 内全部 `product_lines` 且 `is_active = true`
- 排除 `code == source_pl`
- 跨 `factory_id` 允许；不跨租户（schema 隔离）

### 6.4 依据细则

#### 依据 1 — `same_product_type`

- **条件**：`source_type is not null`
- **命中 PL**：`product_lines.product_type_code = source_type` 且 `code ≠ source_pl` 且 `is_active`
- **evidence**：无额外结构（type 级命中即可）；PL 进入 `product_lines[]`

#### 依据 2 — `shared_fmea_mode`

- **条件**：`fmea_mode_texts` 非空
- **候选 FMEA**：`fmea_documents` 满足  
  - `product_line_code ≠ source_pl`  
  - `status = 'approved'`（**仅 approved**；draft / in_review / rework / archived 不参与）  
- **匹配**：图节点 `type∈{FailureMode,FailureCause}` 的 `normalize(name)` ∈ `fmea_mode_texts`
- **evidence 项**：`{fmea_id, node_id, node_type, matched_text}`（`matched_text` 为规范化后文本）  
- 该 FMEA 的 `product_line_code` → 命中 PL

#### 依据 3 — `shared_control_plan`

- **条件**：`cp_keys` 非空
- **候选 CP**：`control_plans.status = 'approved'` 且 `product_line_code ≠ source_pl`
- **匹配**：item 按 §6.2.2 规则生成的 key ∈ `cp_keys`
- **evidence 项**：`{cp_id, characteristic_keys: [匹配到的 key, …]}`  
- CP 的 `product_line_code` → 命中 PL

#### 依据 4 — `same_supplier_material`

- **跳过条件（仅此）**：`source_supplier is null` **或** `material_codes` 为空 → 本依据整段不贡献命中（不报错）。  
  **禁止**因路径 A 或路径 B 单独无行而跳过整依据。
- **命中路径（两条，结果 = A ∪ B）**：

  **A. IQC 检验**  
  `iqc_inspections` 满足：  
  - `supplier_id = source_supplier`  
  - `normalize(part_no) ∈ material_codes`（`part_no` 空则跳过该行）  
  - `product_line_code` 非空且 `≠ source_pl`  
  → 命中 PL = `product_line_code`；evidence `{supplier_id, material_code: normalize(part_no)}`

  **B. IQC 物料主数据**  
  `iqc_materials` 满足：  
  - `normalize(part_no) ∈ material_codes`  
  - `status = 'active'`  
  - `product_line_code ≠ source_pl`  
  - **且** 存在至少一条 `iqc_inspections`：`material_id = materials.material_id` 且 `supplier_id = source_supplier`  
    （物料主数据本身无 supplier_id，必须经检验行绑定供应商，避免「同料号不同供方」误命中）  
  → 命中 PL = `iqc_materials.product_line_code`；evidence 同上

- A 有命中、B 为空 → **仍命中**（仅 A）；反之亦然；A、B 皆空 → 本依据无 PL（其他依据不受影响）。

### 6.5 聚合与截断

1. PL 级累积 `hit_criteria[]` + `evidence`（多依据并集）  
2. 按 `product_type_code`（缺省 `"unknown"`）分组 → `similar_products[]`  
3. 稳定排序：`product_type_code asc`，组内 `product_lines.code asc`  
4. 截断：最多 50 个 type 组；每组最多 30 条 PL；超出设 `truncated=true`

### 6.6 LLM 建议方向

- 仅当 `similar_products` 非空  
- `complete_json` → `{ "items": [ { "product_type_code", "suggestion_direction" } ] }`  
- **必须**覆盖全部命中 type；缺项 → `failed`  
- 写回各元素 `suggestion_direction`

### 6.7 写库 + 审计

```
upsert capa_lateral_diffusion_checks
AuditLog LATERAL_DIFFUSION_CHECKED {
  check_id, similar_count, status, truncated,
  product_type_codes, hit_criteria_union  # 便于 E2E 断言四依据
}
```

## 7. API

| 方法 | 路径 | 权限 | 行为 |
|---|---|---|---|
| （既有） | `POST /api/capa/{id}/advance` → D8_CLOSURE | `canApprove('capa')` | 01.8→01.9；响应含投影 |

| 新增 | `POST /api/capa/{id}/lateral-diffusion/decide` | `canEdit('capa')` | §7.1 |
| 新增 | `POST /api/capa/{id}/lateral-diffusion/rerun` | `canEdit('capa')` | §7.2 |

### 7.1 Decide（全量一次 + 行锁）

**Body（仅此形状）：**

```json
{
  "decision": "notify" | "skip",
  "skip_reason": "string, required if skip（非空白）"
}
```

**事务内顺序（锁死）：**

```
1. 加载 CAPA（工厂可见性 / 状态 ∈ {D8_CLOSURE, ARCHIVED}）
2. SELECT capa_lateral_diffusion_checks
     WHERE capa_id = :id
     FOR UPDATE          -- 串行化 decide 与 rerun；无行 → 404
3. 锁后重读：若 EXISTS notification WHERE check_id = … → 409
4. 若 check.status = empty → 422
5. 禁止 body 含 product_type_codes（有则 422）
6. 写 notifications（notify 或 skip 全量 type）+ 对应审计
7. commit
```

- 一次决策覆盖 check 内 **全部** `similar_products[].product_type_code`  
- **禁止**仅在应用层「先查后插」而无 `FOR UPDATE`：并发 notify∥skip 会双双通过步骤 3 的无锁读，插入并存的 notified 与 skipped 行，并同时写 SENT + SKIPPED 审计  
- 唯一索引（§4.2）是最后防线，**不能**代替行锁（notify 与 skip 行形状不同，UQ 挡不住异决策并存）

**notify：** 对每个 type 下每个 PL 解析收件人（§8）写行；审计：

```
LATERAL_NOTIFICATION_SENT {
  check_id, decision: "notified",
  product_type_codes: [...],
  notification_count: N,
  notification_ids: [...]  # 可截断摘要
}
```

**skip：** 每个 type 一行（`product_line_code=null`），共享同一 `skip_reason`；审计：

```
LATERAL_NOTIFICATION_SKIPPED {
  check_id, decision: "skipped",
  skip_reason: "<必填非空原文>",   # 故事字段级契约必含
  product_type_codes: [...],
  notification_count: N
}
```

**响应：** 完整 `lateral_diffusion`（`decision` 非 null）。

### 7.2 Rerun（同行锁）

**事务内顺序（锁死）：**

```
1. CAPA 状态 ∈ {D8_CLOSURE, ARCHIVED}
2. SELECT check WHERE capa_id = :id FOR UPDATE  -- 与 decide 同一锁点
   （无行：允许新建 check，先 INSERT 再锁或使用 capa 行锁；实现须保证与 decide 互斥）
3. 锁后：若 EXISTS notification → 409（无 force）
4. 重跑 §6，upsert 同一 check_id 行（覆盖 similar_products / status / llm_status）
5. commit
```

- 有命中且无 LLM → 与关闭边相同 blocked/failed  
- **并发**：decide 持锁期间 rerun 阻塞；rerun 持锁期间 decide 阻塞；后到者见已 decide / 新 check 后按上表 409 或成功

## 8. 收件人解析

对目标 `product_line_code`（记其 `pl.factory_id = target_factory_id`），候选用户须**同时**满足：

### 8.1 产品线

`user_product_lines.product_line_code = :pl` 且 `users.is_active = true`。

### 8.2 角色

`users.role_id → role_definitions.id`，且  
`role_key ∈ {field_qe, planning_qe, manager}`  
（**无** `user_roles` 多对多；**不含** `customer_qe` / `supplier_qe` / `viewer` / `admin`）。

### 8.3 工厂范围（对齐 `factory_scope.py`，锁死）

对每个候选用户 `u`：

1. 若请求/服务侧判定 `has_group_admin=True`（与 `RequestScope` / `resolve_factory_scope` 相同来源：对 Module.GROUP 具备 admin 级权限）→ **可见全部工厂**，通过。实现时复用既有 helper，禁止另写一套 group 判定。  
2. 否则 `user_factory_ids = await get_user_factory_ids(u, db)`（读 `user_factories`）：  
   - 若 **非空**：`target_factory_id ∈ user_factory_ids` 才通过（**优先** `UserFactory`，不看默认 `users.factory_id` 是否等于目标厂——避免漏掉「默认厂 A、另有厂 B 权限」的负责人）。  
   - 若 **为空** 且 `u.factory_id is not null`：仅当 `u.factory_id == target_factory_id` 通过（与 scope 层 3 回退一致）。  
   - 若 **为空** 且 `u.factory_id is null`：**不通过**（scope 层 4：无工厂关联 → 无数据访问）。**禁止**把「`factory_id is null`」当成集团全可见。

伪代码：

```python
async def user_can_receive_for_pl_factory(u, target_factory_id, db) -> bool:
    if has_group_admin(u):  # Module.GROUP level admin
        return True
    fids = await get_user_factory_ids(u, db)
    if fids:
        return target_factory_id in fids
    if u.factory_id is not None:
        return u.factory_id == target_factory_id
    return False
```

- 去重 `(PL, user_id)`  
- ≥1 用户：每用户一行；`status=notified`；`recipient_label=username`  
- 0 用户：一行；`recipient_user_id=null`；`recipient_label="未找到负责人"`；`status=pending`

### 10.1 Seed 数据（`seed_e2e`）
