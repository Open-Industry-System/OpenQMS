# US-E2E-01.9 横向扩散预警与通知 — Design

**日期**: 2026-07-19  
**状态**: 设计定稿 v1  
**子故事**: `docs/user-stories/US-E2E-01-capa-8d-closed-loop/US-E2E-01.9-lateral-diffusion.md`（定稿 v1，2026-07-08）  
**AI_REQUIRED**: true（有类似产品命中时：无 LLM 凭证 → BLOCKED 阻断 D8 关闭；LLM 调用失败 → FAILED 阻断关闭。无命中时不调 LLM，关闭可成功）  
**Gap**: `docs/superpowers/specs/2026-07-08-us-e2e-01-gap-analysis.md` §01.9  
**架构**: 方案 A — 同步检查 + 决策 API（fail-closed；通知只落库，不发渠道）

## 1. 目标

D8 审批关闭且 01.8 知识沉淀成功后，系统在**同一事务**内自动检查是否存在可能受同一根因/失效模式影响的**类似产品**（4 依据并集），有则：

1. 落库检查结果（含命中依据 + LLM 建议更新方向）
2. 关闭响应/详情投影可驱动前端弹窗，询问是否通知相关产品负责人
3. 用户确认通知或不通知均留痕；通知状态可追踪

形成「当前 8D 关闭 → 横向评估 → 可选通知」闭环，避免同类风险在其他产品线上重蹈覆辙。

**非目标**（本轮不做）：

- 通知真实渠道（邮件 / webhook / 站内信发送）——只生成可追踪记录
- 类似产品负责人的后续更新闭环跟踪
- 横向扩散的自动强制更新（不改他线 FMEA/CP）
- 语义/向量相似度匹配（依据 2 仅规范化精确文本匹配）
- 改动 01.2 `SameTypeProductKBSource` 行为（可复用 SQL 片段，独立服务）
- verify skill 拆分（另任务）

## 2. 已有基建（复用，不重造）

| 资产 | 用途 |
|---|---|
| `advance_capa` `D8_APPROVAL_PENDING→D8_CLOSURE` + `sink_capa_on_close` | 关闭边同事务钩子；01.9 挂在 01.8 **之后** |
| `provider_adapter.complete_json` + `build_client` | LLM 生成 `suggestion_direction`（与 01.8 / P1-D 一致） |
| `ProductLine.product_type_code` + `product_types` | 依据 1；命中聚合键 |
| 01.4 FMEA 反查 / `fmea_documents.graph_data` | 依据 2 源/目标失效模式与根因文本 |
| `control_plans` / items | 依据 3 特性键 |
| `capa.supplier_id` + IQC 物料 / D3 受影响物料 | 依据 4 |
| `UserProductLine` + `role_definitions` / `user_roles` | 通知收件人解析 |
| `AuditLog` 约定 | `LATERAL_DIFFUSION_CHECKED` / `LATERAL_NOTIFICATION_*` |
| 01.8 `outcome=blocked\|failed` API 形态 | 关闭失败契约对齐 |

**Gap（对照故事）**：

| 验收 | 现状 | 本设计 |
|---|---|---|
| D8 关闭后自动 4 依据并集检查 | 无；仅有推荐源同类型 KB 检索 | 关闭边 `run_lateral_diffusion_check` |
| 通知提示 + 是否通知 | 无 | FE Modal + decide API |
| 通知状态可追踪 | 无 | `capa_lateral_notifications.status` |
| 审计 | 无 | CHECKED / SENT / SKIPPED |
| 无 LLM BLOCKED | 无 | 有命中且无凭证 → 422 blocked |

## 3. 决策摘要

| 决策 | 选择 | 理由 |
|---|---|---|
| 架构 | **方案 A：同步检查 + 决策 API** | 与 01.8 fail-closed 一致；本轮无真实渠道，不做通知 outbox |
| 触发 | **`D8_APPROVAL_PENDING→D8_CLOSURE` 同事务**；顺序 01.8 → 01.9 → 置状态 | 故事 AI_REQUIRED +「关闭后自动检查」；关闭即有完整结果 |
| 产品粒度 | **按 `product_type` 聚合命中**；`product_lines[]` 展开 | 用户确认；故事 `product_id` 映射为 `product_type_code`（系统无独立 products 表） |
| 工厂范围 | **同租户跨工厂** | 用户确认；`product_types` 跨厂共享，横向扩散才有意义 |
| 收件人 | **目标 PL 的 `UserProductLine` ∩ 角色 QE/manager** | 无 product_type.owner；渠道后续迭代 |
| LLM 职责 | **仅 `suggestion_direction`**；4 依据全确定性 | 可测；无命中不调 LLM |
| 空命中 | **`status=empty`，不调 LLM，关闭成功** | 无 AI 工作可做 ≠ blocked |
| 有命中无 LLM / LLM 失败 | **阻断关闭**；`outcome=blocked` vs `failed`，`stage=lateral_diffusion` | 故事 AI_REQUIRED + FAILED 字面 |
| 通知渠道 | **只落库** | 故事明确渠道后续迭代 |
| Decide 幂等 | **一次性**；已 decide → 409；rerun 仅未 decide | 避免重复通知行 |
| 命中上限 | type 组 ≤50，每组 PL ≤30，截断记 `truncated` | 防跨厂爆炸 |

## 4. 数据模型

### 4.1 `capa_lateral_diffusion_checks`

一次 D8 关闭对应一次检查（按 `capa_id` 幂等）。

```python
class CapaLateralDiffusionCheck(Base):
    __tablename__ = "capa_lateral_diffusion_checks"
    __table_args__ = (
        UniqueConstraint("capa_id", name="uq_lateral_check_capa"),
    )

    check_id: Mapped[uuid.UUID] = mapped_column(UUID(as_uuid=True), primary_key=True)
    # 确定性: uuid5(NAMESPACE_URL, f"lateral_check:capa:{capa_id}")

    capa_id: Mapped[uuid.UUID] = mapped_column(
        UUID(as_uuid=True), ForeignKey("capa_eightd.report_id", ondelete="CASCADE"), nullable=False
    )
    factory_id: Mapped[uuid.UUID] = mapped_column(
        UUID(as_uuid=True), ForeignKey("factories.id", ondelete="RESTRICT"), nullable=False
    )  # 源 8D 工厂（审计归属）

    source_product_line_code: Mapped[str] = mapped_column(String(20), nullable=False)
    source_product_type_code: Mapped[str | None] = mapped_column(String(20), nullable=True)

    similar_products: Mapped[list] = mapped_column(JSONB, nullable=False, default=list)
    # 见 4.3

    status: Mapped[str] = mapped_column(String(16), nullable=False)
    # done | empty

    llm_status: Mapped[str] = mapped_column(String(16), nullable=False)
    # done | skipped（empty 时）

    truncated: Mapped[bool] = mapped_column(Boolean, nullable=False, default=False)
    created_at / updated_at: timestamptz
```

### 4.2 `capa_lateral_notifications`

```python
class CapaLateralNotification(Base):
    __tablename__ = "capa_lateral_notifications"

    notification_id: Mapped[uuid.UUID] = mapped_column(UUID(as_uuid=True), primary_key=True)

    check_id: Mapped[uuid.UUID] = mapped_column(
        UUID(as_uuid=True),
        ForeignKey("capa_lateral_diffusion_checks.check_id", ondelete="CASCADE"),
        nullable=False,
    )
    capa_id: Mapped[uuid.UUID] = mapped_column(
        UUID(as_uuid=True), ForeignKey("capa_eightd.report_id", ondelete="CASCADE"), nullable=False
    )

    product_type_code: Mapped[str] = mapped_column(String(20), nullable=False)
    product_line_code: Mapped[str | None] = mapped_column(String(20), nullable=True)
    # notify 行：具体 PL；skip 行：NULL（type 级一行）

    factory_id: Mapped[uuid.UUID | None] = mapped_column(
        UUID(as_uuid=True), ForeignKey("factories.id", ondelete="RESTRICT"), nullable=True
    )  # 目标 PL 所属厂；skip 行可 null

    recipient_user_id: Mapped[uuid.UUID | None] = mapped_column(
        UUID(as_uuid=True), ForeignKey("users.user_id", ondelete="SET NULL"), nullable=True
    )
    recipient_label: Mapped[str] = mapped_column(String(120), nullable=False)

    decision: Mapped[str] = mapped_column(String(16), nullable=False)  # notified | skipped
    status: Mapped[str] = mapped_column(String(16), nullable=False)
    # notified | pending | processed
    # notify+有人 → notified；notify+无人 → pending；skip → processed

    skip_reason: Mapped[str | None] = mapped_column(Text, nullable=True)
    payload: Mapped[dict] = mapped_column(JSONB, nullable=False, default=dict)

    decided_by: Mapped[uuid.UUID] = mapped_column(UUID(as_uuid=True), nullable=False)
    decided_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), nullable=False)
    created_at: Mapped[datetime] = ...
```

**唯一性（实现时迁移表达）**：

- notify 行：`UNIQUE NULLS NOT DISTINCT (check_id, product_type_code, product_line_code, recipient_user_id)`  
  （PostgreSQL 15+ `NULLS NOT DISTINCT`；无人行 `recipient_user_id` IS NULL 时同一 PL 仅一行）
- skip 行：`UNIQUE (check_id, product_type_code) WHERE decision = 'skipped'`（部分唯一索引）

### 4.3 `similar_products[]` 元素

故事字段 `product_id` → 本设计 **`product_type_code`**。

```json
{
  "product_type_code": "DC-DC",
  "product_type_name": "DC-DC 转换器",
  "hit_criteria": ["same_product_type", "shared_fmea_mode"],
  "suggestion_direction": "请复核该类型产品 FMEA 中同类失效模式的探测度与预防控制…",
  "product_lines": [
    {"code": "DC-DC-200", "factory_id": "<uuid>", "name": "…"}
  ],
  "evidence": {
    "shared_fmea_mode": [{"fmea_id": "<uuid>", "node_id": "…", "matched_text": "…"}],
    "shared_control_plan": [{"cp_id": "<uuid>", "characteristic_keys": ["…"]}],
    "same_supplier_material": [{"supplier_id": "<uuid>", "material_code": "…"}]
  }
}
```

- **排除**：源 8D 的 `product_line_code` 永不出现在任何 `product_lines`。
- **无 type 的 PL**：`product_type_code = "unknown"`，`product_type_name = "未分类"`，避免丢掉依据 2/3/4 命中。
- **`hit_criteria` 枚举**（故事契约）：  
  `same_product_type` | `shared_fmea_mode` | `shared_control_plan` | `same_supplier_material`

### 4.4 CAPA 投影 `lateral_diffusion`

挂在 `GET /capa/{id}` 与 advance 关闭成功响应：

```json
"lateral_diffusion": {
  "check_id": "<uuid>",
  "status": "done | empty",
  "llm_status": "done | skipped",
  "truncated": false,
  "similar_products": [ /* 4.3 */ ],
  "decision": null | "notified" | "skipped",
  "notifications": [
    {
      "notification_id": "<uuid>",
      "product_type_code": "DC-DC",
      "product_line_code": "DC-DC-200",
      "recipient_label": "engineer",
      "decision": "notified",
      "status": "notified"
    }
  ]
}
```

- 无 check 行 → `lateral_diffusion: null`（未关闭或历史单）。
- `decision`：任一 notification 的聚合——全 skip → `skipped`；存在 notify 行 → `notified`；无 notification → `null`。

## 5. 关闭钩子与错误契约

### 5.1 顺序

```
advance_capa(D8_APPROVAL_PENDING → D8_CLOSURE):
  1. sink_capa_on_close(...)                 # 01.8 既有
  2. run_lateral_diffusion_check(db, capa, user_id)  # 01.9
  3. capa.status = D8_CLOSURE
  4. AuditLog TRANSITION + D8_APPROVED
  5. AuditLog LATERAL_DIFFUSION_CHECKED（在 step 2 内写）
```

任一步抛错 → 整笔事务回滚（含 01.8 未提交沉淀）。

### 5.2 异常类型（服务层）

| 异常 | API | body |
|---|---|---|
| `LateralBlockedError` | 422 | `{ "outcome": "blocked", "stage": "lateral_diffusion", "message": "…" }` |
| `LateralFailedError` | 422 | `{ "outcome": "failed", "stage": "lateral_diffusion", "message": "…" }` |

与 01.8 对齐：路由层 catch 后转 `HTTPException`；前端 `formatCapaAdvanceError` 增加 lateral 文案映射。

**何时抛**：

| 条件 | 结果 |
|---|---|
| 确定性匹配异常 | `failed` |
| `similar_products` 非空且 `build_client` 失败 / 无凭证 | `blocked` |
| `similar_products` 非空且 LLM 调用/JSON 校验失败 / 缺 type 项 | `failed` |
| `similar_products` 为空 | 不调 LLM；`status=empty`；**不抛** |

### 5.3 幂等

- `check_id = uuid5(NAMESPACE_URL, f"lateral_check:capa:{report_id}")`
- 关闭边重入 / rerun：upsert 同一 check 行，覆盖 `similar_products` / status / llm_status
- **已存在 notification 行时**：`run_lateral_diffusion_check` 在 advance 路径仍可刷新 check 内容，但 **decide 拒绝重复**；rerun 在已 decide 时 409（本轮不做 force 清空）

## 6. 四依据算法（确定性）

### 6.1 输入快照

| 输入 | 来源 |
|---|---|
| `source_pl` | `capa.product_line_code` |
| `source_factory` | `capa.factory_id` |
| `source_type` | `ProductLine.product_type_code`（可 null） |
| `source_supplier` | `capa.supplier_id`（可 null） |
| `fmea_mode_texts` | 01.4 关联 FMEA 图中 FailureMode / Cause 节点文本，经规范化 |
| `cp_keys` | 源 PL 有效控制计划 items 的稳定特性键（characteristic / process_char / special_char 等，实现时定一稳定拼接规则并单测锁死） |
| `material_codes` | D3 受影响物料 / 关联 IQC 物料 code 集合；空则依据 4 跳过 |

**文本规范化**（依据 2）：`strip` → 小写 → 连续空白折叠为单空格。

### 6.2 范围

- 当前租户 schema 内**全部工厂**的 `product_lines`（`is_active=true`）
- 始终排除 `code == source_pl`
- FMEA / CP 查询带各自行级 `factory_id`，不串租户（schema-per-tenant 已隔离）

### 6.3 依据细则

| 依据 | 规则 | 跳过条件 |
|---|---|---|
| **1 `same_product_type`** | 其他 PL 的 `product_type_code == source_type` | `source_type` is null |
| **2 `shared_fmea_mode`** | 其他 PL 的 FMEA（非已删/无效；实现锁定 status 白名单）图中 FM/Cause 规范化文本与源集合交集非空 | 源 `fmea_mode_texts` 空 |
| **3 `shared_control_plan`** | 其他 PL 有效 CP item 特性键与源 `cp_keys` 交集非空 | 源 `cp_keys` 空 |
| **4 `same_supplier_material`** | 其他 PL 存在同一 `supplier_id` + 同一 `material_code`（IQC 物料主数据或 D3 批次关联） | `source_supplier` 空 **或** `material_codes` 空 |

### 6.4 聚合与截断

1. PL 级：每个命中 PL 累积 `hit_criteria[]` + `evidence`
2. 按 `product_type_code`（缺省 `"unknown"`）分组 → `similar_products[]`
3. 上限：最多 50 个 type 组；每组最多 30 条 PL；超出设 `truncated=true` 并截断（稳定排序：type_code asc，PL code asc）

### 6.5 LLM 建议方向

- 仅当聚合后 `similar_products` 非空
- `complete_json` 输入：8D `document_no/title/severity` + D2 摘要 + D4 根因 + D7 预防要点（均截断）+ 每 type 的 `hit_criteria` + evidence 摘要
- 期望输出：`{ "items": [ { "product_type_code": "...", "suggestion_direction": "..." } ] }`
- **严格**：返回项必须覆盖全部命中 `product_type_code`；缺项 → `failed`
- 写回各元素的 `suggestion_direction`

### 6.6 写库 + 审计

```
upsert capa_lateral_diffusion_checks
AuditLog(
  table_name="capa_eightd",
  record_id=capa.report_id,
  action="LATERAL_DIFFUSION_CHECKED",
  changed_fields={
    "check_id": str(check_id),
    "similar_count": len(similar_products),
    "status": status,
    "truncated": truncated,
    "product_type_codes": [...],
  },
  operated_by=user_id,
)
```

## 7. API

| 方法 | 路径 | 权限 | 行为 |
|---|---|---|---|
| （既有） | `POST /api/capa/{id}/advance` → D8_CLOSURE | `canApprove('capa')` | 同事务 01.8→01.9；成功响应含 `lateral_diffusion` |
| （既有） | `GET /api/capa/{id}` | 读 CAPA | 投影 `lateral_diffusion` |
| 新增 | `POST /api/capa/{id}/lateral-diffusion/decide` | `canEdit('capa')` | 见 7.1 |
| 新增 | `POST /api/capa/{id}/lateral-diffusion/rerun` | `canEdit('capa')` | 见 7.2 |

### 7.1 Decide

**Body：**

```json
{
  "decision": "notify" | "skip",
  "skip_reason": "string, required if skip（非空白）",
  "product_type_codes": ["DC-DC"]
}
```

- `product_type_codes` 可选；缺省 = 该 check 全部命中 type
- 必须是 check 中已有 type 的子集；未知 code → 422
- 无 check → 404
- `status=empty` → 422「无类似产品，无需决策」
- 已存在任一 notification → **409**
- CAPA 状态须为 `D8_CLOSURE` 或 `ARCHIVED`

**notify 写库：**

对每个选定 type 下每个 `product_lines[]` 项：

1. 解析收件人（§8）
2. 每人一行（或无人一行）：`decision=notified`，`status=notified|pending`，填 `payload`
3. 审计一条 `LATERAL_NOTIFICATION_SENT`（`changed_fields` 含 count、product_type_codes、notification_ids 摘要）

**skip 写库：**

每个选定 type **一行**：`product_line_code=null`，`decision=skipped`，`status=processed`，`skip_reason` 必填；审计 `LATERAL_NOTIFICATION_SKIPPED`。

**响应：** 更新后的 `lateral_diffusion` 投影。

### 7.2 Rerun

- 仅 `D8_CLOSURE | ARCHIVED`
- 已 decide → **409**（本轮无 `force`）
- 未 decide：重跑 §6，upsert check，返回投影
- 无 LLM 且将产生命中 → 与关闭边相同 blocked/failed

## 8. 收件人解析

对目标 `product_line_code`：

1. `UserProductLine` where `product_line_code = PL`
2. 用户 `is_active`
3. 角色 `role_key ∈ {quality_engineer, manager}`（经 user_roles → role_definitions）
4. 工厂可见：`user.factory_id is null` **或** `user.factory_id == pl.factory_id`；若存在既有 factory-access 表/helper 则并入（实现时对齐 `check_factory_access` / 用户工厂列表，禁止串出租户）
5. 去重 `(PL, user_id)`

| 结果 | 行 |
|---|---|
| ≥1 用户 | 每用户一行；`status=notified`；`recipient_label=username` |
| 0 用户 | 一行；`recipient_user_id=null`；`recipient_label="未找到负责人"`；`status=pending` |

**payload 最小集：**

```json
{
  "document_no": "...",
  "title": "...",
  "severity": "...",
  "d2_summary": "...",
  "hit_criteria": ["..."],
  "suggestion_direction": "...",
  "source_capa_id": "<uuid>",
  "product_type_code": "..."
}
```

## 9. 前端

### 9.1 关闭后弹窗 `LateralDiffusionModal`

- 触发：approve 关闭成功且 `lateral_diffusion.status === "done"` 且 `similar_products.length > 0` 且 `decision == null`
- 展示：type 列表、`hit_criteria` Tag、`suggestion_direction`、可展开 PL（含 factory）
- 操作：通知 / 不通知（skip 必填理由）
- testid：`lateral-diffusion-modal`、`lateral-hit-{product_type_code}`、`lateral-decide-notify`、`lateral-decide-skip`、`lateral-skip-reason`

### 9.2 常驻 `LateralDiffusionCard`

- 可见：`D8_CLOSURE | ARCHIVED` 且 `lateral_diffusion != null`
- 内容：检查状态、命中摘要、决策状态、通知列表（recipient/status）
- 未 decide 可打开 Modal；可触发 rerun（未 decide）
- testid：`lateral-diffusion-card`

### 9.3 错误文案

`formatCapaAdvanceError` 映射：

- `stage=lateral_diffusion` + `blocked` → 横向扩散被阻断：LLM 未配置
- `stage=lateral_diffusion` + `failed` → 横向扩散检查失败，可重试关闭

### 9.4 i18n

`frontend/src/locales/{zh-CN,en-US}/capa.json` 增加 lateral 相关键（与现有 capa 命名风格一致）。
