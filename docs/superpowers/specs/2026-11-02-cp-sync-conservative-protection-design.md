## 1. 为什么补充

Task 6 静态核对发现，现有 CP 同步、通用更新和草稿回退没有可复用的“受 CAPA 评审行禁止改删”运行时保护。CAPA 的版本审核、覆盖检查和部署扫描并不是写入授权检查；其中 `expected_action=delete` 还允许合法的删除意图。因此，不能继续把“沿用已有保护”当作已实现前提。

制定本补充时，Task 6 尚无生产或测试代码改动。此前 101 项既有回归通过，仅是调查基线，不代表新同步通过。

用户已选择：本次采用保守保护，阻止自动同步改删活动 CAPA 引用的行；历史快照本身不永久锁住草稿；带执行关联的行不自动删除；不新增解除保护或 CAPA 特批删除流程。下文将该选择落实为可验收的规则，已于 2026-11-02 获用户确认，按此继续实施。

## 2. 适用范围与非目标

- 约束本次新增的 **PFMEA → CP 自动同步预览和应用**，保护受控内容，不改变标准表格栏目。
- CP 必须处于现有允许编辑的草稿状态；已批准 CP 仍不可由本路径修改。历史批准版本与哈希永不改写。
- 新规则不是对全部 CP 写入口的统一治理。现有手工编辑、通用更新、回退语义不在本补充中擅自改成新审批流程，也不能把这些入口推荐为绕过同步保护的办法。
- CAPA 的现有目标、审核、决定发布流程只做必要的 CP 输入锁定／新鲜度协调，不改变其通过、阻断、延期或豁免的业务语义。
- 不实现“勾选后强制修改”、保护解除、特批删除、新角色或新权限等级。
- 不删除 SPC、量具、MSA 研究、特殊特性、CAPA 材料或其他关联证据。
- 若后续要对所有手工写入口施加相同禁止规则，或允许 CAPA 指定删改通过该同步执行，需另行设计和确认，不能混入本次补充。

## 3. 保护判定的事实来源

### 3.1 活动 CAPA

沿用 `backend/app/state_machines/eightd_state.py` 的 `capa_open_clause`／`is_capa_open_value`：除 `D8_CLOSURE`、`ARCHIVED` 外的现有状态均为活动状态，包括 `D7_COMPLETED`、`D8_GATE_PENDING`、`D8_APPROVAL_PENDING`。

不新增“已评审”状态枚举。未知状态视为无法安全判定并返回阻断，不默认为已关闭。

仅查询同租户、同工厂、同产品线内的相关 CP/CAPA，不能靠同名对象或显示名称建立引用。越权返回不泄露对方 CAPA 的名称、编号或内容。

### 3.2 当前有效材料

每个活动 CAPA 按以下范围确定保护依据：

1. 当前完成的影响分析：`CapaDocgAnalysis.is_current=True` 且 `status='done'`。
2. 此分析的最新决定，按既有 `revision` 语义选取；其 `audit_run_id` 关联的审核批次与 `version_snapshot` 是决定所绑定的材料。
3. 无决定但有审核时，采用此分析最新完整审核批次。批次无法唯一解析时，不猜测为无保护。

已被替换的旧分析、旧审核批次、旧决定，以及与活动流程无关的历史 CP 快照，不会单独永久保护当前草稿。仍保留它们原有不可变证据，不改写旧记录。

没有当前完成分析时，不能仅因一个 CAPA 与 FMEA 同源就推断它引用了所有 CP 行。运行中的分析尚未公布的新引用，通过第 6 节发布互斥与输入重校验处理。

### 3.3 从材料定位受保护行

使用完整 CP 文档 UUID 和 CP 行 `item_id`，不使用特性名称、工序号或 `source_fmea_node_id` 替代行身份。

- 当前 `affected_docs` 中 `doc_type='control_plan'`、`doc_id` 匹配该 CP 的 `key_points`：`target_kind='cp_item'` 的 modify/delete 目标，其 `target_key` 对应的现存行受保护。
- 当前有效审核 `coverage` 的 `key_point` 中明确引用的同一 CP 行同样受保护，不因结果是 passed/pending_update/incomplete 而绕开。
- 当前有效审核的 `version_before`／`version_after` 及决定的 `version_snapshot` 若绑定了该 CP 的实际版本，解析、验证该版本后，版本 `items_snapshot` 中仍存在于当前 CP 的行纳入保护。这是活动评审的有效引用，不等同于扫描任意历史快照。
- 整份文档的 `add` 意图本身不凭空保护全部旧行；若已有有效版本引用，则按上一项确定范围。
- 对已能确定引用该 CP、但材料结构、目标 UUID、版本归属或哈希无法安全解析的记录，阻断该 CP 的自动改删并提示材料需复核；不静默忽略。正常新增独立行是否可用仍依据原同步契约与选择校验，不把无法判定当作删除授权。

保护的是当前实际存在的行；历史目标已不存在时不复活、不伪造 CP 行。已缺失目标的审核／豁免规则继续按原 CAPA 逻辑处理。

## 4. 操作规则

| 对象／情形 | 同步修改 | 同步删除 | 处理方式 |
| --- | --- | --- | --- |
| 已批准 CP | 阻止 | 阻止 | 保持既有状态保护 |
| 活动 CAPA 当前有效材料引用的现存行 | 阻止实际内容变更 | 阻止 | 保留行和全部来源／执行关联，提示 CAPA 材料复核 |
| 只有无关历史快照引用的草稿行 | 按原同步校验 | 按原同步校验及关联保护 | 不因单纯历史存在永久锁住 |
| 无 CAPA 保护、带 SPC／量具关联的行 | 保留关联，变化后提示适用性复核 | 阻止自动删除 | 不删除／清空关联，不改 SPC 或量具实体 |
| 被特殊特性记录 `cp_item_id` 引用的行 | 保留关联并复核适用性 | 阻止自动删除 | 不自动置空、迁移或级联删除特殊特性 |
| 无保护、无执行／反向关联、来源及基线可信的草稿行 | 显式预览后按原契约处理 | 来源确实移除且显式选择后允许 | 权限、锁、摘要、逐行基线及事务要求不变 |
| 无可靠来源基线的旧／混合／手工行 | 冲突复核，不自动覆盖 | 不因源图没有它就删除 | 不能重绑到第一个同名对象 |

“实际内容变更”至少包括特性名称、产品／过程列、规范、特殊分类、工序号／名称、设备，以及将行移到不同来源对象。来源接受版本推进属于受控材料的追溯变化；不能在行被阻断时偷偷推进其 `accepted_source_version_id`，也不能更新它的字段后声称只改元数据。

值与来源材料均无变化的真正 no-op 不算修改。受保护行已有差异时保持 pending；不能通过只推进元数据让它显示已同步。

## 5. CAPA 的明确删除意图

本次规则不把 `expected_action='delete'` 当作自动同步的特批：

- 只要行属于第 3 节活动有效材料，自动同步的删除候选就被阻断。
- 不能把审核覆盖命中、已有 waiver、预览摘要或用户勾选当作新的前置删除授权。
- 不修改原 CAPA 覆盖计算，仍保留其对实际合法删除的识别能力。
- 本同步不提供解除保护路径，也不指导用户通过直接改库、通用更新或回退绕过。

因此，某些 CAPA 所要求的删除不会由本次自动同步完成。这是用户选择的保守边界，而不是已经具备正式受控删除流程。相应待办保持明确，不自动完成或自动关闭 CAPA。

## 6. 并发与发布协议

不能只在预览中检查，或只在同步端查询一次 CAPA 后立即删除。

1. 预览只读，输出保护原因及对应候选的不可应用状态，不加写入型锁，不改变分析／审核／决定。
2. 应用沿用 Task 5 的作用域、CP 父对象、来源版本和授权锁协议；取得目标 CP 写锁后，重新读取当前已提交的有效保护材料与执行／反向引用，再核对完整预览摘要和选择。
3. 当前 CAPA 目标清单发布、相关审核／决定落库若将该 CP 作为有效输入，必须在其发布事务中取得与 CP 写锁相冲突的对应 CP 父锁，并在等待后重新核对输入版本／行身份。不能在持有旧结果时直接发布为新有效材料。
4. CAPA 分析的外部计算阶段不持有数据库锁；只在最终发布／输入重校验阶段参与协议。运行中但尚未公布的引用不能制造“无行可锁所以安全”的幻象。
5. 同步保护判定不修改 CAPA 状态、分析、审核或决定，不为扫描而逐项锁 CAPA 根对象；避免引入 CP→CAPA 与既有 CAPA→CP 的反向锁循环。涉及多个 CP 时以稳定 UUID 顺序取得对应 CP 父锁。
6. 同步先完成时，之后发布的 CAPA 材料必须基于新 CP 重新校验，失效则返回可解释的需重算／重审结果；CAPA 发布先完成时，同步应看到引用并阻断对应改删。
7. 删除关联检查必须与关联新增写入兼容：反向特殊特性引用受 CP 行／外键锁保护；新增关联等待后必须重新确认目标仍存在。不得靠删除外键或级联策略掩盖冲突。
8. 因保护变化而过期的选择返回 409，要求重取预览；失败后无行、来源版本、审计或 CP 版本的部分提交。不能在异常后改走旧同步实现。

实现前应对实际 CAPA 发布／审核／决定写入口逐个标出参与点，并与现有锁顺序核对。若既有多阶段提交无法在上述事务边界安全参与，作为设计阻塞重新说明，不能悄悄扩大为全局租户／审批重构。

## 7. API 与呈现

沿用 Task 6 的 action、candidate_key、issues/conflicts 结构，不新增标准表格列。

建议问题码：

- `protected_capa_material`：活动有效 CAPA 材料引用该行。
- `linked_execution_reference`：SPC／量具／特殊特性等关联禁止自动删除。
- `protection_state_unresolved`：已识别该 CP 的材料无法安全解析。

预览对不可应用项给出明确原因。应用若选择了被阻断项，整次拒绝并返回安全业务错误，不悄悄跳过后报告全部成功；允许用户重新选择同一有效预览中可应用的其它项，仍按原契约核对摘要、保护新鲜度与部分覆盖。

对无 CAPA 阅读权限但有 CP 写权限的用户，可以提示“存在受控流程引用，需复核”，不能回传无权查看的报告编号、状态细节或目标内容。审计后台保留授权范围内的操作者、CP 行、拒绝／变更原因及依据标识，不泄露材料正文。

## 8. 实现范围

确认后在 Task 6 的现有文件范围外，允许增加一个聚焦服务，例如 `backend/app/services/cp_sync_protection.py`，负责只读保护解析、候选判定和写入时重检；不建设通用审批引擎。

必要适配仅涉及：

- 新同步的预览／应用、来源接受及 pending 计算。
- `capa_doc_gate_service.py` 中当前目标清单发布、审核及决定落库的 CP 输入锁／新鲜度协调，以及它实际调用的局部 helper。
- 如特殊特性链接写入缺少必要的目标存在性／锁检查，仅补与本删除竞态直接有关的校验，不改提取和分类政策。
- 对应的单元、真实 PostgreSQL 双会话及 API 测试。

CP 通用更新、回退、CAPA 正式特批删除、全局租户生命周期及任意历史材料清理不在本补充中改变语义。发现其它写入口可能影响新协议时，列出具体交错再确认，不以“不在范围”为由宣称安全已完成。

## 9. 验收条件

1. 活动状态按现有枚举判断；D8_CLOSURE／ARCHIVED 不因其历史材料永久保护草稿。
2. 当前分析的明确目标、当前审核覆盖目标、当前有效审核／决定的 CP 版本引用均能定位保护；旧已替换材料不会单独永久锁行。
3. 同名／相同工序号／同特性 UUID 的不同文档、工厂或租户不能串联保护；无权用户看不到关联 CAPA 明细。
4. 当前材料 malformed、版本归属／哈希错误时 fail closed，并有可解释问题，不返回假阴性。
5. 受保护行的修改／删除均拒绝，真实 no-op 不被误当修改；不偷偷推进接受版本或清 pending。
6. CAPA `expected_action=delete`、已有 waiver 或客户端选中不能绕过本次保守规则。
7. SPC／量具关联及特殊特性反向引用分别覆盖；删除拒绝后所有关联和证据保持，不只验证外键异常。
8. 合法无关联草稿来源删除仍可明确确认执行，不把保守规则扩大为永久禁止全部删除。
9. 保护变化使预览过期；不可应用选项整次拒绝，可应用子集保持真实 pending 与来源版本。
10. 真实双会话分别覆盖：同步先提交／CAPA 先发布、审核／决定替换与同步、CAPA 关闭与保护重检、关联新增与删除。没有死锁、越权、假同步或部分提交。
11. 本轮不修改历史快照、标准表头、权限等级、CAPA 覆盖含义或全局租户机制；既有特性、导入、权限替换竞态及 CAPA 回归保持通过。
