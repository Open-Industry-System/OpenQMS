# Oracle preview setup and verification

Use the shared `deploy-oracle-release.py` guarded release pipeline in its built-in preview mode, backed by `oracle-preview-remote.py::PreviewRelease`. `deploy-oracle-preview.py --cleanup N` supports trusted closed-PR cleanup. Build and runtime-network prerequisites have been verified on Oracle; live application rollout, preview TLS issuance and the full preview lifecycle remain pending.

## Trusted host installation

Install the protected-default-branch controller bundle root-owned under the location required by the shared forced-command receiver. Include `compose.preview.yml`, `scripts/oracle-preview-remote.py`, `scripts/oracle-preview.py`, `scripts/oracle-preview-initialize.py`, the shared production helper and manifest checker, plus `deploy/preview-Caddyfile`. Candidate PR source is build context only; it must never supply host scripts, Compose files or privileged commands. Host Python must be 3.12+.

Install trusted `deploy/preview-Caddyfile` as `/etc/openqms/preview-Caddyfile`, mode 0644. Create root-owned `/etc/openqms/preview-routes`, root-only `/var/lib/openqms-previews`, and external Docker network `openqms-preview-edge`. Include trusted `deploy/preview-edge.override.yml` in production Compose and install matching `/etc/openqms/production-edge-Caddyfile`. Production Caddy remains fixed at 172.30.0.10 internally. Only production and preview web containers join the edge network. Snippets are mounted read-only; the Caddy administrative API uses a container-local Unix socket with no TCP or host socket exposure. Apply this edge configuration through guarded production rollout.

Provision dedicated buildx docker-container builder `openqms-preview-builder` and container `buildx_buildkit_openqms-preview-builder0`: positive memory <=2GiB, NanoCpus <=2 CPUs and PidsLimit <=512, plus rotated logs. The preview helper checks these limits before build and requires canonical NanoCpus-only configuration: CpuQuota=0 and CpuPeriod=0. A real legacy-quota-to-NanoCpus update reported bounded NanoCpus while the running cgroup cpu.max remained unlimited. Existing builders with any nonzero legacy quota/period must be deliberately recreated by an administrator and their live CPU limit verified; automatic quota conversion is forbidden. Configure builder egress policy to block host/private infrastructure while permitting required package registries. No production/GitHub credentials or production data may enter this builder. Trusted PR authors still execute arbitrary application/build code within these boundaries.

The production frontend context includes the exact shared source helper `frontend/e2e/helpers/characteristic-diagnostics.ts`, which a checked TypeScript unit test imports. Other E2E sources, environment files, session state and private keys remain excluded. Production keeps the complete TypeScript check; this exception does not add test sources to the final Caddy stage, which copies only Vite output and its Caddyfile.

Preview backend builds explicitly use `PIP_INDEX_URL=https://pypi.org/simple`, matching production Compose. Oracle could not reach the development Dockerfile’s default regional mirror in the same bounded build namespace, while the official index returned HTTP200. The frontend receives no pip setting, and developer Dockerfile defaults remain unchanged.

The runtime edge bridge also needs scoped egress filtering: a PR controls its web image and ordinary HTTP must not reach host services or OCI metadata. Preserve established replies, same-edge TCP8080 proxy traffic, the actual DNS resolver on TCP/UDP53 and public TCP80/443 for Caddy/ACME; deny host addresses, private/CGNAT/link-local/reserved destinations and other traffic. Filter host INPUT separately while preserving established responses, and explicitly block IPv6 forwarding/input when the edge network has IPv6 disabled. Keep production/backend and per-preview private bridges outside these rules. Verify real DNS, proxy, host-originated published-port replies and metadata/private denial before activation.

On the configured Oracle host, the dedicated interfaces are `br-oq-build` and `br-oq-edge`, with root-owned `openqms-preview-build-firewall.service` and `openqms-preview-edge-firewall.service` ordered before Docker. Their rules select only these interfaces. The Docker container builder was deliberately recreated from its inspected fresh Config/HostConfig, retaining its state volume and network while setting per-container json-file logging to 5 MiB × 2, public build DNS and canonical resource bounds; no Docker daemon restart was needed. Recreating that container later requires restoring and revalidating those settings, including live cgroup limits. The installer reuses existing resources; it does not provision or attest firewall/log policies.

Use a dedicated deployment account and pinned SSH host identity. Forced-command keys, no interactive login and no Docker group membership are required. The shared receiver uses a persistent deployment lease and narrowly scoped verbs; no arbitrary SSH/scp is authorized. Preview target forwarding must permit only `127.0.0.1:25432` and `127.0.0.1:25433`, never wildcard forwarding or production port 5432. Do not reuse unrestricted ubuntu/root credentials.

## Preview release contract

The shared pipeline stages immutable exact-tested SHA source, validates source/controller manifests, builds bounded images, then starts only owned PostgreSQL/Redis/Neo4j infrastructure. At most two preview inventories exist. Each project creates mode-0600 random independent secrets; its database binds one fixed loopback slot solely for the verified SSH target tunnel. Application and data networks have no shared production connectivity. Compose bounds all six services' CPU, memory, PIDs and logs.

The local shared pipeline registers/labels its independent GitHub-hosted test database and preserves the mandatory `make deploy-release` sequence against verified distinct runtime database identities. Candidate migration/preflight code executes only inside bounded target containers, while the credentialed runner executes trusted control code and revalidates unprivileged CI receipts for checks. It verifies target identity through its tunnel, migrates the preview target inside a bounded target container, revalidates exact successful unprivileged CI check receipts, initializes preview accounts through the trusted readonly container helper, runs target preflight, revalidates current GitHub authorization/SHA/state, and rolls out. The initializer receives numeric PREVIEW_PR, seeds only an empty preview database without printing credentials, rotates/disables all nonviewer accounts and revokes their refresh sessions, and verifies the public readonly viewer. Candidate application code never runs on the privileged host Python interpreter. Runtime container ownership and image IDs are verified before route publication.

Each numeric PR route is `pr-N.preview.openqms.smartindustry.world`. Configure wildcard A/AAAA DNS to Oracle ingress and permit HTTP80/HTTPS443. Each host obtains its own HTTP-01 certificate; no DNS credentials or wildcard certificate are used. Rehearse ACME and Caddy validation/reload behavior before enabling previews.

Cleanup locally reads current GitHub PR metadata twice, including immediately before authorizing the host cleanup handshake. It requires GH_TOKEN and GITHUB_REPOSITORY locally, with no token transfer to Oracle and no release-run gate. Cleanup acquires the host flock, validates exact project/PR labels, removes the route first, removes only those owned containers/volumes/networks, then revokes its secret file and frees the loopback slot. Immutable source/manifests remain for audit. Rejected or failed staging can retain a partial stack counting against capacity; cleanup is required before capacity can be reused. Updating a preview can temporarily disrupt its prior runtime.

## Verification status

Preview unit tests cover canonical inputs, capacity, ownership, route rollback and cleanup ordering, fresh cleanup authorization/reopened PRs, stale publication prevention, scoped secrets/ports, initializer invocation and runtime-image publication guards. Trusted Compose configuration validation and Python compilation pass locally. Bounded-container initializer database integration has verified fresh seed, all nonviewer defaults disabled/rotated, refresh session revocation, retained readonly viewer and clean CAPA preflight. Real host execution, TLS issuance and route lifecycle still require their corresponding integration/lifecycle checks; unit tests do not prove live deployment success.
