# PR 预览验收与合并

1. 创建 PR 时填写模板中的预览验收计划：影响页面/角色/流程、每项操作步骤及预期结果、权限拒绝与回归检查。至少一条具体场景；保留模板标记与表头，替换所有占位内容。已有 PR 也须补充这一部分，草稿同样适用。
2. `PR test plan` 自动检查描述。缺失章节、空表或占位内容会失败并要求补充。修改 PR 描述会重新检查并触发 CI；可信部署资格门禁也会读取最新描述，未补齐则不发布。
3. 完整 CI 通过后，Oracle 工作流发布 `https://pr-<编号>.preview.openqms.smartindustry.world`。人工验收检查不阻塞预览部署。发布成功时产生受信工作流 artifact，绑定仓库、PR、head SHA 和实际 merge SHA。
4. 人工打开预览，逐项执行计划。从 PR 下“测试环境已就绪”评论（或 **PR preview acceptance** 工作流 Summary）复制完整的 `/preview-accept <head SHA> <发布 run ID> <计划摘要>` 命令，在 PR 评论中另附具体测试结果或截图链接。命令自身不能视为测试结果。默认允许作者或具有 write/maintain/admin 权限的协作者确认；Bot 账号、无写权限账号、部署前的评论均不被接受。若需独立审核，将受信 workflow 中 `REQUIRE_INDEPENDENT_REVIEWER` 改为 `'true'`。
5. main 规则集须将 `PR test plan` 与 `Preview human acceptance` 加入必需状态检查，保留原完整 CI 检查与严格最新 main 要求。两项成功后才能合并。不得通过删检查或管理员绕过代替验收。

新提交、计划内容修改、预览重新发布或删除确认评论后需要重新核验；旧 head、旧计划、旧 merge、过期 artifact 不能完成当前验收。预览重新发布后，应等待新的工作流检查，再复制新的命令确认。描述中验收区块之外的文字不改变计划摘要。机器人只能校验人工声明的来源和版本，无法证明人工真的执行过浏览器操作；确认人对实际结果负责。

元数据工作流仅执行默认分支上的受信脚本，不执行 PR 源码，不领取生产/预览 SSH Secrets。`issue_comment` 修改/删除、PR 描述/提交更新和 Oracle 发布完成都会重新检查；API/证据读取异常保持失败或等待，不能沿用旧成功。异常修复后可手动运行该工作流复核。单次最多读取 1000 条 PR/评论元数据，超限拒绝而非截断授权；发布查找限最近 100 次成功工作流，旧预览须重新发布。

## 首次启用顺序

本功能首次引入时，默认分支还没有该元数据工作流和发布回执。因此先在实现 PR 上完成已有完整 CI、实际预览和人工确认，再合入；合入后验证受信工作流已产生两个状态，最后将两个状态加入 main 规则集。提前要求尚未存在的状态会导致启动死锁。既有 PR 缺计划时需作者补充具体业务检查项，不由机器人伪造验收计划或人工结果。

## 发布通知与资源释放

发布回执验证当前 PR、head 与 merge SHA 后，机器人在 PR 下创建“测试环境已就绪”评论，包含 HTTPS 地址、版本、发布记录与人工确认命令。后续发布更新同一条机器人评论；内容无变化则不编辑。用户伪造同名标记的评论不会被修改，机器人自己的通知事件也不会触发循环运行。已有预览过期时刷新为等待当前版本状态，不能沿用旧通知验收。

PR 合并或直接关闭都会触发受信清理，且不依赖生产/预览发布开关。清理按项目归属检查移除预览路由、容器、命名/匿名数据卷、独立私网和预览 secret 文件，释放端口槽位；生产、共享网络与审计/源码记录保留。清理步骤成功后，同一评论改为“预览资源已释放”，停用测试地址；步骤失败/中断则通知清理未完成并提供工作流链接，不假报释放。PR 重新打开时拒绝旧清理通知，并要求重新发布、验收。
